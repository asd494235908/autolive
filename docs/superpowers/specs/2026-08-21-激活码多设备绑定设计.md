# 激活码多设备绑定设计

> 状态说明（2026-08-22）：本文记录迁移 0022 和“创建时设置 1～100 台容量、列表展示绑定进度”的已实施基线。后续的完整明文重新查看、独立设备绑定明细、容量修改和核销设备切换已转入 [`服务端商业化与生产能力补齐设计`](./2026-08-21-服务端商业化与生产能力补齐设计.md) 与 [`服务端商业化与生产就绪 PRD`](../../../tasks/prd-server-commercial-production-readiness.md) Phase 3；后续方案采用独立 `activation_code_secrets` 加密表，不修改本文的历史实施证据，当前尚未实施。

## 背景

当前激活码创建接口虽然已有 `max_devices` 字段，但服务端把它固定限制为 `1`，数据库也只记录首次核销设备。管理端创建表单因此固定提交 `max_devices: 1`，列表无法展示多设备绑定进度。

## 目标

- 管理员创建激活码时可以选择最多绑定的设备数量。
- 同一个激活码可以被不同设备分别核销，最多成功 `N` 台。
- `N` 默认值为 `1`，允许范围为 `1～100`。
- 每次核销在同一事务内校验、绑定设备、增加已绑定数量并更新激活码状态。
- 管理端列表展示 `已绑定数量 / 最大设备数`。
- 已有单设备激活码和历史已核销数据继续可读、可核销语义不变。
- 当前基线中激活码明文仍只在创建成功响应中返回一次；列表和重试响应不返回明文。后续仅允许对新生成激活码通过独立加密表和管理员二次验证提供重新查看，历史哈希-only 激活码保持不可逆。

## 非目标

- 不允许同一台已绑定设备重复占用同一激活码配额。
- 不新增历史完整激活码查看接口，不把明文写入数据库、日志或前端静态资源。
- 不改变设备解绑、用户归属和激活码作废的既有权限语义。

## 数据模型

新增迁移 `0022_支持激活码多设备绑定.up.sql`，在 `activation_codes` 增加：

- `max_devices INTEGER NOT NULL DEFAULT 1`，约束为 `1～100`。
- `bound_devices INTEGER NOT NULL DEFAULT 0`，约束为不小于 `0` 且不大于 `max_devices`。

历史数据回填规则：已有 `used_by_device_id` 的激活码回填 `bound_devices = 1`，其余回填为 `0`。原有 `used_at`、`used_by_user_id`、`used_by_device_id` 继续保存首次核销归属，作为兼容字段；`bound_devices` 表示总绑定数量。

领域模型 `ActivationCode` 增加 `bound_devices`，列表和创建响应都返回该字段。创建响应的 `plain_code` 仍只出现一次。

## 核销流程

1. 在事务中锁定会话、用户、设备和激活码行。
2. 校验激活码未过期、未作废，且 `bound_devices < max_devices`。
3. 按现有规则拒绝已绑定或禁用设备，避免同一设备重复占用配额。
4. 写入设备状态和会话绑定。
5. 将 `bound_devices` 加一；第一次核销时写入兼容的首次归属字段。
6. 当新数量达到 `max_devices` 时将状态改为 `used`，否则保持 `active`。
7. 幂等记录、业务状态、会话绑定和审计 Outbox 同事务提交；失败全部回滚。

Memory 兼容实现沿用同一状态机和幂等语义。PostgreSQL normalized 实现使用新增字段，不回退到快照全量读改写。

## 管理端交互

- 创建表单增加 Ant Design `InputNumber`，默认 `1`，最小 `1`，最大 `100`。
- 提交时发送用户选择的 `max_devices`，不再固定发送 `1`。
- 表格显示 `bound_devices / max_devices`，缺失的历史字段按 `0 / 1` 兼容展示。
- 创建成功弹窗继续显示并支持复制一次性明文激活码。

## API 与契约

- `CreateActivationCodeRequest.max_devices` 的 OpenAPI 最大值从 `1` 调整为 `100`。
- `ActivationCode.bound_devices` 作为必需整数返回，范围为 `0～max_devices`。
- 既有激活码创建、列表、作废和客户端激活路由保持不变，只扩展字段语义。
