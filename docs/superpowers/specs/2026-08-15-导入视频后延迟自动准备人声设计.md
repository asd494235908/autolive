# 导入视频后延迟自动准备人声设计

## 目标

导入视频后仍然自动准备 XTTS-v2 与参考人声，但先让最终效果窗口稳定打开并播放，再延迟 4 秒启动自动准备，以减少导入瞬间的解码、磁盘和模型加载竞争。

## 已确认约束

- 自动准备必须保留。
- 延迟从最终效果窗口打开成功开始计算。
- 延迟固定为 4 秒，处于用户允许的 3～5 秒范围内。
- 不增加 MP4 哈希缓存；现有哈希流程继续按导入后的当前视频重新计算。
- 切换视频、组件卸载或用户取消时，未开始或正在等待的自动准备必须可取消。
- 不改变 XTTS 准备、哈希校验和播放状态机的业务语义，只调整自动准备启动时机。

## 方案

在桌面主页的导入流程中，`openFinalEffectWindowFromHome()` 成功返回后启动 `prepareVoiceCloneAfterImport()`。该函数创建自己的 `AbortController`，先执行一个可取消的 4 秒等待，再进入现有的快照轮询和哈希就绪判断；等待结束后继续调用现有 `prepareVoiceCloneSource({ automatic: true })`。

等待使用可注入的纯逻辑调度辅助函数测试，不使用任意长睡眠掩盖竞态。若等待期间 AbortSignal 被取消，函数立即返回并且不调用自动准备。现有组件卸载清理继续负责取消控制器。

## 用户状态

等待阶段继续使用现有自动准备等待状态，并把提示改为“视频已开始播放，4 秒后自动准备人声”。等待结束后沿用“等待 MP4 哈希完成后自动准备”的状态提示。哈希失败、超时和 Worker 不可用的现有错误提示不变。

## 非目标

- 不新增哈希缓存、文件指纹缓存或缓存失效策略。
- 不修改 Rust 媒体探测、哈希算法或 XTTS Worker 实现。
- 不改变用户手动“准备人声”按钮的行为。
- 不修改视频循环、固定话术播放或原音轨恢复逻辑。

## 验收标准

1. 导入并成功打开最终效果窗口后，自动准备至少延迟 4 秒启动。
2. 延迟期间视频可以继续播放，自动准备调用不会提前发生。
3. 延迟期间切换视频或卸载页面，自动准备不会被旧任务触发。
4. 延迟结束后仍会等待 MP4 哈希 ready，并调用现有自动准备入口。
5. 不出现哈希缓存相关的新代码或新配置。
6. 前端测试、构建和本地 Tauri 开发启动验证通过。
