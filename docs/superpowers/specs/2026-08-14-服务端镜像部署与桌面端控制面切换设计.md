# 服务端镜像部署与桌面端控制面切换设计

## 1. 文档状态

- 状态：已确认，待按本文档编写实施计划
- 日期：2026-08-14
- 适用范围：`backend` Go 控制面、`admin-web` React 管理前端、`desktop` Rust/Tauri 客户端
- 目标环境：本地 Apple Silicon 构建，远程服务器 `192.168.100.213` 运行 `linux/amd64` 容器

## 2. 目标

将服务端前后端以 Docker 镜像形式在本地构建并上传到远程服务器，在服务器现有 PostgreSQL Docker 集群中创建本项目独立数据库，完成数据库迁移，并将桌面端的登录、激活、设备信息、心跳、模型号池租约和调用记录接口统一切换到远程控制面。

部署完成后，管理系统和桌面端通过同一个入口访问：

```text
http://192.168.100.213:18090
```

## 3. 范围

### 3.1 本次实施

1. 为 Go 后端增加可复用的多阶段 Docker 构建文件。
2. 为 React 管理前端增加生产镜像构建文件和 Nginx 配置。
3. 以 `linux/amd64` 为目标平台在本地构建两个镜像。
4. 将镜像、Compose 部署文件和非敏感配置模板上传到服务器。
5. 使用服务器现有 `postgres-shared` 容器所在的 `shared-net` 网络连接 PostgreSQL。
6. 创建独立数据库、独立应用账号并执行现有 Go 数据库迁移。
7. 启动 Go API 和 React/Nginx 服务，并做健康检查和登录链路验证。
8. 将桌面端控制面地址改为构建期环境变量，默认指向远程统一入口。
9. 更新 Tauri HTTP 权限和相关测试，使其允许新的控制面地址。

### 3.2 本次不实施

- 不修改服务器上已有容器、已有端口和已有 Compose 项目。
- 不在服务器上执行 Docker 构建。
- 不把 PostgreSQL 新端口暴露到公网。
- 不把数据库密码、应用密钥、管理员密码写入仓库或镜像。
- 不改动桌面端媒体处理、播放器、FFmpeg 资源和实时话术幻化业务逻辑。
- 不在本次任务中引入域名、HTTPS 证书和公网反向代理；后续可在保持 API 路径不变的情况下升级。

## 4. 已确认的服务器约束

服务器只读核查结果：

- CPU 架构：`x86_64`。
- Docker 已安装，服务器端不负责构建镜像。
- `8080` 已被现有服务占用，不能作为宿主机映射端口。
- `18080`、`18081`、`18082` 已被现有服务占用。
- `18090` 当前未监听，作为本项目唯一宿主机入口。
- 已有 PostgreSQL 容器：`postgres-shared`。
- PostgreSQL 所在外部 Docker 网络：`shared-net`。
- PostgreSQL 容器服务名：`postgres-shared`，容器内端口：`5432`。
- 服务器主机上的 PostgreSQL 映射端口 `5433` 不作为应用容器连接地址。

## 5. 总体架构

```text
┌──────────────────────┐
│ React 管理系统        │
│ admin-web             │
└──────────┬───────────┘
           │ 浏览器访问
           ▼
┌──────────────────────────────────────────────┐
│ 192.168.100.213:18090                         │
│ autolive-admin / Nginx                         │
│                                               │
│ /       -> React dist                           │
│ /api/*  -> http://autolive-api:8080/api/*     │
└──────────────────┬───────────────────────────┘
                   │ Docker 内部网络
                   ▼
          ┌─────────────────────┐
          │ autolive-api        │
          │ Go API :8080        │
          └──────────┬──────────┘
                     │ shared-net
                     ▼
          ┌─────────────────────┐
          │ postgres-shared     │
          │ :5432               │
          │ autolive_control... │
          └─────────────────────┘

桌面端控制面基地址：
http://192.168.100.213:18090
```

### 5.1 统一入口的原因

- 管理前端使用同源 `/api`，不需要单独配置 CORS。
- 桌面端只保存一个控制面基地址，登录、激活、心跳和模型号池不会出现多地址漂移。
- Go API 不直接暴露宿主机端口，减少端口冲突和外部暴露面。
- 将来切换到 HTTPS 或域名时，只需要修改入口配置和桌面端构建变量。

## 6. 镜像设计

### 6.1 Go 后端镜像

- 构建阶段使用 Go 构建镜像编译 `cmd/server` 和 `cmd/migrate`；当前本地通过 `docker.1ms.run` 镜像代理获取基础镜像。
- 目标平台固定为 `linux/amd64`。
- 运行阶段使用 Alpine 精简镜像，并安装 `ca-certificates` 与 `wget`，满足 HTTPS 供应商调用和容器健康检查。
- 容器非 root 用户运行。
- 镜像使用 `CMD` 指定默认 API 进程，使 Compose 可以为一次性迁移容器覆盖启动命令。
- 默认监听容器内 `:8080`，通过环境变量配置数据库、存储模式、密钥和管理员初始化信息。
- 运行镜像不包含源代码、数据库凭证文件和本地构建缓存。

### 6.2 React 管理前端镜像

- 本地先使用 Node/pnpm 执行生产构建，再将已验证的 `dist` 目录打入 Nginx 镜像；服务器不执行前端构建。
- 运行阶段使用 Nginx 提供静态文件。
- Nginx 将 `/api/` 反向代理到 Compose 服务名 `autolive-api:8080`。
- 支持 React History API 回退到 `index.html`。
- 不把 API 地址硬编码到前端业务代码；生产环境使用同源 `/api`。

### 6.3 构建原则

- 本地执行 `docker buildx build --platform linux/amd64`。
- 镜像通过 `docker save` 生成归档后上传，服务器执行 `docker load`。
- 镜像使用不可变版本标签，例如提交摘要或时间戳；部署文件不使用悬空的 `latest`。
- 服务器只执行加载、迁移、启动和验证，不执行 `go build`、`pnpm build` 或 Docker build。
- 基础镜像来源与摘要记录在发布记录中，避免仅依赖可变标签判断版本。

## 7. 服务器部署编排

Compose 部署文件放在服务器项目目录，例如：

```text
/opt/services/autolive/
├── docker-compose.yml
├── .env                         # 仅服务器存在，禁止提交
├── images/
│   ├── autolive-api-<version>.tar
│   └── autolive-admin-<version>.tar
└── deploy/
    └── 迁移与健康检查脚本
```

Compose 服务：

1. `autolive-api`
   - 使用 Go 后端镜像。
   - 加入 `shared-net`。
   - 不发布宿主机端口。
   - 健康检查请求 `/api/v1/health`。
2. `autolive-admin`
   - 使用 Nginx 管理前端镜像。
   - 发布 `18090:80`。
   - 加入 `shared-net`，用于反向代理 API。
3. `autolive-migrate`
   - 使用 Go 后端镜像中的迁移程序。
   - 一次性执行，成功后退出。
   - 连接 `postgres-shared:5432`。
   - API 启动前必须确认迁移成功。

部署顺序：

```text
检查端口和 Docker 网络
        ↓
加载两个镜像
        ↓
创建数据库和应用账号
        ↓
执行 migrate
        ↓
启动 autolive-api
        ↓
启动 autolive-admin
        ↓
健康检查与业务链路验证
```

## 8. PostgreSQL 设计

默认命名：

- 数据库：`autolive_control_plane`
- 应用用户：独立生成，不复用 PostgreSQL 管理员账号
- 连接主机：`postgres-shared`
- 连接端口：`5432`

数据库管理员凭证只从本地已有凭证文件或交互式环境读取，用于一次性建库和授权；不会写入 Git、Dockerfile、镜像层或命令输出。

应用连接串只写入服务器部署目录下的权限受控 `.env` 文件，并通过 Compose 注入容器。数据库迁移由现有 `backend/cmd/migrate` 执行，应用启动时继续执行版本一致性检查。

## 9. 桌面端控制面切换

### 9.1 地址配置

桌面端控制面基地址从构建环境变量注入：

```text
VITE_CONTROL_PLANE_BASE_URL=http://192.168.100.213:18090
```

客户端代码保留统一的 URL 拼接和请求封装，业务模块不直接拼接服务器地址。默认地址用于本地联调，正式构建必须显式传入目标环境地址。

### 9.2 需要覆盖的接口

- 登录、刷新令牌、退出登录。
- 激活码兑换和客户端激活状态读取。
- 客户端资料、设备基础信息、心跳。
- 模型号池租约申请、续租、释放。
- 大模型直连调用记录上报。

### 9.3 Tauri 权限

Tauri HTTP capability 允许统一入口的 `/**` 路径，删除仅面向 `127.0.0.1:8080` 和 `localhost:8080` 的旧生产权限。测试同步验证新地址，避免代码地址已切换但运行时权限仍拦截请求。

### 9.4 安全边界

本次使用服务器内网 HTTP，仅用于当前联调和局域网部署。若桌面端需要跨公网使用，下一阶段必须切换 HTTPS，并同步更新 Tauri capability、服务端可信来源和证书策略。

## 10. 配置与敏感信息

以下内容只存在于服务器 `.env` 或部署时的受保护变量中：

- PostgreSQL 管理员连接信息。
- PostgreSQL 应用用户密码。
- `APP_SECRET_ENCRYPTION_KEY`。
- 初始管理系统账号密码。
- 模型号池提供商密钥（如部署环境需要）。

仓库只保存 `.env.example`，使用占位符和变量说明，不保存真实值。

## 11. 回滚设计

- 每次部署保留上一版两个镜像和 Compose 配置。
- 新版本迁移执行前先检查数据库迁移是否可逆；不可逆迁移必须先备份并单独确认。
- API 或前端健康检查失败时，不切换入口容器到新版本，保留上一版服务。
- 运行异常时可将镜像标签和 Compose 环境变量恢复到上一版，再执行 `docker compose up -d`。
- 不删除现有服务器容器和数据卷。

## 12. 验收标准

### 12.1 镜像和部署

- 两个镜像均为 `linux/amd64`，可在服务器正常加载。
- 服务器没有执行本地代码构建。
- `autolive-admin` 通过 `18090` 可访问。
- `/api/v1/health` 返回成功。
- API 容器可连接 `postgres-shared:5432`。
- 数据库迁移完成且应用启动版本检查通过。

### 12.2 管理系统

- 管理员可以登录。
- 用户、设备、激活码、模型号池页面可以加载并完成基本读写。
- 前端请求全部经同源 `/api` 代理，不出现 CORS 错误。

### 12.3 桌面端

- 桌面端启动后不再请求 `127.0.0.1:8080` 或 `localhost:8080`。
- 登录、刷新令牌、激活、心跳至少各完成一次真实接口验证。
- 模型号池租约申请/续租/释放链路可用。
- Windows、Intel Mac、Apple Silicon Mac 的构建配置使用同一控制面地址注入机制。

## 14. 设计结论

本项目采用“本地构建、远程加载；Nginx 单入口；Go API 内网化；复用现有 PostgreSQL Docker 网络；桌面端构建期注入控制面地址”的部署方式。该方式符合当前服务器端口、架构和“不在服务器构建”的约束，同时为后续 HTTPS、域名和多环境配置保留扩展空间。
