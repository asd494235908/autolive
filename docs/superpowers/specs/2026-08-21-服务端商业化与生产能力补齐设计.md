# 服务端商业化与生产能力补齐设计

> 状态：已确认的服务端规划设计，本轮只写文档，不实施代码、数据库迁移或部署；React 管理页和 Rust/Tauri 客户端不在本专项实施范围。
>
> 上位执行文档：[`tasks/prd-server-commercial-production-readiness.md`](../../../tasks/prd-server-commercial-production-readiness.md)

## 1. 设计目标

将当前“用户、设备、激活码和模型号池的开发期控制面”扩展为可商用、可发布、可运维的服务端，同时保持 Go 模块化单体、PostgreSQL 规范化事实源、OpenAPI 唯一契约和服务器不构建源码的现有边界。

本设计补齐七个能力域：

1. 订阅、订单、设备和套餐版本等管理查询/筛选 API。
2. 套餐版本、订单、微信支付和订阅权益的商业事实链。
3. 密码重置令牌、投递 Outbox 与可恢复 Worker。
4. 激活码独立加密表、完整明文重显、设备容量与绑定切换。
5. 对象存储、短时下载授权、签名和 Provenance 真实性校验。
6. 数据保留、备份恢复、指标/追踪、CI 签名与可验证发布。
7. 按 namespace 和版本管理的 JSON Schema Draft 2020-12 公共配置校验。

## 2. 已选方案与取舍

### 2.1 推荐方案：模块化单体 + 专用领域表 + 可替换适配器

- 订阅、订单、支付、激活码、发布制品和公共配置各自拥有专用表、Repository 和 Service 入口。
- 微信支付、对象存储、密码重置投递和 OTLP 导出通过小型适配器接入，不让业务领域依赖具体供应商。
- 异步任务复用 PostgreSQL Outbox/Job 模式，使用 `FOR UPDATE SKIP LOCKED`、有界批次、指数退避、最大尝试次数和死信状态，本阶段不增加外部消息队列。

该方案最符合当前代码和团队规模，也能在后续真实负载证明有必要时再拆分独立进程。

### 2.2 未选方案

- 全部堆入现有 `controlplane.go`：初期改动少，但会继续放大单文件、事务和职责耦合。
- 立即拆微服务和引入 Kafka/RabbitMQ：不符合当前部署和运维基线，还会在商业语义未稳定时增加分布式事务成本。

## 3. 领域设计

### 3.1 管理查询 API

管理列表统一使用 SQL 分页、固定白名单筛选/排序和最大时间窗口，不先加载全量快照再内存筛选。计划资源包括：

- `subscriptions`：按用户、套餐版本、状态、开始/到期时间筛选。
- `orders`：按订单号、用户、支付渠道、状态、金额和创建/支付时间筛选。
- `plan-versions`：按套餐、版本、状态和发布时间筛选。已发布版本不原地修改，变更时新建版本。
- `devices`：在现有列表/详情上增加用户、激活状态、在线派生状态、操作系统、客户端版本、最后心跳时间和排序白名单。

详情端点不回显密钥、Token、微信原始通知正文或全量个人数据。

### 3.2 套餐、订单、微信支付与订阅

- `plans` 是稳定套餐身份；`plan_versions` 是不可变的价格、有效期和权益快照。
- `orders` 保存整型分金额、CNY 币种、状态、用户和套餐版本；订单创建后价格不随后续套餐变更。
- `payment_attempts` 保存商户订单号、微信支付订单号、通知 ID、状态和脱敏结果；通知 ID 和供应商交易号建立唯一约束。
- 首个生产支付入口默认为适合桌面/浏览器的微信 Native 支付二维码；JSAPI、H5、App 支付和退款另立后续范围。
- 使用微信支付 API v3 官方 Go SDK，不自行实现签名协议。回调先使用原始 body 和 `Wechatpay-*` 请求头验签/解密，再在一个短事务中幂等记录支付事实、标记订单并生效订阅，同时写入下游通知 Outbox，提交后立即应答；核心权益不依赖另一个异步 Worker 才生效。
- 不只依赖回调：结果未知、长时间 `paying` 和 Worker 恢复时通过微信订单查询对账。
- 只有验签通过且金额、商户号、APPID、商户订单号与本地事实一致时，才能在同一 PostgreSQL 事务中标记支付成功并生效订阅。

### 3.3 密码重置投递

- 密码重置使用随机一次性 Token，数据库只保存哈希、用户、过期时间、消费时间和发起元数据。
- 公开请求始终返回中性结果，不枚举账号；高风险路由按 IP 和账号摘要限流。
- 请求事务内写入 `password_reset_deliveries`，Worker 在事务外投递，记录 provider message ID、尝试次数、下次重试和死信原因码，不记录 Token 或邮件正文。
- 首期只规划邮箱投递适配器；用户需具有已验证邮箱，不通过邮件直接发送新密码。

### 3.4 激活码明文与设备绑定

采用已确认的“独立加密表”方案：

- `activation_codes` 继续只保存核销哈希和业务元数据；明文可用性由独立密文记录是否存在派生，不把明文或可恢复密文写回该表。
- `activation_code_secrets` 以 `activation_code_id` 为主键，保存 `format_version`、`key_id`、AES-256-GCM 密文和时间。AAD 绑定领域、版本与激活码 ID。
- 新激活码的哈希、元数据和密文在同一事务提交。旧激活码只有哈希，必须标记 `legacy_unavailable`，不能恢复或静默替换。
- `POST /api/v1/admin/activation-codes/{code_id}/reveal` 需要管理员密码二次认证、专用限流、审计和 `no-store`；只允许 HTTPS 生产调用。
- `activation_code_device_bindings` 以 `slot_no` 表达已核销名额，保存活动、已切换、已解绑和历史未知状态。历史多设备仅回填首台设备，其余名额明确显示“历史设备未知”。
- 容量为 1～100，不能低于已核销名额；过期/作废不可修改。切换设备复用原名额，撤销旧设备会话和租约，新设备不继承旧会话。

### 3.5 发布制品与外部下载

本域仅管理桌面安装包、FFmpeg/FFprobe 运行资源、容器镜像元数据和它们的发布清单，不存储用户本地音视频。

- `artifact_releases` 记录版本、渠道、状态、源提交、构建身份和发布时间。
- `artifact_files` 记录平台、架构、对象 key、字节数、SHA-256、签名 bundle 和 Provenance/SBOM 引用。
- CI 上传前完成构建、哈希、签名和 Provenance；服务端验证签名者身份、OIDC issuer、repository/workflow/ref 策略、subject digest 与 SBOM/Provenance 后才允许发布。
- 对象桶默认私有。客户端请求下载时先校验订阅/设备权限，再签发短时、仅 GET、固定对象的预签名 URL；不返回永久公网链接或存储凭证。
- 服务端下载响应提供已验证签名清单、文件哈希、平台/架构和信任策略版本；客户端安装前验证属于后续消费端集成任务，不在本专项修改 Rust/Tauri。

### 3.6 namespace 级公共配置 Schema

- 每个公共配置 namespace 必须注册不可变的 schema 版本，使用 JSON Schema Draft 2020-12。
- 发布配置时先验证 namespace 存在、Schema 本身合法、实例符合 Schema，再执行现有敏感字段拒绝规则。
- `$ref` 只能指向编译期或管理员预注册的受信 Schema，运行时禁止从任意 URL 拉取，避免 SSRF 和不可复现校验。
- Schema 变更先对已发布配置做 dry-run；不兼容变更新建版本，不原地重写历史 Schema。
- 客户端只读已发布 revision，响应携带 namespace、schema version、revision 和 ETag；校验失败不发布部分配置。

### 3.7 生产运维与可验证发布

- 扩展现有保留 Worker，覆盖支付通知/尝试、密码重置 Token/投递、订单对账任务、制品下载记录和过期 Schema draft；每个数据集有独立 TTL、批次、超时、容量告警和审计保留例外。
- PostgreSQL 和对象存储分别备份；备份加密、跨失效域保存、定期恢复到隔离环境。首期规划目标为 RPO 不高于 24 小时、RTO 不高于 4 小时，上线前必须以恢复演练证明。
- 保留现有 Prometheus 作为指标事实源，增加订单、支付、Worker、对象存储、备份和发布低基数指标；使用 OpenTelemetry Go + OTLP 增加分布式追踪，不同时搭建第二套重复业务指标。
- Trace 传播 request ID/trace context，但属性不包含密码、Token、明文激活码、微信原始通知、用户邮箱、预签名 URL 或高基数资源 ID。
- CI 使用托管构建身份产生 SBOM、制品签名和 SLSA Provenance，发布/部署前按允许的 repository、workflow、ref、issuer 和 subject digest 验证；任何一项失败即拒绝。

## 4. 错误、幂等与恢复边界

- 所有商业写操作要求 `Idempotency-Key`，相同 key 但不同指纹返回稳定 `409`。
- 订单、支付、订阅和套餐版本使用显式状态机，禁止用字符串错误推断状态。
- 支付回调、密码投递和对账可重复，消费者默认按“至少一次”设计，只有数据库唯一约束/幂等事实能防重。
- 外部调用不在数据库锁或事务内执行。提交结果未知时保留幂等键并通过查询/对账恢复，不盲目生成新订单或新支付。
- Worker 优雅关闭时停止领取、等待已领取任务或在超时后释放租约，不丢弃无主 Goroutine。

## 5. 发布顺序

1. 先更新 PRD、专项设计、OpenAPI 计划和数据分类。
2. 按领域增加前向迁移，不修改 0001～0022。
3. 先发布兼容读路径和新表，再启用 Worker/支付/下载流量；最后移除过渡路径。
4. 生产发布前完成备份和隔离恢复演练、微信支付沙箱/小额真实回调验收、制品签名验证和回滚演练。
5. Go 服务和待分发制品只在本地开发机或 CI 构建，服务器只接收已签名、已验证制品。

## 6. 非目标

- 本轮不实施任何代码、迁移、配置或部署。
- 不在 Go 服务中存储、处理或下载用户本地视频和音频。
- 不开发实时话术幻化、直播平台接入、RTMP/OBS 或媒体研究分析。
- 不在第一期实施支付退款、优惠券、发票、多币种、短信密码重置或多支付渠道。
- 不因对象存储而让服务端成为大文件中继；数据面通过短时预签名 URL 直连存储。
- 不实现 React 管理页面或 Rust/Tauri 下载、安装和本地验签逻辑；消费端以后依据 OpenAPI/签名清单另立集成任务。
