## 1. 设计目标

将当前“用户、设备、激活码和模型号池的开发期控制面”扩展为可商用、可发布、可运维的 Go 服务端和权限化 React 管理端，同时保持 PostgreSQL 规范化事实源、OpenAPI 唯一契约和服务器不构建源码的现有边界。

本设计补齐十个能力域：

1. 自定义角色、固定权限点、服务端强制授权和权限化 React 管理端。
2. 订阅、订单、设备和套餐版本等管理查询/筛选 API 与页面。
3. 套餐版本、订单、微信支付和订阅权益的商业事实链。
4. 密码重置令牌、投递 Outbox 与可恢复 Worker。
5. 激活码独立加密表、完整明文重显、设备容量与绑定切换。
6. 对象存储、短时下载授权、签名和 Provenance 真实性校验。
7. 数据保留、备份恢复、指标/追踪、CI 签名与可验证发布。
8. 按 namespace 和版本管理的 JSON Schema Draft 2020-12 公共配置校验。
9. 按 product 的订阅/设备席位、产品范围权限和商业准入。
10. 双重脱敏错误摘要、最小反馈状态流和对应 React 管理页。

## 2. 已选方案与取舍

### 2.1 推荐方案：模块化单体 + 专用领域表 + 可替换适配器

- 订阅、订单、支付、激活码、发布制品和公共配置各自拥有专用表、Repository 和 Service 入口。
- 权限目录固定并版本化，管理员创建角色并从目录选择权限；用户通过一个或多个角色获得权限并集，不使用用户级 allow/deny 覆盖。
- 微信支付、对象存储、密码重置投递和 OTLP 导出通过小型适配器接入，不让业务领域依赖具体供应商。
- 异步任务复用 PostgreSQL Outbox/Job 模式，使用 `FOR UPDATE SKIP LOCKED`、有界批次、指数退避、最大尝试次数和死信状态，本阶段不增加外部消息队列。

该方案最符合当前代码和团队规模，也能在后续真实负载证明有必要时再拆分独立进程。

### 2.2 未选方案

- 全部堆入现有 `controlplane.go`：初期改动少，但会继续放大单文件、事务和职责耦合。
- 立即拆微服务和引入 Kafka/RabbitMQ：不符合当前部署和运维基线，还会在商业语义未稳定时增加分布式事务成本。

## 3. 领域设计

### 3.1 管理员 RBAC 与 React 管理端

当前系统只有 `admin/user` 两级角色，所有管理路由共用 `requireAdmin`；React 只判断是否有 Session，登录后显示全部导航。后续改为以下统一授权模型：

- `admin_permissions` 保存由代码/OpenAPI 和迁移共同版本化的固定权限目录；管理员不能创建任意权限代码。
- `admin_roles` 保存内置和自定义角色，`admin_role_permissions` 保存角色权限，`user_admin_roles` 支持用户按 product 绑定多个角色；有效权限取角色并集，不支持用户级覆盖。
- 内置 `super_admin` 不可删除、停用或改名，并固定拥有全部权限；本地管理员永久绑定该角色。现有 `role=admin` 用户兼容回填为 `super_admin`，保证升级不丢权限。
- 管理 API 使用 `requirePermission(code)`；每个请求按用户 ID 读取当前有效权限，不把完整权限长期写入 Token。角色停用或撤销后对现有 Session 立即生效。
- 角色管理者只能授予自己拥有的权限，分配用户角色时目标角色权限也必须是操作者当前权限的子集；不能分配/撤销 `super_admin`，最后一个有效 `super_admin` 和本地管理员绑定受服务端保护。
- 固定权限按用户/角色、设备、激活码、套餐、订单、订阅、支付、密码重置、制品、公共配置、模型号池、审计和运维分组。高风险权限拆为 `activation_codes.reveal`、`activation_codes.switch_device`、`model_pool.rotate_secret`、`artifacts.publish`、`public_config.publish` 等独立点。
- 新增当前管理员摘要、权限目录、角色 CRUD 和用户角色分配 API。`/api/v1/admin/me` 只需有效认证会话且只返回本人角色/权限，以便权限被撤销后返回空权限而不暴露他人信息。所有权限变更要求幂等键和语义化审计。
- React 新增“角色与权限”页面和用户角色分配；启动后读取 `/api/v1/admin/me`，按有效权限过滤导航、守卫路由和操作按钮，直接访问无权限页面显示 403。前端展示不是授权依据，API 始终再次校验。

### 3.2 管理查询 API 与页面

管理列表统一使用 SQL 分页、固定白名单筛选/排序和最大时间窗口，不先加载全量快照再内存筛选。计划资源包括：

- `subscriptions`：按用户、套餐版本、状态、开始/到期时间筛选。
- `orders`：按订单号、用户、支付渠道、状态、金额和创建/支付时间筛选。
- `plan-versions`：按套餐、版本、状态和发布时间筛选。已发布版本不原地修改，变更时新建版本。
- `devices`：在现有列表/详情上增加用户、激活状态、在线派生状态、操作系统、客户端版本、最后心跳时间和排序白名单。
- `subscription-device-slots`：按订阅、产品、设备、状态和绑定/释放时间筛选。

详情端点不回显密钥、Token、微信原始通知正文或全量个人数据。

React 管理端增加套餐版本、订单、订阅和增强设备页面，使用 Ant Design 表格、筛选表单、详情抽屉和 URL 查询状态；页面和操作按对应 `*.read`/`*.manage`/`*.reconcile`/`*.adjust` 权限控制，并覆盖 loading、empty、error 和 403。

### 3.3 套餐、订单、微信支付、订阅与设备席位

- 所有商业事实绑定 P0 `product`；`plans` 是稳定套餐身份，`plan_versions` 是不可变的价格、有效期和设备席位快照。有效订阅开放该产品全部功能，不按 Token 或功能等级划分。
- `orders` 保存整型分金额、CNY 币种、状态、用户和套餐版本；订单创建后价格不随后续套餐变更。
- `payment_attempts` 保存商户订单号、微信支付订单号、通知 ID、状态和脱敏结果；通知 ID 和供应商交易号建立唯一约束。
- 首个生产支付入口默认为适合桌面/浏览器的微信 Native 支付二维码；JSAPI、H5、App 支付和退款另立后续范围。
- 使用微信支付 API v3 官方 Go SDK，不自行实现签名协议。回调先使用原始 body 和 `Wechatpay-*` 请求头验签/解密，再在一个短事务中幂等记录支付事实、标记订单并生效订阅，同时写入下游通知 Outbox，提交后立即应答；核心权益不依赖另一个异步 Worker 才生效。
- 不只依赖回调：结果未知、长时间 `paying` 和 Worker 恢复时通过微信订单查询对账。
- 只有验签通过且金额、商户号、APPID、商户订单号与本地事实一致时，才能在同一 PostgreSQL 事务中标记支付成功并生效订阅。
- 设备席位原子占用且不能超卖；释放、禁用或转移要撤销旧会话、租约和离线授权，转移不继承会话。访问顺序为用户、产品成员、设备、订阅、席位。
- React 提供脱敏支付状态、订单详情、对账结果和订阅调整入口；二维码、商户密钥、原始通知和预签名地址不得进入 Session 或前端持久化。

### 3.4 密码重置投递

- 密码重置使用随机一次性 Token，数据库只保存哈希、用户、过期时间、消费时间和发起元数据。
- 公开请求始终返回中性结果，不枚举账号；高风险路由按 IP 和账号摘要限流。
- 请求事务内写入 `password_reset_deliveries`，Worker 在事务外投递，记录 provider message ID、尝试次数、下次重试和死信原因码，不记录 Token 或邮件正文。
- 首期只规划邮箱投递适配器；用户需具有已验证邮箱，不通过邮件直接发送新密码。
- React 仅向有 `password_resets.read/retry` 权限的管理员展示脱敏投递状态、失败原因码和重试操作，不返回 Token、重置 URL 或邮件正文。

### 3.5 激活码明文与设备绑定

采用已确认的“独立加密表”方案：

- `activation_codes` 继续只保存核销哈希和业务元数据；明文可用性由独立密文记录是否存在派生，不把明文或可恢复密文写回该表。
- `activation_code_secrets` 以 `activation_code_id` 为主键，保存 `format_version`、`key_id`、AES-256-GCM 密文和时间。AAD 绑定领域、版本与激活码 ID。
- 新激活码的哈希、元数据和密文在同一事务提交。旧激活码只有哈希，必须标记 `legacy_unavailable`，不能恢复或静默替换。
- `POST /api/v1/admin/activation-codes/{code_id}/reveal` 需要管理员密码二次认证、专用限流、审计和 `no-store`；只允许 HTTPS 生产调用。
- `activation_code_device_bindings` 以 `slot_no` 表达已核销名额，保存活动、已切换、已解绑和历史未知状态。历史多设备仅回填首台设备，其余名额明确显示“历史设备未知”。
- 容量为 1～100，不能低于已核销名额；过期/作废不可修改。切换设备复用原名额，撤销旧设备会话和租约，新设备不继承旧会话。
- React 激活码页面增加绑定详情、容量修改、设备切换和明文重显弹窗；分别要求 `activation_codes.read/manage/switch_device/reveal`，重显前收集管理员密码二次认证且不持久化明文。

### 3.6 发布制品与外部下载

本域仅管理桌面安装包、FFmpeg/FFprobe 运行资源、容器镜像元数据和它们的发布清单，不存储用户本地音视频。

- `artifact_releases` 记录 product、版本、渠道、状态、最低版本、灰度/强制升级/撤回策略、源提交、构建身份和发布时间。
- `artifact_files` 记录平台、架构、对象 key、字节数、SHA-256、签名 bundle 和 Provenance/SBOM 引用。
- CI 上传前完成构建、哈希、签名和 Provenance；服务端验证签名者身份、OIDC issuer、repository/workflow/ref 策略、subject digest 与 SBOM/Provenance 后才允许发布。
- 对象桶默认私有。客户端请求下载时先校验订阅/设备权限，再签发短时、仅 GET、固定对象的预签名 URL；不返回永久公网链接或存储凭证。
- 服务端下载响应提供已验证签名清单、文件哈希、平台/架构和信任策略版本；客户端安装前验证属于后续消费端集成任务，不在本专项修改 Rust/Tauri。
- React 提供制品草稿、验签结果、发布、撤销和下载授权记录页面；发布/撤销使用独立高风险权限与确认，不展示对象存储凭证或完整预签名 URL。

### 3.7 product/environment/namespace 公共配置 Schema

- 每个 product/environment/namespace 必须注册不可变的 schema 版本，使用 JSON Schema Draft 2020-12；配置不能授予或延长订阅权益。
- 发布配置时先验证 namespace 存在、Schema 本身合法、实例符合 Schema，再执行现有敏感字段拒绝规则。
- `$ref` 只能指向编译期或管理员预注册的受信 Schema，运行时禁止从任意 URL 拉取，避免 SSRF 和不可复现校验。
- Schema 变更先对已发布配置做 dry-run；不兼容变更新建版本，不原地重写历史 Schema。
- 客户端只读已发布 revision，响应携带 namespace、schema version、revision 和 ETag；校验失败不发布部分配置。
- React 提供 namespace、Schema 版本、配置 revision、dry-run 错误和发布/回滚操作；使用 Ant Design JSON 编辑输入与错误列表，不能覆盖组件内部样式或在浏览器执行配置内容。

### 3.8 客户端错误报告与反馈

- 错误摘要要求用户同意、客户端预脱敏和服务端再次脱敏，并限制字段、长度、批量、采样、指纹去重、幂等、速率、TTL 与删除；本专项只实现服务端契约/二次脱敏/管理面，客户端接线另立消费端任务。
- 首版拒绝 crash dump、截图、附件、本地路径、Token/Cookie、Prompt/业务正文、BYOK 和短期凭证。
- 反馈只保存 product/user、受限文本和 `open → in_progress → resolved/closed` 最小状态；不做附件、外部工单同步或通知。
- React 只展示产品范围的低敏摘要、聚合趋势和反馈状态，不提供原始 dump/完整日志下载。

### 3.9 生产运维与可验证发布

- 扩展现有保留 Worker，覆盖支付通知/尝试、密码重置 Token/投递、订单对账任务、制品下载记录和过期 Schema draft；每个数据集有独立 TTL、批次、超时、容量告警和审计保留例外。
- PostgreSQL 和对象存储分别备份；备份加密、跨失效域保存、定期恢复到隔离环境并核对 product 关系、席位占用和跨产品引用。首期规划目标为 RPO 不高于 24 小时、RTO 不高于 4 小时，上线前必须以恢复演练证明。
- 保留现有 Prometheus 作为指标事实源，增加订单、支付、Worker、对象存储、备份和发布低基数指标；使用 OpenTelemetry Go + OTLP 增加分布式追踪，不同时搭建第二套重复业务指标。
- Trace 传播 request ID/trace context，但属性不包含密码、Token、明文激活码、微信原始通知、用户邮箱、预签名 URL 或高基数资源 ID。
- CI 使用托管构建身份产生 SBOM、制品签名和 SLSA Provenance，发布/部署前按允许的 repository、workflow、ref、issuer 和 subject digest 验证；任何一项失败即拒绝。
- React 运维页只展示低敏聚合状态、Worker 积压、备份新鲜度、恢复演练结果和发布验签状态；详细指标/Trace 仍由受保护的 Prometheus/OTLP 后端承载。

## 4. 错误、幂等与恢复边界

- 所有商业写操作要求 `Idempotency-Key`，相同 key 但不同指纹返回稳定 `409`。
- 订单、支付、订阅和套餐版本使用显式状态机，禁止用字符串错误推断状态。
- 支付回调、密码投递和对账可重复，消费者默认按“至少一次”设计，只有数据库唯一约束/幂等事实能防重。
- 外部调用不在数据库锁或事务内执行。提交结果未知时保留幂等键并通过查询/对账恢复，不盲目生成新订单或新支付。
- Worker 优雅关闭时停止领取、等待已领取任务或在超时后释放租约，不丢弃无主 Goroutine。
- 权限缺失统一返回 `403` 和稳定错误码；React 收到 403 时刷新当前权限摘要并展示无权限状态，不自动重试写操作。

## 5. 管理端交互与验证

- React 管理端统一使用 Ant Design，不自制表格、分页、表单、弹窗、抽屉、通知或权限树基础组件，不覆盖 `.ant-*` 内部样式。
- 菜单、路由和按钮基于同一权限目录元数据；权限标签、说明和风险分组从受版本控制的前端映射生成，不在页面内散落字符串判断。
- 服务端权限矩阵测试覆盖每个管理路由的未登录、无权限和有权限结果；React 测试覆盖导航过滤、直接 URL、按钮状态、权限变化和 403。
- 涉及表格/筛选/抽屉/权限树的页面执行 React typecheck/test/build、浏览器流程和键盘/焦点/窄屏检查；支付、加密、Worker 和数据库状态仍以 Go/PostgreSQL 集成证据为主。

## 6. 发布顺序

1. 先更新 PRD、专项设计、权限矩阵、OpenAPI 计划和数据分类。
2. 按领域增加前向迁移，不修改 0001～0022；先兼容回填 `super_admin`，再切换管理路由权限判断。
3. RBAC API 和 `/admin/me` 先于权限化 React 导航发布；服务端未切换完成前不启用新角色分配入口。
4. 先发布兼容读路径和新表，再启用商业页面、Worker、支付/下载流量；最后移除过渡路径。
5. 生产发布前完成权限矩阵负测试、备份和隔离恢复演练、微信支付小额真实回调验收、制品签名验证和回滚演练。
6. Go、React 和待分发制品只在本地开发机或 CI 构建，服务器只接收已签名、已验证制品。

## 7. 非目标

- 本轮不实施任何代码、迁移、配置或部署。
- 不在 Go 服务中存储、处理或下载用户本地视频和音频。
- 不开发实时话术幻化、直播平台接入、RTMP/OBS 或媒体研究分析。
- 不在第一期实施支付退款、优惠券、发票、多币种、短信密码重置或多支付渠道。
- 不因对象存储而让服务端成为大文件中继；数据面通过短时预签名 URL 直连存储。
- 不实现 Rust/Tauri 下载、安装和本地验签逻辑；桌面消费端以后依据 OpenAPI/签名清单另立集成任务。
- 不支持管理员创建任意权限点、用户级权限覆盖、资源行级 ABAC 或组织/租户层级；后续有真实需求再扩展。
