> 日期：2026-08-31  
> 状态：M1 契约、脱敏兼容探针、Rust/Tauri 最小桌面入口和 React 扫码状态面板已实施；正式发布代码仍未完成。真实兼容探针是首个技术门禁，书面授权证据是正式集成与分发门禁。Python 运行时统一使用 Conda 的 `gpautolive-douyin` 环境（可由 `AUTOLIVE_CONDA_ENV` 覆盖）。2026-08-31 首次运行已验证强制 TLS 下二维码生成/轮询，但因未扫码超时，读取/发送/自回显仍未验证。  
> 上游基线：`cv-cat/Douyin_Spider@9afaf79580b1ee84e8954ff906ff26869d5b7f1f`  
> 授权前提：用户已说明与上游作者存在私下授权；正式分发前仍须完成第 14 节的书面授权和第三方制品门禁。
> 首个实施里程碑 M1：扫码登录 → 读取弹幕 → 本地回复池随机选句 → 串行发送 → 验证回显。M1 不调用大模型。

## 1. 目标

在 GpAutoLive 的 Rust/Tauri 桌面客户端中接入一个本地、受管、单会话的抖音直播自动回应能力：

1. 用户扫码登录抖音。
2. 用户输入一个抖音直播间号或标准直播间 URL。
3. 桌面端实时显示该直播间的公屏弹幕。
4. 每收到一条新的、非本账号发送的公屏弹幕，创建且只创建一个自动回应任务。
5. Rust 从用户本地回复池随机选定一条回应，并按保守速率向同一直播间发送一条普通公屏消息。

上游发送接口只有 `room_id + content + type=0`，不存在 `reply_to_message_id`。因此“一条弹幕对应一条回复”的准确含义是：每个唯一入站 `msgId` 对应一个自动回应任务，并最多发起一次普通公屏发送；不得描述为平台原生线程回复。`@昵称` 只是文本关联，不代表平台建立了回复关系。

“每条必回”受队列容量和平台发送速度约束。设弹幕持续到达速率为 `λ_in`，账号可安全发送速率为 `μ_out`：当 `λ_in > μ_out` 持续存在时，队列会增长。按用户最新确认，自动回应使用**用户可配置但有产品硬上限的有界队列**；队列满时继续读取和展示弹幕，丢弃最旧的尚未进入平台发送阶段的任务，为最新弹幕腾出位置，并累计显示丢弃数量。只有未被丢弃的任务承诺最多尝试发送一次。

## 2. 首版范围

### 2.1 包含

- 一个抖音登录会话。
- 同一时刻一个活动直播间。
- 只读取 `WebcastChatMessage`。
- 有界、仅内存保存的实时弹幕列表。
- 每个唯一外部弹幕创建一个自动回应任务；本账号回显不得再次入队，防止自激循环。
- 用户可配置容量的有界任务队列、并行回复生成、单通道串行发送和满队列丢弃。
- 用户配置 `1～100` 条本地回复候选；每个新任务入队时随机选定一条并固定，不在发送前重复抽样。
- 扫码登录、凭据过期、直播结束、断网重连、发送冷却和退出回收状态。
- Windows 10/11 x64 本地打包和真实直播间门禁。

### 2.2 不包含

- 多账号、多直播间并发、弹幕历史、搜索或导出。
- 礼物、点赞、进场、关注、房间统计、私信、作品评论或发布。
- 代理池、换 IP、风控绕过、验证码绕过或平台检测规避。
- Go API、数据库、管理端弹幕页面或云端转发。
- 读取 Chrome Cookie、普通文件保存 Cookie、面向最终用户的 Cookie 粘贴框。
- `douyin_desktop` 独立产品线；本能力直接属于当前 `autolive` 桌面客户端。
- 对平台风控或发送限额的绕过；不通过增加账号并发来追求“每条必回”。
- 自动回复本账号自己发出的消息、重连重复帧或无法确定唯一 `msgId` 的消息。
- M1 不调用 OpenAI-compatible 模型、不申请模型租约，也不把随机回复包装成 AI 回复；模型生成属于链路通过后的独立后续阶段。

## 3. 上游审查结论

可复用的协议知识和最小链路为：

- `DouyinAuth.from_qrcode_login(..., bootstrap_creator=False)`：扫码建立登录会话。
- `DouyinAPI.get_live_info()`：由公开 `web_rid` 解析本场 canonical `room_id`。
- `DouyinAPI.get_webcast_detail()`：取得初始 cursor/internalExt。
- WebSocket `PushFrame -> gzip -> LiveResponse`，按 `needAck` 回 ACK。
- 只把 `WebcastChatMessage` 映射为最小弹幕 DTO。
- `DouyinAPI.sendMsgInRoom()`：向当前 canonical `room_id` 发送普通公屏文本。

不能直接分发或启动上游 `dy_live/server.py`，原因包括：

- 心跳线程没有取消与 Join；断线后立即递归重连且无退避上限。
- stdout 会打印 `sec_uid`、昵称和弹幕正文，无法作为稳定 IPC。
- 多处 HTTPS 请求关闭证书校验。
- 登录路径可能把 Cookie、ticket 和私钥写入 `.env`，并存在 Cookie 日志。
- 发送接口没有本地限频、结果分类或平台幂等保证。
- Python/npm 依赖未完整锁定，仓库没有公开 LICENSE。

因此只抽取经授权的最小代码闭包，并由 GpAutoLive 自己提供生命周期、输入校验、脱敏、背压、测试和发布证据。

抖音开放平台公开的评论管理文档目前描述的是授权用户自己发布的**视频评论**读取/回复，并要求 `item.comment` 或 `video.comment` scope；本次直播 `WebcastChatMessage` 读取和 `/webcast/room/chat/` 发送不属于该公开视频评论接口。由此推断，本方案仍是基于 Web 直播协议的非官方稳定性链路，不能套用开放平台视频评论配额，也不能把“代码可调用”视为平台允许任意频率自动发送。阶段 1 必须向实际合作/平台渠道确认自动回应边界，并以真实风控结果收紧发送速率。

## 4. 总体架构

```text
GpAutoLive 主窗口 React
  │ 仅调用允许列表内的 Tauri 命令；不持有抖音凭据
  ▼
Rust DouyinLiveManager（单所有者）
  ├─ 登录/直播/发送状态机
  ├─ M1 仅内存抖音会话凭据
  ├─ 500 条展示缓冲、可配置自动回应队列、代际和限频
  ├─ AutoReplyCoordinator：去重、自回显过滤、随机选句、过期丢弃和发送调度
  ├─ sidecar 进程、管道、线程、超时和 Job Object
  └─ 主窗口权限与 shutdown_all
  │ 继承匿名 stdin/stdout；严格有界 NDJSON v1
  ▼
裁剪后的 Python sidecar
  ├─ 扫码认证及必要的受管 Node 签名子进程
  ├─ 房间解析、WSS、protobuf、ACK、心跳和读取重连
  └─ 单次发送；不自动重试写操作
  │ HTTPS/WSS + 证书验证 + 固定域名允许列表
  ▼
抖音直播 Web / Webcast 接口
```

M1 不新增 Go API、数据库或管理端页面。Go 继续处理 GpAutoLive 登录、设备和激活；Cookie、二维码 Token、弹幕、昵称、房间地址和随机回复正文均不进入 Go。现有模型号池继续保持原边界，不能成为 M1 的前置依赖。

选择 Python sidecar 而不是把协议全部重写为 Rust，是为了复用已经授权且已验证的登录、签名、protobuf 和直播链路；选择匿名管道而不是 localhost 服务，是为了避免端口、额外认证和防火墙面。

## 5. 用户流程与界面

### 5.1 入口

不新增路由。在桌面主页右栏增加紧凑的“抖音直播互动”卡片，显示登录、连接、直播间和丢弃计数摘要；“打开”按钮复用现有 `FeatureDrawer`。

抽屉使用 Ant Design 现有组件，包含：

1. 扫码登录/退出登录区；二维码过期可刷新，登录默认只保存在当前进程。
2. 直播间号或 `https://live.douyin.com/<数字>` 输入和连接/断开按钮。
3. 连接状态、重连次数、消息缺口和限频冷却提示。
4. 自动回应总开关、本地回复池和发送速率只读摘要。回复池 `1～100` 条，每条 trim 后 `1～80` 个 Unicode 字符且 UTF-8 不超过 `320` 字节，去重后至少保留一条。
5. 自动回应队列容量设置，默认 500，可在 10～5000 之间调整；运行中只读，暂停后才允许修改。
6. 有界弹幕与任务列表；每条显示 `排队/待发送/发送中/已接受/未发送/被拒绝/结果未知/队列满已丢弃/等待过期已丢弃`。
7. 当前入站速率、发送速率、队列深度、容量、最老任务等待时间、冷却和累计丢弃数。
8. 可选的人工暂停、清空尚未发送的队列、查看失败原因；不提供跳过平台限频的开关。

自动回应默认关闭，用户明确开启后才开始接纳任务。抽屉关闭不自动断开直播或暂停已开启的自动回应，但卡片必须持续显示醒目的“自动回应中”。用户点击“断开”或应用退出时停止。切换直播间必须先停止接纳、处理或明确取消旧队列，再完整停止旧会话，清空旧消息与任务，最后连接新房间。

### 5.2 可访问性与反馈

- 表单使用可见标签，不仅依赖 placeholder。
- 消息和任务使用稳定 `seq/msg_id` 键，内容只按 React 文本节点渲染。
- 首版不加载外部头像，不自动把正文 URL 转为链接。
- 自动回应开关在离线、未认证、回复池为空、冷却或风险控制时禁用。
- loading、empty、error、offline、recovery 均有独立状态；错误通过 `aria-live` 提示。
- 轮询、定时器和在途请求在组件卸载时对称清理。

## 6. 状态模型

避免一个巨大枚举，拆成四个正交状态机：

- 认证：`logged_out | qr_pending | scanned | authenticated | expired | failed`
- 直播：`idle | resolving | connecting | connected | reconnecting | offline | room_ended | stopping | failed`
- 自动回应：`disabled | running | paused | risk_controlled`
- 单任务：`queued | ready | sending | accepted | not_sent | rejected | outcome_unknown | dropped_queue_full | dropped_expired | cancelled`

每次开始、停止或切换直播间都增加 `session_generation`。任务固定绑定创建时的 generation、`msgId` 和 canonical `room_id`；Rust 不接受 Renderer 自行传入的 `room_id`。旧 generation 的 sidecar 事件、定时器、任务结果和发送许可全部丢弃。

## 7. 输入、数据与背压契约

### 7.1 直播间

- 原始输入最多 256 字符。
- 只接受 `[1-9][0-9]{0,19}` 或 `https://live.douyin.com/<同一规则>`。
- ID 全程使用字符串，禁止转为 JavaScript `number`。
- URL 只允许 HTTPS、精确主机、默认端口、无 userinfo；首版拒绝短链和任意跳转。
- 查询串和 fragment 丢弃，不进入网络请求或日志。
- Rust 是最终校验者；sidecar 再校验一次。

### 7.2 弹幕 DTO

只向 React 返回：

```text
session_generation, seq, msg_id, received_at,
nickname, content, truncated
```

不返回完整 protobuf `User`、`sec_uid`、头像、等级、电话、城市或平台原始帧。昵称最多 64 个 Unicode 字符，正文最多显示 500 个 Unicode 字符，超长时截断并标记。

### 7.3 容量

- 压缩帧最大 1 MiB，解压后最大 4 MiB。
- 单帧最多处理 500 个消息项。
- sidecar 到 Rust 接收通道容量 1000，Rust UI 环形缓冲固定 500 条。
- 自动回应队列由用户配置：默认 500，最小 10，最大 5000。Rust 对前端和本地配置再次校验，不能使用 `0`、负数、超上限或非整数绕过硬限制。
- `queue_capacity` 和回复池使用桌面端既有 WebView LocalStore 模式保存非敏感草稿；每次恢复后仍须通过 Rust 权威校验，损坏值回退默认容量且不得自动开启自动回应。
- Rust 轮询每批最多返回 100 条；列表满时丢最旧项并累计 `dropped_count`。
- 用上游 `msgId` 做 4096 项、10 分钟 TTL 的有界去重。
- ACK 和心跳不能被慢 UI 阻塞；断线或溢出必须显示消息缺口，不声称完整回放。
- 只有具备唯一 `msgId`、非本账号发送且属于当前 generation 的弹幕才允许创建任务。
- 队列容量统计 `queued + ready`，不包含已经进入 `sending` 的唯一任务和终态任务。
- 新任务到达且队列已满时，原子选择最旧的、尚未进入 `sending` 的任务，将其标记为 `dropped_queue_full`，然后把新任务加入队尾。
- 正在 `sending` 的任务绝不因队列满而取消，避免产生无法判断是否已发送的结果。
- 每次丢弃递增 `dropped_queue_full_count`，UI 显示本场累计值和最近一次丢弃时间；不写入普通日志的弹幕正文。
- 队列容量只能在自动回应 `disabled/paused` 时修改。调小后若现有任务超出新容量，按同一“丢最旧未发送任务”规则立即收缩并显示本次丢弃数。
- 任务从接收时间起最大等待 `60` 秒；发送 Worker 取任务前再次检查，超过时标记 `dropped_expired` 并继续下一项。M1 不把该时限开放为用户配置，避免队列容量与过期时限形成第二套难以解释的组合配置。
- 回复池只能在 `disabled/paused` 时修改。任务入队时使用显式依赖 `rand 0.10.2` 在全部启用候选中均匀抽取；候选超过一条时尽量不连续选择同一索引。已经入队的任务保留当时选中的回复，后续修改回复池不改写旧任务。
- 最终发送正文为 `@{安全昵称} {候选回复}`；昵称 trim 后移除换行、NUL 和控制字符。组合超过 `100` 个 Unicode 字符或 `400` UTF-8 字节时先省略 `@昵称`，候选自身仍不合格则任务进入 `not_sent`。
- 串行所有权优先级固定为：`停止/切房/退出 > 暂停/清空/缩容 > 队列满丢弃/过期丢弃 > 新弹幕入队 > 发送完成`。所有动作在同一 Manager 锁/actor 内提交，避免多个线程各自删除。
- 有序发送游标遇到 `dropped_queue_full/dropped_expired/cancelled` 必须显式越过；终态任务仅在 UI 环形历史中保留最近 500 条或 10 分钟，先到者淘汰。
- 队列不写本地数据库；退出、切房或直播结束时未发送任务统一标记取消。若后续业务要求崩溃恢复和跨场次补发，另立持久化与隐私方案，不在首版增加 SQLite。

### 7.4 逐条自动回应流水线

```text
唯一外部弹幕
  -> 去重与自回显过滤
  -> 从本地回复池随机选定一句
  -> 组合可选的 @昵称并再次校验
  -> 有界任务入队
  -> 等待期间执行 60 秒过期检查
  -> 单发送 Worker 按入站顺序和限频串行发送
  -> accepted / not_sent / rejected / outcome_unknown
```

- 同一 `msgId` 只允许创建一个任务，重连重放不能产生第二次回应。
- 本账号发送的回显必须通过登录用户标识过滤，不能触发新的任务，防止无限自回复。
- 为保持“一条对应一条”的可审计关系，发送顺序按入站 `seq`；已丢弃或取消的序号不会阻塞后续任务。
- 回复候选和最终正文都按不可信输入校验；不使用 `dangerouslySetInnerHTML`，不把候选当命令、URL 或 sidecar 操作。
- 每条任务最多一次平台发送尝试。`unknown` 不自动重发，否则无法保证“一条只回一次”。

## 8. IPC 与桌面命令

sidecar stdout 只允许 NDJSON v1；stderr 只允许有界、脱敏诊断。Rust 对每行设置 64 KiB 上限，拒绝坏 JSON、未知版本、未知操作、未知字段和重复请求 ID。所有 ID 均为最多 64 个 ASCII 字符，数字型平台 ID 仍用字符串承载。

统一包络冻结为：

```json
{"v":1,"id":"req-1","op":"live.open","payload":{}}
{"v":1,"type":"response","request_id":"req-1","ok":true,"result":{}}
{"v":1,"type":"response","request_id":"req-1","ok":false,"error":{"code":"stable_code","message":"脱敏中文提示","retryable":false,"outcome":"not_sent"}}
{"v":1,"type":"event","event":"live.chat","session_id":"ls-1","generation":1,"payload":{}}
```

协议字段和事件：

| 操作/事件 | 必填 payload/result | 约束 |
|---|---|---|
| `auth.qr.start` | 请求 `timeout_ms`；事件 `auth.qr` 返回 `png_base64/expires_at_unix_ms` | `timeout_ms=300000`；PNG 解码后≤256 KiB；不返回原始二维码 URL |
| `auth.state` | `state=waiting/scanned/confirmed/expired/cancelled/failed` | `confirmed` 后 sidecar 内存持有会话和 self user id，均不回 React |
| `auth.restore` | M1 禁用 | M1 重启后必须重新扫码 |
| `auth.logout` | 无 | 清空 sidecar 内存凭据和登录身份 |
| `live.open` | 请求 `web_rid/generation`；结果 `session_id/title/live_status` | `web_rid` 已由 Rust 校验；canonical room id 只保留在 Rust/sidecar |
| `live.chat` | `msg_id/received_at_unix_ms/author_id/nickname/content` | `author_id` 只供 Rust 自回显过滤，不进入 React DTO |
| `live.gap` | `reason/dropped_count` | 原因仅允许 `sidecar_backpressure/reconnect/no_replay` |
| `live.state` | `state=connecting/connected/reconnecting/room_ended/auth_expired/risk_controlled/closed/failed` | 必须带当前 session/generation |
| `chat.send` | 请求 `session_id/generation/client_action_id/content` | 正文≤100 Unicode 且≤400 UTF-8 字节 |
| `chat.send` 结果 | `state=accepted/not_sent/rejected/unknown`、可选 `platform_status_code` | `client_action_id` 原样回传；`unknown` 禁止重试 |
| `live.close` | `session_id/generation` | 幂等；关闭后不得再发该 generation 事件 |
| `shutdown` | 无 | 成功响应后进程退出；超时由 Rust Job 回收 |

稳定错误码最小集合冻结为：`protocol_invalid`、`auth_timeout`、`auth_expired`、`room_input_invalid`、`room_not_live`、`room_resolve_failed`、`ws_handshake_failed`、`ws_protocol_invalid`、`risk_controlled`、`rate_limited`、`send_rejected`、`transport_before_dispatch`、`transport_after_dispatch`、`sidecar_exited`。`transport_before_dispatch` 映射 `not_sent`，`transport_after_dispatch` 映射 `unknown`。

最小 sidecar 操作为：

```text
auth.qr.start, auth.cancel, auth.logout,
live.open, live.close, chat.send, shutdown
```

发送结果必须分为：

- `accepted`：平台业务状态码表示接口接受，不承诺公屏一定展示。
- `not_sent`：可证明未发送，例如本地校验或本地限频拒绝。
- `rejected`：平台明确拒绝。
- `unknown`：请求派发后超时、断连或响应不可判定；禁止自动重试。

Tauri 主窗口命令建议为：

```text
begin_douyin_qr_login
get_douyin_live_status
logout_douyin_account
start_douyin_live_room
poll_douyin_live_comments
set_douyin_auto_reply_config
start_douyin_auto_reply
pause_douyin_auto_reply
stop_douyin_live_room
```

自动发送不是 Renderer 对每条消息逐次调用 `chat.send`：Rust 的 AutoReplyCoordinator 是唯一调度者，sidecar 只接受当前 generation 内由 Rust 产生的内部发送请求。上述命令只进入 `main` capability，`final-effect` 窗口无权认证、监听、配置或发送。自动生成的权限文件和 schema 由 Tauri 构建流程生成，不手改生成产物。

Rust 状态轮询统一返回 `snapshot_revision`；弹幕/任务轮询使用单调 `after_seq` 和 `next_seq`。revision/seq 倒退、session/generation 不匹配或迟到 sidecar 响应一律丢弃。终态映射固定为：sidecar `accepted/not_sent/rejected/unknown` 分别对应任务 `accepted/not_sent/rejected/outcome_unknown`。

## 9. 登录与敏感信息

- 正式版只提供扫码登录，不读取浏览器 Cookie，不提供 Cookie 粘贴。
- 扫码显式传 `bootstrap_creator=False`，不启动创作者能力。
- 二维码 Token 只在 sidecar/Rust 短暂存在；WebView 只获得临时二维码图片，过期、取消或确认后立即清理。
- Cookie、ticket、`ts_sign`、私钥、证书、CSRF、`ttwid`、`msToken` 作为一个会话凭据包处理。
- M1 只存内存，不提供“在此设备保持登录”；应用重启后重新扫码。完整 Cookie/ticket/私钥/证书会话包可能超过 [Windows Credential Manager `CREDENTIAL` 的 `CredentialBlob` 上限](https://learn.microsoft.com/windows/win32/api/wincred/ns-wincred-credentiala)，因此不得把整包直接写入单个 keyring 条目。
- 扫码取得的会话凭据只驻留 sidecar 内存，IPC 只向 Rust 投影认证状态和自回显过滤所需的最小账号标识，不返回原始凭据。初始化和控制命令只走继承 stdin，不把秘密放入 argv、环境变量、`.env`、普通文件、React、日志、错误或崩溃报告。
- 扫码取得的凭据必须通过上游已有的一致性检查；登出时清空 sidecar 和 Rust 内存。
- 后续若要求保持登录，另立 DPAPI 加密文件方案：Credential Manager 只保存随机 wrapping key，版本化密文文件保存会话包；必须补齐 ACL、原子替换、损坏回退、退出清理和升级测试后才能启用。该方案不阻塞 M1。
- 所有 HTTPS 恢复证书验证；出站域名使用固定 allowlist，不提供代理配置。

## 10. 读取、重连与发送策略

### 10.1 读取

- 直播信息 REST 总超时 15 秒，WSS 握手 10 秒。
- 连续 30 秒没有有效协议帧视为失活。
- 先按协议发 ACK，再把弹幕放入业务队列。
- 仅网络型读取失败自动重连：`1/2/4/8/15 秒 + jitter`，最多 5 次。
- 稳定接收有效帧 60 秒后才重置连续失败计数。
- 直播结束、认证失效、风险控制或用户停止时不自动重连。
- 重连重新解析直播状态和 canonical `room_id`，但旧 generation 的发送永远拒绝。

### 10.2 发送

- 只有已认证、已连接、当前 generation 匹配时允许发送。
- 正文 trim 后 1～100 个 Unicode 字符且 UTF-8 不超过 400 字节；拒绝换行、NUL 和控制字符。真实门禁发现平台限制更小时只允许下调。
- 同一会话最多一个发送请求在途。
- 产品初始保守限频：至少 3 秒一条、每账号每房间最多 5 条/分钟；不宣传为平台官方限制。阶段 1 真实门禁只能把限制调得更严，未取得明确平台许可前不能为了追赶积压放宽。
- 429、验证码或风险控制后至少冷却 60 秒；平台要求更长时取更长值。
- 每个任务由 Rust 生成并缓存 `client_action_id`，只做本地重复调用防护，不冒充平台幂等。
- `unknown` 结果计入“结果未知”，系统不自动重发；UI 允许用户查看，但不提供一键批量重发。
- 如果持续入站速率超过安全发送速率，队列保持在用户配置容量，持续按“丢最旧未发送任务”策略更新；不能通过并发调用 `sendMsgInRoom` 规避单账号发送限制。
- 429、验证码、认证失效或风险控制出现后，立即停止新发送并进入 `risk_controlled`；继续读取时仍可入队，但任务照常受 60 秒过期和容量丢弃约束。不得自动恢复发送，必须由用户完成官方验证/重新扫码后手动恢复；旧 generation 任务在重新登录或切房时统一取消。

### 10.3 M1 本地随机回复

M1 只使用用户本地配置的回复池，不申请模型租约，不调用 Go 或模型供应商：

- 回复池 `1～100` 条，trim、去重并逐项执行字符数、字节数和控制字符校验。
- Rust 在任务入队时均匀随机选定候选并保存候选索引；候选超过一条时避免与上一任务连续相同。
- 任务只保存本场内存中的弹幕摘要、候选索引、最终正文和状态，不持久化弹幕或回复历史。
- 测试链路可把回复池设为唯一且带本次测试标识的一条，便于验证“读取一次、发送一次、回显不再入队”；随机性测试另使用多个候选和固定注入 RNG。

### 10.4 后续模型回复边界

模型回复不属于 M1。只有随机回复链路通过真实门禁后才允许进入后续阶段，并固定使用现有 `purpose=chat`：Go 的唯一 OpenAPI 契约签发短期 delegated credential；Rust 控制面客户端直接取得并只存内存，Renderer 不接触 `direct_access_token`；Rust 直接调用供应商并向 Go 上报不含正文的 usage/延迟/状态摘要。当前 Go 尚不返回 delegated credential，现有由 Renderer 提交 `direct_access_token` 的 `direct_model_chat` 不能复用于本功能，必须先完成契约、服务端、Rust 所有权和泄密测试。

## 11. 进程与退出

- 通过现有 Windows 后台进程入口启动固定绝对路径的 sidecar，不使用 shell 拼接，不弹控制台窗口。
- Python sidecar 和必要的 Node 子进程必须进入同一个启用 `KILL_ON_JOB_CLOSE` 的 Job Object。
- sidecar 收到 stdin 初始化消息前不得启动 Node，保证 Rust 先完成 Job 绑定。
- stdout/stderr 持续读取，单行和尾缓冲有上限，防止管道写满死锁。
- 停止顺序：禁止新发送并推进 generation → 取消登录/重连 → 关闭 WSS → 关闭 stdin → 等待网络和心跳 → 终止超时进程 → 关闭 Job → Join 所有线程 → 清理内存凭据。
- 优雅退出预算纳入现有 `shutdown_all` 的 3 秒总预算；Manager 的 `Drop` 只做兜底。
- 正常停止、sidecar 崩溃、UI 重载和应用退出后都不得残留 Python/Node 进程或线程。

## 15. 验收矩阵

| 类别 | 场景 | 通过条件 |
|---|---|---|
| 输入 | 合法 ID/标准 URL、HTTP、短链、userinfo、非抖音域、端口、超长和 Unicode 数字 | 只接受契约内输入；其余稳定拒绝且无 panic |
| 解析 | 正常 chat、礼物/点赞、坏 gzip/protobuf、解压炸弹、超 500 项 | 只产出 chat DTO；畸形输入有界失败 |
| ACK | `needAck` fixture | ACK 字段精确，且不被 UI 背压阻塞 |
| 重连 | 断网、恢复、耗尽、用户停止、直播结束 | 按退避执行；停止后不再重连；缺口可见 |
| 突发 | 容量 100 时输入 10,000 条弹幕 | outstanding 队列始终≤100；持续丢最旧未发送任务；发送中任务不取消；UI 可操作且计数准确 |
| 一对一 | 唯一外部弹幕、重连重放、本账号回显 | 每个已接纳 `msgId` 恰好一个任务；重复帧和自回显不建任务 |
| 随机回复 | 单候选、多候选、固定 RNG、候选去重、连续重复 | 单候选确定发送；多候选只选启用项；可重复测试；多候选尽量不连续相同 |
| 顺序与过期 | 队首等待超过 60 秒、队首被容量丢弃 | 游标越过终态，后续任务继续按 seq 发送，无永久队首阻塞 |
| 发送 | 空白、超长、控制字符、重复 task、限频、平台拒绝 | Rust 最终校验；单请求在途；每任务最多一次平台尝试 |
| 未知结果 | 平台已处理但客户端超时 | 返回 `outcome_unknown`，不自动重试、不误报失败 |
| 竞态 | 解析/重连/发送中切换房间 | 旧 generation 事件和结果丢弃，不向错误房间发送 |
| 凭据 | 扫码、登出、过期、应用重启 | M1 只存内存；重启后必须重新扫码；React/Go/日志/普通文件无凭据 |
| 权限 | main 与 final-effect 窗口 | 只有 main 可认证、监听、发送 |
| 生命周期 | 正常停、sidecar 崩溃、应用退出、UI 重载 | 无 Python/Node 孤儿进程、线程或管道泄漏 |
| 真实环境 | 自有测试直播间低速输入 20 条中文/emoji 弹幕 | 每个已接纳外部 `msgId` 对应一次回应尝试；无自回复循环或重复发送 |
| 队列配置 | 10、500、5000、0、负数、5001、运行中修改、暂停后缩容 | 合法容量生效；非法值拒绝；运行中拒绝；缩容按规则丢最旧且计数准确 |
| 高流量环境 | 入站持续高于发送上限 | 队列保持用户容量并持续丢最旧任务；读取不中断；不提高发送并发 |
| 长稳 | 2 小时并至少 3 次断网恢复 | 内存、句柄、线程和队列达到平台后稳定 |

## 18. 开发完成后的审查流程

每个阶段由独立子线程实现相互独立的部分；主线程合并后逐文件检查 diff、未使用代码/依赖、重复组件、敏感信息、错误路径和文档一致性，再执行统一验证。代码完成后先向用户确认是否进入“代码总监式挑剔审核”；审核结论修复并复测后才交付。
