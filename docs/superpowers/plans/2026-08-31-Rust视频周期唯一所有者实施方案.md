# Rust 视频周期唯一所有者实施方案

> 2026-08-31 参数面板补链与连续展示：实机通过 mpv IPC 连续回读确认完整 `glsl-shader-opts` 中普通视频、高级视觉参数及计划标记均已跨周期变化，原故障包含 DTO 未携带 Active N 参数以及 React 在确认间隙隐藏整块参数面板。`active_cycle_snapshot` 仍只在读回和下一帧呈现均确认后从 `current_schedule` 原子发布，并由 React 的 effective 状态只读投影；面板在配置加载后始终完整显示，同一播放代际的非 Source 确认间隙保留上一轮已确认显示值，新代次无已确认值或 Source/关闭处理时显示当前配置值。显示保留不改变后端 Active 事实，运行快照不得写回配置基线，避免每轮状态刷新反向重置 Rust 周期。CPU4 继续严格遵守 `4/83` 支持边界。

> 日期：2026-08-31
> 范围：桌面客户端受管视频周期、mpv 提交确认、状态投影
> 非目标：普通声音候选、插话文件、麦克风插话、固定话术、RTMP、虚拟摄像头、Go 控制面

## 1. 目标与唯一事实源

修复后，mpv 提供视频物理事实，`RealtimeVideoRuntime` actor 是视频周期唯一状态所有者。React 只提交配置和播放意图，并展示 Rust 发布的状态；WebView 是否可见、是否支持当前媒体的音轨、计时器是否被节流，都不得改变视频周期行为。

| 事实或行为 | 唯一所有者 |
| --- | --- |
| 视频源内 PTS、实际 FPS、pause、seeking、cache、EOF | mpv 观察值 → Rust |
| 周期抽样、N/N+1/N+2、到期合并、变化次数 | `media_video_cycle` |
| shader/CPU4 提交、读回、呈现确认、恢复 | `RealtimeVideoRuntime` |
| 音画同步纠偏 | Rust；PortAudio 只提供可听 PTS |
| 周期范围、开关和基础参数 | React 配置意图 |
| 视频进度、周期和实际后端 | React 只读投影 Rust DTO |

## 2. Rust 周期控制器

`media_video_cycle` 持有媒体段身份、配置修订、周期范围、基础视频参数、N/N+1/N+2、下一 sequence、已确认变化次数、最新 mpv PTS/FPS 和当前应用事务。控制器只接收五类事件：`Configure`、`PlaybackIntent`、`SourceBoundary`、`MpvObservation`、`ApplyResult`；只产生准备快照、发起应用、清空旧周期和发布状态四类动作。

抽样继续使用 Mulberry32，不引入随机库。种子由 `session_id + playback_generation + clock_epoch + loop_index + sequence` 确定性派生；相同身份重放必须生成逐字段相同的快照。跨媒体身份绝不复用旧 FPS 或通过取模复用计划。

## 3. 唯一视频时钟与播放意图

受管视频的位置只来自 Rust DTO 的 `presented_pts_ms`。`sourceAudio.currentTime` 仅用于 WebView 音频兼容和诊断，不再回退为视频周期时钟。音频不支持、缓冲或不可用只影响音频展示，不得令视频周期进入 `stalled`。

播放、暂停、用户 seek、停止由 Tauri 命令直接发送 Rust 播放意图。WebView 不再生成视频 `clock_epoch`，也不再通过 `sync_realtime_video_renderer` 驱动周期主链。

## 4. 原子媒体边界

换源、循环和新 generation 使用同一串行事务：封住提交并取消旧 applying；发布 `source_transitioning`；清空 N/N+1/N+2、FPS、epoch、指纹和待确认事务；GPU/CPU4 写入中性快照；执行 `loadfile replace` 或合法循环 seek；回读路径、pause、EOF、seeking 和递增 PTS；读取新媒体实际 FPS；建立新媒体段身份；使用新 FPS 建立首个周期；首个快照呈现确认后才发布已生效。

任何一步失败都保持 fail-closed，不得把旧媒体的 shader 参数或旧 N 宣传为当前媒体已生效。

## 5. 应用确认事务

GPU 事务状态固定为：

```text
Ready → Applying → ReadbackConfirmed → PresentedConfirmed → Active
```

规范化后的完整 shader 选项、媒体段身份、实际 FPS 和 sequence 使用项目既有 `sha2` 计算 SHA-256。指纹前 48 位拆成两个可由浮点精确表示的 24-bit 计划标记，一并写入完整 `glsl-shader-opts`。回读使用固定允许列表并按键值映射比较，不依赖字符串顺序。

匹配响应和完整回读只进入 `ReadbackConfirmed`；必须继续观察到 mpv PTS 严格越过提交前 PTS，且没有 shader/VO 致命错误，才进入 `PresentedConfirmed` 并晋级 N、增加变化次数。

软超时只发布 `result_unknown`，不晋级、不降级，IPC worker 继续等待迟到响应。回读不匹配时，同一指纹最多幂等重发一次。硬超时优先重建同一种 mpv 后端，只重放最后已确认 N；结果未知的 N+1 不得重放。只有确认的渲染失败或同后端重建失败才进入既有单向降级。

## 6. fail-closed 状态合同

Rust 每次发布携带严格递增 `status_revision`，并同时发布媒体 generation、应用状态、实际 FPS、计划指纹、确认变化次数和 N/N+1/N+2。React 保存：

- `lastObservedStatus`：诊断用途，可以记录被拒绝的 DTO。
- `effectiveStatus`：只有 DTO 合法、revision 单调、generation 匹配且应用已经呈现确认时存在。

身份拒绝、DTO 无效、revision 回退、generation 不匹配、`applying`、`result_unknown`、未完成读回或未完成呈现时，`effectiveStatus` 必须为空，`effects_applied=false`，界面显示“视频后端状态待确认”。旧 DTO 不能继续显示为“实时 GPU 已生效”。

## 7. React 删除边界

删除 React 视频侧运行时调度引用、未来计划、候选 sequence、重试状态、活动视频快照、提交在途状态、候选 prepare/commit 函数、100ms 视频分支，以及生产代码对 `prepare_realtime_video_plan`、`commit_realtime_video_plan` 和视频主链 `sync_realtime_video_renderer` 的调用。音频周期保持现状。

后台可停止 UI 轮询；恢复可见时立即读取一次 Rust 状态。前台看到轮次从 8 跳到 14 属于显示补帧，不属于周期突发执行。

## 10. 代码总监审查整改（2026-08-31）

正式审查在首轮实现之上继续发现并修复了以下高风险问题：

1. 已存在活动 N 时重新配置可能继承 `Active`，导致新配置无法重新读取 FPS 和建立周期队列。配置收口现在统一清空旧计划和指纹，并显式回到 `Available → source_transitioning`。
2. shader 异步提交在途时，后续到期观察可能用 N+2 覆盖待确认 N+1。运行时现在仍记录 mpv 观察值，但在事务结束前禁止替换 pending 计划。
3. 暂停意图曾会清除 `result_unknown` 事务。暂停现在保留待确认事务；只有 seek、停止或媒体边界使旧事务失效。
4. 重新配置遇到不可取消的在途 IPC 时，旧命令可能迟到执行。现在先失效并关闭旧 mpv 会话，再以中性快照开始新配置事务。
5. 关闭视频处理成功写入中性快照后，旧 shader 事务仍可能迟到晋级。中性化成功现在会显式丢弃被替代事务。
6. shader/VO 致命错误原先晚于呈现晋级检查，可能短暂发布错误的 `Active`。现在先处理致命证据，再允许 `PresentedConfirmed → Active`。
7. React 的被拒绝 DTO 曾仍可能参与 Original/EOF/进度判断。前端现区分 `lastObserved`、`accepted`、`effective`：诊断可保留最后观察，所有控制和普通状态投影只读取已接受状态，物理确认完成后才存在 effective。
8. mpv 的源内 PTS 与 Rust 计划的跨 loop 绝对 PTS曾直接相减。主页现在按 `loop_index × source_duration + presented_pts_ms` 投影绝对呈现位置。
9. 控制器曾允许没有同 sequence 应用事务的计划推进。晋级现在强制要求同 sequence 事务存在并已呈现确认。
10. React 中重复的视频随机抽样实现和类型已经删除，避免再次形成第二个视频周期事实源；普通声音抽样保持不变。

## 11. 中性 Source 会话接管修复（2026-08-31）

开发端复核发现，“源画面播放中 · 等待 Rust 视频周期接管”并不一定表示 mpv 或 GPU 会话不存在：受管 mpv 可以已经使用 GPU/CPU4 物理模式运行，只是尚未提交首个周期快照，因此逻辑后端仍显示为中性 `Source`。旧实现把这个逻辑展示状态当作周期不可用，并走了只更新 PTS 的轻量分支，导致控制器永远没有机会读取实际 FPS、建立 N/N+1/N+2 并提交首个计划。

修复后的能力判断只依赖真实执行事实：视频处理已开启、受管 mpv 进程和会话存在、物理启动模式为 GPU 或 CPU4。满足这些条件时，即使逻辑后端仍为 `Source`，runtime 也会创建控制器、把 mpv 观察送入控制器、补齐实际 FPS，并建立首个周期队列；Source 轻量 PTS 分支只允许在控制器确实不存在时执行。

同时关闭了 Original 自愈与首周期配置之间的竞态：React 在同 generation 的中性 Source 已由 GPU/CPU4 物理会话承载时，不再发起 Original ensure；Rust actor 对已经进入队列的迟到 ensure 再做一次所有权核对，只要周期控制器已安装且物理周期会话仍可用就幂等返回。这样旧请求不能把 `Available / source_transitioning` 覆盖成 `Source / Active`，也不能让控制器落入“存在但永远收不到 Available tick”的夹死状态。

loop、seek、换源和新 generation 统一重新进入 `Available / Spawned / source_transitioning`，清除旧计划、旧 FPS 和待确认事务后再由新边界观察建立队列。真正降级到 Original、没有受管进程或没有可用会话时则清除可能残留的控制器并保持 `Idle`，不得伪造周期接管。React 对“当前 generation 已接受、物理 GPU/CPU4 会话存在、逻辑 Source 且 apply state 长期 Idle”的组合显示明确错误“Rust 视频周期未建立”；正常的 applying、result_unknown 和 source_transitioning 仍显示待确认，不误报为缺失。

本次回归新增并锁定：中性 Source + GPU 会话可建立控制器、Source 快路径不得吞掉已有控制器、loop/EOF 后可重新填充 FPS 与队列、Original fallback 不建立周期、迟到 Original ensure 不覆盖控制器，以及前端等待态和缺失态的区分。最终门禁更新为 Rust library 518 项、视频观察合同 14 项、前端后端状态合同 36 项；Rust 全量、Clippy、前端类型检查与 511 项全量测试均通过。

## 12. 开发端真实接管闭环（2026-08-31）

真实 30fps MP4 复验继续发现并修复了四个只在完整 Tauri/mpv 链路出现的断点：React 调用 `configure_realtime_video_cycle` 的周期字段改为与 Rust DTO 一致的 `min_period_ms/max_period_ms`；CPU4 无活动 N 启动时统一发布 `Available/Spawned`；首周期配置按物理 GPU/CPU4 模式同步逻辑 backend 与 `parameter_support.backend`，避免 fail-closed 接收器拒绝自相矛盾 DTO；同一源、同一物理模式、同一 HWND 的中性 mpv 会话原地复用，不再误走跨源停止分支。

mpv 的 `glsl-shader-opts` 正式读回在当前运行时返回 JSON 对象而非逗号字符串。IPC 边界现在同时接受有界字符串和有界对象映射；对象只允许合法键及字符串/数字标量，数值经有限浮点规范化后再与本地完整选项 map 比较，数组、对象嵌套、非有限值、超限条目和超限字节继续 fail-closed。该修复保留计划指纹、完整选项校验和下一帧呈现确认，不降低读回强度。

真实门禁结果：30fps MP4 在 D3D11/D3D11VA `gpu-next/libplacebo` 会话中进入 `Active`，界面显示 N/N+1/N+2，已确认变化从 0 推进到 10；mpv 读回包含变化后的两个 24-bit 计划标记和 `al_runtime_source_fps=30`。主窗口处于后台、最终效果窗置前期间，PTS 从约 28.57s 推进到 60.03s，计划标记由 `3661106/2935545` 变为 `4971542/5216042`；主窗口重新置前只刷新 Rust 权威状态，没有触发突发 prepare/commit。非 30fps TS、MP4→TS→MP4、软/硬超时故障注入和长时间稳定性仍未在本次复验执行，继续保留为发布前实机门禁。

## 13. 状态恢复原子性修复（2026-08-31）

普通声音与视频同时开启的真实测试捕获到非法 DTO：Rust 保留 `N=active`，却把 `activation/lifecycle` 改成 `Available/Spawned`，React 按严格合同拒绝该状态。根因是 tick 把两类恢复合并处理：逻辑 `Source` 表示物理效果不可确认，必须清除旧槽位；单纯的 `parameter_support.backend` 漂移只是元数据问题，不应打断已经确认或正在确认的事务。

修复后，逻辑 `Source` 分支先按物理 `process_launch_mode` 认领 GPU/CPU4，再统一调用 `begin_source_transition()`，原子清除 N/N+1/N+2、活动/待提交指纹并重新读取 mpv PTS/FPS。仅 support 漂移时只恢复权威后端支持报告，保留 Active 和在途事务。`finalize_pending_plan` 不再信任计划携带的旧 support，而是在晋级前按物理启动模式重新规范化，避免下一轮再次发布自相矛盾状态。

回归测试分别锁定 Source 清槽、support-only 保留事务，以及活动计划晋级不得重放旧 support。普通声音链和 PortAudio 不在本次代码修改范围内；EOF 边界的音频 recovery 只作为联合实测观察项。

后续真实测试又发现两处同类深层状态：Source 恢复原来只清 DTO，runtime 的 current/pending、两份 schedule 和 controller queue/apply transaction 仍可能在下一 observation 重新提交旧计划；shader 硬超时重建则先发布 `Available`，随后恢复最后确认 N 却没有同步恢复 Active 生命周期。现在 Source fail-closed 恢复、Configure 和 EOF 的首次预转换统一失效两层计划，边界完成后的新身份转换不再重复清空；GPU renderer 重建按 `current` 原子投影生命周期和确认 N，CPU4 空计划与 demote 过渡也强制清除残留活动槽。Rust 测试合同新增与 React 一致的约束：活动 N 必须对应 Active，GPU/CPU4 Active 必须存在活动 N。

## 14. TS 呈现 PTS 单调化（2026-08-31）

开发端 TS 联合测试发现，mpv `time-pos` 在自然播放中可能因时间戳重排和毫秒舍入出现短暂回摆。旧控制器把任何 `1ms` 回退都判为 `PresentedPtsRegressed`；约 `40ms` 的观察 tick 连续三次命中后，会把健康 GPU/CPU4 会话错误降级到 Original。

修复只作用于同一 `MediaSegmentIdentity` 内的自然播放观察：以已观测最大 PTS 作为周期调度高水位。普通容器允许 `min(ceil(2 × 1000 / actual_source_fps) + 2ms, 100ms)`；`.ts/.m2ts` 按真实样本使用 `min(ceil(6 × 1000 / actual_source_fps) + 2ms, 500ms)`，覆盖本机 22.001848fps TS 的 227ms 回摆。容差内不降低高水位、不提前或重复提交计划，超过容差仍 fail-closed；没有有效实际 FPS 时不放宽。显式 seek 仍必须更换 `clock_epoch`，loop、换源和新 generation 仍必须建立新媒体段身份并原子清空队列，因此该容差不能跨边界掩盖真实时钟回退。

结构化错误携带 previous、observed、delta 和 tolerance。继续实测确认 30fps MP4 的 300ms 回退来自 Rust 音画同步 `HardSeek`，不是容器抖动：mpv 的物理 seek 成功后，runtime 立即把周期控制器观察高水位 rebase 到目标源内 PTS，再恢复播放；该内部纠偏不更换媒体身份，也不清除 N/N+1/N+2 或应用事务。若 seek IPC 失败则不得 rebase。原始 Rust 状态中的 `presented_pts_ms` 继续保留 mpv 物理观察值，只有周期到期判断使用单调高水位。

## 15. CPU4 重启原子性与联合实机结论（2026-08-31）

代码总监复核发现，CPU4 prepare 因进程缺失、宿主 HWND 变化或同模式重启时，旧实现会以空计划启动新进程，随后又可能从 runtime `current` 投影 Active N，形成“物理中性、逻辑已生效”。修复后必须在停止旧进程前通过 `current_cpu4_plan` 快照最后已确认 N，并把该计划交给 `start_cpu4_process` 在新进程真实重放；源边界已经原子清空 current/schedule 时自然得到空计划，不得跨源复用。

本轮在桌面开发端同时开启普通声音处理与视频处理，使用 22.001848fps TS 和 30fps MP4 顺序播放。主窗口置于后台期间，Rust/mpv 完成 TS EOF 换源，视频周期确认次数继续推进；重新置前只刷新 Rust 权威状态，没有出现前端突发 prepare/commit。mpv 固定属性回读确认当前路径为 MP4、`container-fps=30`、`estimated-vf-fps=30`、`pause=false`，shader 完整选项包含新的两个 24-bit 计划标记和 `al_runtime_source_fps=30`，不再携带 TS 的 `22.001848`。PortAudio 在播放段内保持运行并持续产生最终混音 PCM；EOF 边界日志允许短暂进入 recovery，但本轮没有执行 30 分钟长稳、200 周期、软/硬 IPC 超时或真实 CPU4/Original 故障切换，以上仍是发布前门禁。

## 16. 帧健康误降级收口（2026-08-31）

最终联合复测在 22fps TS + PortAudio 负载下观测到连续三个 `vo-passes` timing 窗口超过 `45.598ms` 预算，其中新增样本 P99 约 `56.629ms`，但 frame-drop/decoder-drop 为 `0/0`，mistimed/delayed 不可用。旧实现用“健康计数增长或 P99 超限”推进硬降级，因而把缺少输出异常证据的尾尖峰误判为持续过载。

修复后，滚动与增量 P99 仍写入权威状态作为遥测和故障说明，但硬降级连续计数只接受 frame-drop、decoder-drop、mistimed 或 delayed 的实际增长；完整健康窗口清零计数，连续三个真实异常窗口仍执行 GPU profile → CPU4 → Original 的既有单向降级。presented-PTS 停滞 watchdog、IPC 断链、进程退出和 shader/VO 致命错误均未放宽。PortAudio 触发的 Rust HardSeek 在物理 seek 成功且周期 PTS 高水位 rebase 后立即清除帧健康基线，再按用户暂停态决定是否恢复播放，旧 pass/计数不能跨 seek 继承。

本轮不重写 `vo-passes` 遥测算法。当前 pass snapshot 尚未完整利用 mpv 的 count/index，逐 pass P99 求和也不是严格的逐帧总耗时 P99；由于该值不再单独影响后端生存性，它作为已知遥测精度风险保留。后续若要恢复 timing-only 自动降级，必须先按新增 count、稳定 pass 身份和逐帧对齐总耗时重建证据，并重新完成真实负载门禁。

2026-08-31 联合长稳在 TS EOF/VO 重配置处进一步捕获到 `vo-passes samples 无效`，旧实现把三次辅助遥测解析失败直接升级为物理后端降级。修复后帧预算采样增加稳定播放资格：EOF、暂停、seek、缓存、待处理 source/loop/seek 边界和非 `Active` 应用阶段一律跳过；空、缺失或非法 samples 作为暂不可用并清除跨边界基线，不参与降级。传输失效仍立即同后端重建，真实健康计数连续增长仍保留原门禁。旧计时作废后，最新代码于 07:15:56–07:46:04 重新完成 30 分 08 秒 TS+MP4+PortAudio+插话后台联合长稳：播放池进入第 7 次循环，D3D11/gpu-next 保持 Active，普通声音变化 347 次、插话 161 次，未出现 fallback、IPC 超时、watchdog 或遥测误降级。当前机器门禁通过；200 周期、故障注入、CPU4/Original 和跨硬件门禁仍未覆盖。

## 17. 首次代次发布原子性（2026-08-31）

最终构建复测发现一个间歇窗口：首次 GPU 启动的 `record_renderer_started/claim_realtime_status` 已把逻辑 backend 切到 RealtimeGpu，但正常 prepare 尾部尚未写入 GPU parameter support；若 ConfigureCycle/Prepare 在中间取消或失败，actor 仍会发布 backend/support 不一致的 DTO。React 正确 fail-closed 后，该非法快照可能持续到当前源 EOF，导致首个 generation 只显示“等待 Rust 视频周期接管”。

唯一 `publish_status` 现在在递增 revision 和复制快照前执行原子合同收口：Source 对应 Source 空支持与 NotApplicable，RealtimeGpu 对应 GPU83 支持，CPU4 对应 CPU4 精确支持。同 backend 已经存在的 incomplete/unsupported 报告不改写，避免掩盖真实能力缺口。该收口不替代各状态转换自身的认领逻辑，而是保证任何命令成功、失败、取消或 tick 中间态都不能越过 Rust→React 信任边界发布自相矛盾 DTO；React 校验保持原样。

## 18. shader 响应等待期间的 IPC 独占（2026-08-31）

mpv 命名管道由唯一 worker 串行执行。实机联合测试发现，shader 已异步提交但仍处于 `AwaitingResponse` 时，旧 tick 会继续发送 EOF、PTS 和帧健康同步查询；这些请求排在 shader 后面，却可能先耗尽 250/350ms 观察预算并调用 `expire()`，从而由客户端主动关闭整个 IPC 会话。修复后，`AwaitingResponse + Ok(false)` 立即结束当前 tick，不再发出任何后续 mpv IPC；`AwaitingPresentation` 仍恢复 PTS 观察，保证读回后能够以严格越过提交前 PTS 完成下一帧确认。同步命令的结果未知隔离、shader 软/硬超时、读回验证和既有单向降级规则保持不变。

## 19. 周期边界倒退与音频重锚收口（2026-08-31）

联合播放发现“每个周期卡顿并倒退数秒”包含两条物理链。其一，周期提交仍把跨循环绝对 PTS 交给只接受源内 PTS 的帧调度器；TS 在边界出现轻微时间戳回摆时，新 sequence 又会先命中 `OutOfOrderPts`，最终被误报为“周期静态调度快照缺失”，连续失败后触发 GPU 档位切换和 mpv 重启。现在提交使用 `loop_index × duration` 做检查减法，只向调度器传源内 PTS；新 sequence 遇到同段轻微回摆时以现有高水位生成完整快照，不降低调度时钟，也不触发后端降级。

其二，普通声音 revision 变化时 PortAudio 曾以被原生 mpv 接管、可能为 `0` 或旧值的 WebView `video.currentTime` 重锚。错误音频锚点持续后会触发 AV Recovery，并把 mpv 硬定位到落后数秒的可听 PTS。受管视频的 PortAudio 重锚现只接受同 generation/loop 的 Rust `presented_pts_ms`；权威状态缺失时 fail-closed 等待，不回退 WebView 视频时钟。同一媒体身份的可听时钟短暂缺样只清空当前诊断并恢复基础 speed，不销毁 AV 控制器身份；恢复后不会再次被当作 Startup。Recovery 和 ClockAuthorityChanged 只允许视频落后时向前定位，禁止把领先的视频向后拉，领先偏差只用有界降速收敛。

Rust 状态同段只接受单调非递减的呈现 PTS，显式 seek、loop 和换源边界才允许降低；shader 应用事务存在时暂停 PTS watchdog 的软 seek。回归覆盖新 sequence 的轻微回摆、跨循环绝对/源内 PTS 换算、同段状态回退拒绝、Recovery 禁止向后定位、音频时钟短暂缺样保持身份、shader 应用期间 watchdog 禁用，以及最终效果窗 PortAudio 只使用 Rust 已呈现 PTS。

## 20. 单次 IPC 遥测超时不得重建播放器（2026-08-31）

联合长稳继续捕获到一次静默 mpv 重建：物理视频仍在连续播放，但一次播放观察或 `vo-passes` 帧预算属性读取超时会绕过既有连续失败门禁，立即停止健康进程并用当前 generation 重建。管道名末尾数字是媒体 `session_id/playback_generation`，不是进程实例计数；因此从 `-1` 变为 `-7` 只表示 generation 7 发生了一次重建，不能解读为六次重启。

播放观察的单次 `IpcTimeout` 现在作为结果未知的瞬时失败，纳入三次连续门禁；下一次成功观察会清零计数。帧预算属于辅助遥测，单次超时只清空本轮 pass/drop 基线并等待下一稳定窗口，不得杀死或降级播放器。明确的 IPC 断连、连续观察超时、shader 硬超时、进程退出以及确认的 VO/shader 失败仍保留既有同后端重建或单向降级路径。回归测试锁定单次播放观察超时和单次帧预算超时均保持 backend epoch、GPU 后端与降级历史不变。

## 21. EOF 无下一帧与 PortAudio 跨段时钟（2026-08-31）

开发端复现出两个独立边界。视频 shader 已完成完整选项读回、进入 `AwaitingPresentation` 后，如果 mpv 同时到达 EOF，本段已没有下一真实帧可以越过提交前 PTS；旧 actor 又把 `AdvanceAfterEof` 排在未完成的 shader 事务之后，形成相互等待。现在只有“EOF 身份匹配且阶段恰为 `AwaitingPresentation`”允许推进命令越过 idle 门禁，单源循环和多源换源在执行边界事务前丢弃这份无法呈现的 pending apply，再由新段重新建立 N/N+1/N+2。`AwaitingResponse`、`PresentedConfirmed` 和非 EOF 状态继续保持原有串行门禁。回归同时锁定首个控制器计划编译出的 shader 快照不是中性值。

声音侧的 `OutputTimeline` 原来先计算 callback 已消费帧对应的绝对时间，再把结果转换回旧 segment 的源内 PTS；一旦实际 PCM 越过段尾，转换永久返回 `None`，健康判定持续进入 recovery。现在状态时间轴直接使用 `presentation_anchor + callback_elapsed` 计算连续绝对呈现时间；当可听 callback 已物理跨段且显式 pending 尚未晋级时，输出线程按绝对时间建立同源新 `loop_index`、源内 PTS 与 `LoopBoundary`。存在完全匹配的新段 pending 时复用它的 audio epoch，否则分配新 epoch；底层 `AudibleAudioClock` 仍严格拒绝越段观察。

真实 72.3 秒素材继续暴露出帧调度器的跨循环序号门禁：新 segment 合法地从 sequence 1 重新开始，但旧调度器先与上一轮较大的 sequence 比较，再处理已经推进的 schedule epoch，因此把所有新 loop shader 快照误判为 `StaleSequence`。现在明确的 Startup/LoopBoundary/SourceChanged 新 epoch 先取得重置权，允许 sequence 重启；同一 epoch 内的 sequence 倒退仍 fail-closed。AV 状态发布同时保证 `av_sync_drift_ms/audible_audio_pts_ms/audio_epoch` 只在 Active 进程下成组出现，source transition 和重锚首个无 drift 观察统一隐藏三项字段。实机跨循环后 D3D11/d3d11va/gpu-next 由 14 次确认继续推进到 19 次，N/N+1/N+2 恢复，PortAudio 保持“已生效”，React 未再拒绝 DTO。本轮未覆盖多文件、CPU4/Original、故障注入和长稳。
