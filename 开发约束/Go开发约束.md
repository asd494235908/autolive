## 本项目补充约束

- Go 后端遇到成熟、维护中且与当前版本兼容的第三方库或官方 SDK 已经解决的能力时，必须优先使用，不得自行重新编写同类 HTTP、数据库、鉴权、校验、序列化、日志、重试或加密工具。
- 只有现有成熟方案无法满足明确需求时，才允许自行实现；实现前必须记录原因、边界、测试方式和后续替换路径。
- 新增 Go 依赖必须有真实调用点、版本策略、许可证和安全评估，不得为“以后可能用”保留依赖。

# Go AI 开发规范

本规范约束 AI 在 Go 仓库中的分析、设计、实现、验证和交付行为。它适用于服务、CLI、Worker、Library 及多模块仓库，不预设 Web 框架、数据库库、缓存客户端或消息系统。项目已有约定与本规范冲突时，AI 必须先指出冲突、风险和建议，再由用户确认取舍；安全性与正确性要求不得静默降低。

## 1. 使用方式与规则级别

### 1.1 规则级别

- **必须**：交付前不可跳过；暂时无法满足时，必须停止相关交付或明确报告阻塞、影响和补救条件。
- **应当**：默认遵守；偏离时必须说明项目事实、收益、代价和验证方法。
- **禁止**：容易造成安全、正确性或维护性问题的做法；不得以赶进度为由绕过。

### 1.2 适用方式

- AI 必须先识别本次任务涉及的章节，并把相应规则转成验收项；规则不适用时，应当基于仓库事实说明原因，不能仅写“无关”。
- AI 必须优先遵守仓库说明、用户已确认的架构决定和工具链版本；不得用本规范擅自重构任务范围外的代码。
- AI 应当选择满足当前需求的最小复杂度；小项目不强制套用大型项目分层，大项目也不得省略真实存在的边界。
- AI 禁止把示例目录、库或命令解释为固定技术栈；所有检查命令均须满足本文件注明的适用条件。

## 2. 开发前必须完成的分析

### 2.1 仓库事实检查

- AI 必须先读取用户需求、仓库说明文件、根目录与相关子目录中的约定、`go.mod`/`go.work`、现有包结构、可执行入口、相关实现、测试、配置及构建脚本。
- AI 必须确认 Go 版本、Module 边界、现有依赖、代码生成方式、质量命令和部署约束；禁止仅凭文件名猜测项目约定。
- AI 必须先判断项目属于服务、CLI、Worker、Library 还是多模块仓库，再决定入口、包边界和文件位置；一个仓库含多种形态时，必须逐一标明。
- AI 应当用搜索和调用链确认现有能力是否可复用，并检查相邻代码与测试；禁止读到第一个相似实现就直接复制。

### 2.2 功能边界与文件说明

- AI 必须在改动前明确目标、非目标、输入输出、错误与安全边界、兼容性要求和可验证的验收条件。
- 新增文件前，AI 必须说明文件职责、调用方、依赖方向和放置理由；若无法说明清楚，应当先收窄职责而不是创建宽泛目录。
- AI 必须列出可能受影响的 API、数据库、缓存、消息、配置、迁移、文档和部署文件；不需要同步修改时，应当核实而非默认忽略。
- 涉及网络、并发或持久化时，AI 必须在实现前确定超时、取消、重试、幂等、资源释放和失败恢复策略。
- AI 禁止在没有理解现有结构时先创建 `utils`、`common`、`helpers`、`shared` 或 `misc`。

## 3. 框架与依赖选型

### 3.1 引入门禁

- 标准库或现有依赖能以可维护方式满足需求时，AI 禁止新增功能重叠的框架或库。
- AI 必须先检查现有版本、直接与间接依赖、许可证约束、替换成本及安全公告，再提出新增或升级。
- 只有需求确实需要框架或第三方依赖时，AI 才应当进行选型；不得为包装少量标准库调用而引入依赖。
- AI 禁止仅以个人偏好、网络文章、旧版本经验、下载量或热度作为选型依据。

### 3.2 调研与结论

- 需要选型时，AI 必须查询候选项当前的官方文档和发布信息，并比较维护状态、稳定性、Go 版本兼容性、生态与工具链、性能、安全、许可证和迁移成本。
- 性能比较必须对应项目工作负载并说明测量条件；禁止把脱离场景的 Benchmark 排名直接当作结论。
- AI 必须向用户列出候选项、最终选择、选择理由、主要代价和被排除方案；存在重大锁定效应或迁移风险时，必须先获得确认。
- 引入依赖后，AI 必须确认 `go.mod`/`go.sum` 变化与需求一致，并移除本次改动产生或暴露的未使用依赖；禁止为“以后可能用”保留依赖。

## 4. Module、Package、目录与文件放置

### 4.1 Module 与仓库

- 单仓库默认必须只使用一个根 `go.mod`；只有组件需要独立发布、独立版本或独立生命周期时，才允许增加 Module，并必须明确跨 Module 的版本与依赖策略。
- 使用多 Module 时，AI 必须说明其边界和发布关系；`go.work` 应当只服务于明确的本地协作场景，禁止依赖未提交的本地替换完成发布构建。
- 仅包含一个命令且没有可导入公共包的新 Module，入口**允许**位于根目录；包含多个命令，或同时包含命令与可导入包时，入口**应当**放在 `cmd/<app>/`。已有仓库使用其他清晰布局时必须尊重其 `go.mod`、安装路径和发布约定，禁止仅为套模板搬迁。无论入口位于何处，都必须只负责依赖装配、配置加载、启动和关闭，禁止承载业务逻辑。
- 不对外公开的实现应当放在 `internal/`；只有确实需要被外部 Module 导入且能够稳定维护的 API 才放公开包。

### 4.2 Package 与文件

- 包必须按业务能力或清晰职责组织，并保持依赖方向可解释；禁止仅按 `controller`、`service`、`repository` 名称机械分层。
- `pkg/` 禁止作为默认收纳目录；使用它前必须证明其中 API 面向仓库外部且具备稳定承诺。
- 包名应当简短、小写、单词化、通常不含下划线，并符合领域语义、避免重复父目录语义；`bytes`、`errors`、`strings` 等复数名称在语义准确时完全合法，禁止为了追求“单数”改坏名称。文件名应当使用小写和下划线，按职责拆分而不是按行数任意切割。
- AI 禁止创建职责不清的 `utils`、`common`、`helpers` 或 `misc` 包；通用行为应当归属最接近其领域含义的包。
- 生成文件、数据库迁移、开发脚本、无秘密的配置示例、测试数据和 API 定义必须分别放入含义明确的目录，并遵循仓库既有约定。
- 生成文件必须可识别来源和再生成方式；手写代码禁止混入会被生成器覆盖的文件。
- 测试文件应当靠近被测包；跨组件集成测试和测试数据只有在范围明确时才放独立目录。

## 5. API、接口与模块边界

### 5.1 Go 接口与依赖方向

- 接口必须由使用方定义，并保持为调用方真正需要的最小方法集合；禁止由实现方预先创建覆盖全部方法的“大接口”。
- 只有存在替换实现、测试边界或稳定抽象需求时才应当创建接口；禁止为了复用一行代码或假想未来实现建立公共包与接口层。
- 构造函数必须建立有效对象并显式注入必需依赖；可选项应当有清楚默认值和验证，禁止依赖隐式初始化顺序。
- 包之间必须保持单向、可解释的依赖；出现循环依赖时必须重新划分职责，禁止用全局变量、回调注册或复制类型掩盖循环。
- 禁止全局可变业务状态；进程级只读常量或经明确生命周期管理的基础设施对象除外。

### 5.2 外部 API 与兼容性

- API 必须明确输入、输出、错误、鉴权、幂等和版本兼容边界；公开行为变化必须同步更新契约、文档和测试。
- 项目采用 OpenAPI、Protobuf 或等价契约时，必须明确唯一事实源、生成命令和兼容性检查；禁止同时手工维护多份会漂移的 Schema，也禁止直接修改可再生成产物。
- 数据传输类型应当与持久化模型和核心领域类型解耦到实际需要的程度；禁止把内部字段无选择地序列化到外部。
- AI 应当优先保持向后兼容；确需破坏兼容性时，必须说明迁移步骤、过渡期和回滚条件。
- 禁止把底层数据库错误、堆栈、内部路径或敏感字段直接暴露给客户端。

## 6. 错误处理与 Panic 边界

### 6.1 普通错误

- 可预期的失败必须通过返回值传递；调用方必须处理、转换或明确上交，禁止吞掉错误或只记录后继续返回成功。
- 包装错误必须使用 `%w` 保留错误链，并补充失败动作和对象上下文；禁止重复堆叠“发生错误”等无价值文本。
- 调用方必须按错误类型、哨兵错误或 `errors.Is`/`errors.As` 分类；禁止通过匹配错误字符串控制流程。
- 错误文本、响应和日志禁止泄露 Token、密码、密钥、连接串、个人数据或完整敏感载荷。
- 多阶段操作必须定义部分成功语义；清理、回滚或关闭的错误不得无条件覆盖首个业务错误，应当按项目约定合并或记录。

### 6.2 Panic 与恢复

- 只有不可恢复的程序错误，例如违反内部不变量或启动期缺少必需条件，才允许在明确边界处 Panic；普通输入、网络、数据库和业务失败禁止 Panic。
- HTTP 与 Worker 的执行边界必须恢复意外 Panic、记录必要诊断信息并隔离单个请求或任务的影响；恢复后禁止伪装成成功。
- `recover` 只能放在能够定义失败语义的边界；禁止在底层包中静默恢复并继续使用可能损坏的状态。
- 启动期 Panic 或致命错误必须导致非零退出；运行期是否终止进程应当依据状态是否仍可信，并由最外层边界决定。

## 7. Context、并发与资源生命周期

### 7.1 Context 与外部调用

- `context.Context` 必须作为首个参数显式传递，不得存入结构体，不得传 `nil`；仅跨 API 边界需要的请求级值才可放入 Context。
- 下层禁止使用 `context.Background()` 或新建无关 Context 绕过上层取消；只有进程根任务可以创建根 Context，并必须明确所有者。
- 网络、数据库及其他外部调用必须支持取消并设置与调用链预算一致的超时；客户端断开或上游取消后，必须停止无意义工作。
- 超时、取消、临时失败、永久失败和业务拒绝必须可区分；重试不得突破上层截止时间。

### 7.2 Goroutine、Channel 与共享状态

- 每个 Goroutine 都必须有明确所有者、启动点、退出条件、取消路径和等待机制；禁止启动无法追踪、无法停止的后台 Goroutine。
- 并发任务必须设置上限，并依据资源容量和负载验证；禁止为每个输入无界创建 Goroutine。
- 批量并发必须定义首错或聚合失败策略、取消传播、结果收集、顺序要求和部分成功语义。
- 每个 Channel 必须明确发送方、接收方和关闭方；只由发送方关闭，接收方禁止关闭共享 Channel，发送方也不得在仍可能发送时关闭。
- Channel 缓冲大小必须有依据；禁止把扩大缓冲当作修复死锁、背压或泄漏的手段。
- 共享状态应当优先通过所有权划分或不可变数据减少共享；使用锁时必须缩小临界区，并禁止持锁执行慢 I/O、阻塞发送或未知回调。
- 使用 `sync.WaitGroup`、互斥锁、原子操作或并发原语时，必须验证复制、计数、加锁顺序和异常退出路径；竞态敏感改动必须执行竞态检测。

### 7.3 资源生命周期

- 文件、HTTP Response Body、数据库 Rows、事务、Ticker 和连接等资源成功获取后，必须立即安排与其作用域匹配的释放；循环中禁止无界累积 `defer`。
- 必须检查会影响数据完整性或持久化结果的 `Close`、`Flush`、`Commit`、`Rollback` 等错误；只读资源的关闭错误可按风险记录。
- 事务必须保证所有返回路径均提交或回滚；资源所有者必须负责释放，禁止依赖垃圾回收替代显式关闭。

## 8. HTTP、数据库、缓存与消息

### 8.1 HTTP 与 API

- HTTP 状态码必须表达传输与协议结果，业务错误码必须表达稳定业务语义；禁止所有错误统一返回 HTTP 200。
- 输入必须在边界校验类型、长度、范围、格式和组合约束；分页必须设置默认值与上限，请求体和文件上传必须限制大小。
- 写操作必须按业务风险设计幂等键、唯一约束或状态机；不得只依赖客户端避免重复提交。
- 普通有限请求必须配置读取、处理、写入和空闲等适用超时，并对慢客户端、限流、取消和过载定义行为。
- WebSocket、SSE、流式上传/下载等长连接禁止机械套用普通请求总超时；必须分别定义握手超时、读写或心跳空闲超时、可选的最大连接寿命，以及协议允许的续期或重连行为。
- 长连接必须设置进程级及主体/租户级连接或订阅上限、单连接有界缓冲和背压；必须定义慢消费者处置、断开后的 Context 取消、心跳失效、重连重放与顺序语义，以及优雅关闭时停止新连接和排空在途消息的边界。
- 上传路径必须使用服务端生成或严格净化的名称并限制目标目录、类型和权限；禁止直接拼接用户路径，防止路径穿越。
- 鉴权、授权和资源归属检查必须在可信边界执行；通过 ID 获取资源时仍必须检查当前主体权限。

### 8.2 数据库与事务

- SQL 必须使用参数化查询；禁止把用户输入拼接进 SQL 结构。动态列名或排序字段必须来自白名单。
- 事务应当尽量短，禁止在事务或持锁期间进行不必要的远程 I/O；必须明确隔离级别、锁顺序、冲突重试和提交失败处理。
- 重试事务必须有上限、退避并保证操作幂等；禁止对语义未知的数据库错误无限重试。
- 查询必须检查预期索引和必要时的执行计划；禁止无界查询、N+1、循环逐条写入和无上限结果集。
- 批量写入应当使用数据库支持的批处理并控制批量大小；连接池必须设置并验证最大连接、空闲连接、生命周期和等待指标，避免池耗尽。
- Schema 变化必须提供与发布顺序兼容的迁移和回滚/前滚方案；危险迁移必须说明锁表、数据回填和停机风险。

### 8.3 缓存

- Redis 或其他缓存的设计必须说明 Key 命名、过期策略、容量、序列化版本和数据归属。
- 缓存必须处理穿透、击穿、雪崩、一致性、过期抖动和分布式锁失效；具体策略必须与读写比例和可接受陈旧度匹配。
- 缓存禁止作为唯一事实来源，除非业务明确将其设计为权威存储并提供相应持久性与恢复保证。
- 分布式锁必须有唯一持有者标识、到期与续期策略，并只允许持有者释放；禁止把锁当作数据库约束或幂等设计的替代品。
- 锁租约可能过期但旧持有者仍能写入下游时，必须使用 fencing token、版本条件写入或等价机制拒绝陈旧持有者；禁止仅凭“已成功加锁”推断后续副作用仍受保护。

### 8.4 消息

- 消息消费必须默认可能重复，并定义稳定幂等键、去重范围及副作用提交顺序。
- 必须明确确认时机、重试上限、退避、死信处理和不可重试错误；禁止失败后立即无限重投。
- 生产端必须定义发送失败、重复发送和本地状态已提交但消息未发送的处理；需要一致性时应当采用与现有架构匹配的 Outbox 等方案。
- 顺序处理必须明确排序键和并发范围；禁止假设队列全局有序或“恰好一次”能够自动消除业务重复。

## 9. 配置、安全与敏感信息

### 9.1 配置

- 配置必须由环境变量或项目明确的配置源注入，并在启动时完成类型、范围和必填项校验；非法配置必须快速失败。
- 仓库必须提供不含秘密的示例配置，并说明变量含义、默认值和是否必填；禁止把生产凭据写入源码、测试夹具、镜像或示例。
- 配置优先级和热更新语义必须明确；无法安全热更新的配置应当通过受控重启生效。

### 9.2 安全边界

- 外部输入必须按信任边界校验、规范化和编码，并针对 SQL 注入、XSS、CSRF、SSRF、路径穿越、越权、重放和敏感信息泄漏建立防护与测试。
- 服务端发起的 URL 请求必须限制协议、目标网段、重定向和解析结果，防止 SSRF 访问本机、元数据服务和内网资源。
- 密码必须使用适合密码存储的哈希算法；Token、会话、API Key 和签名必须定义有效期、轮换、撤销和重放防护。
- 文件和目录必须使用最小权限；临时文件必须安全创建并及时清理。
- 日志、指标、Trace 和错误响应禁止输出 Token、密码、密钥或完整敏感请求体；确需关联时应当脱敏、摘要或使用不可逆标识。
- AI 必须检查新增依赖、开放端口、调试端点和默认配置扩大了哪些攻击面，并在交付中说明残余风险。

## 10. 日志、指标、链路与性能

### 10.1 可观测性

- 日志必须结构化，并至少包含时间、级别、组件以及适用的请求 ID 或 Trace 标识；字段名和错误分类应当稳定。
- 请求或任务入口必须建立关联标识并向下游传播；禁止把个人信息或无界内容用作关联标识。
- 关键请求、队列、数据库和外部依赖必须提供延迟、错误率、吞吐及相关资源指标，以回答慢、错、堵塞和容量问题。
- 高基数字段，例如用户 ID、完整 URL、订单号和错误全文，禁止作为指标标签；应当放日志或 Trace，并控制采样与保留。
- 告警必须对应可行动的用户影响或资源风险；禁止仅因单次错误产生无法处置的噪声告警。

### 10.2 性能

- 性能优化前必须先用 Benchmark、`pprof`、Trace 或生产指标定位瓶颈，并记录基线、目标和代表性负载。
- 优化必须同时验证延迟分位数、吞吐、CPU、内存、分配和外部资源影响；禁止仅凭微基准牺牲正确性或可维护性。
- 只有存在性能目标或回归风险时才应当添加 Benchmark；结果必须可重复，并避免把外部环境噪声误判为代码变化。

## 11. 测试与质量门禁

### 11.1 测试策略

- 测试必须覆盖适用的成功、失败、空值、边界、超时、取消和并发路径；修复缺陷时必须增加能够复现该缺陷的测试。
- 时间、随机数、网络和外部依赖必须具有可控边界；应当通过小接口、测试服务器、固定种子或可注入时钟控制，而不是依赖睡眠和真实公网。
- 应当优先使用表驱动测试表达同一行为的多个输入；禁止为单一简单分支制造复杂测试框架或无价值 Mock 层。
- 集成测试必须明确外部前置条件、隔离数据并可重复执行；禁止依赖执行顺序或遗留环境状态。
- Fuzz 应当用于解析器、协议、序列化和不可信输入边界，并把发现的失败样本保留为回归用例。

### 11.2 质量命令

- 对适用的 Go 项目，交付前必须执行仓库规定的格式化命令、`go vet ./...`、`go test ./...` 和 `go test -race ./...`；因平台、构建标签或外部服务无法执行时，必须报告原命令、原因和未覆盖风险。
- 仓库未提供格式化命令时，必须对本次改动的全部 Go 文件执行 `gofmt -w <files>`，再用 `gofmt -l <files>` 验证无输出；禁止只检查部分改动文件。
- 只有仓库存在可执行程序时才必须执行 `go build ./...`；纯 Library 仓库不把构建可执行文件作为门禁。
- 使用构建标签、代码生成或多个 Module 时，必须逐一执行项目约定的对应检查；禁止只在根目录跑到“无包可测”就宣称通过。
- AI 必须删除本次改动产生或暴露的未使用代码、导入、依赖和配置，并检查重复实现；禁止以注释掉代码代替删除。

## 12. 构建、启动与优雅关闭

### 12.1 构建与启动

- 构建必须可从干净环境按仓库文档复现，并固定必要的 Go 版本、生成步骤和构建参数；禁止依赖开发机未声明的文件或工具。
- 本地和 CI 构建不得把密钥编译进二进制；版本、提交标识等非秘密元数据应当通过明确机制注入并可查询。
- 服务和 Worker 必须明确配置校验、日志初始化、连接初始化、迁移责任、监听或消费启动的顺序；初始化失败必须清理已获得资源并非零退出。
- Readiness 必须反映是否可接收新工作，Liveness 必须反映进程是否需要重启；禁止用外部依赖短暂故障直接制造无休止重启。

### 12.2 优雅关闭

- 可执行程序必须处理适用的系统信号并触发统一取消；关闭流程必须先停止接收新请求或任务，再等待在途工作，最后关闭外部资源。
- 优雅关闭必须设置总超时，并为超时后的强制退出定义日志和退出语义；禁止无限等待泄漏的 Goroutine。
- HTTP、Worker、消息消费者、数据库、缓存、追踪导出器和日志缓冲必须按依赖逆序关闭，并检查关键关闭错误。
- 容器构建、镜像、用户、健康检查和供应链等部署规则统一遵循仓库根目录 [`AGENTS.md`](../AGENTS.md)；本文件不重复另一套不存在的容器规则。

## 13. AI 开发执行流程

AI 必须按顺序执行以下流程；发现阻塞时必须在进入依赖步骤前报告：

1. 阅读需求、仓库说明、`go.mod`/`go.work`、相关实现、入口、测试和配置。
2. 明确功能边界、非目标、兼容性、安全约束和验收条件。
3. 检查现有目录、Module、Package、依赖、生成器和质量约定。
4. 说明每个新增文件的职责、调用方、依赖方向和放置理由。
5. 仅在必要时调研框架或依赖，并向用户提交候选项、选择、代价和排除理由。
6. 先补充或设计能够验证行为的测试；文档或纯配置任务应当定义等价的结构与内容验证。
7. 实现满足需求的最小改动，保持现有风格和兼容边界。
8. 检查错误、超时、取消、并发上限、资源释放、幂等及安全边界。
9. 删除本次改动产生或暴露的未使用代码、依赖、导入、配置和重复实现。
10. 按适用条件执行格式化、静态检查、测试、竞态检测和构建。
11. 检查 API 文档、示例配置、数据库迁移和部署文件是否需要同步更新。
12. 汇报改动文件、验证命令与结果、未验证项、残余风险和必要后续动作。

- AI 禁止在验证失败后宣称完成；若失败与本次改动无关，必须提供可复现证据并说明影响。
- AI 应当把实现与任务范围保持一致；发现旁支问题时记录风险，不得擅自扩大为无关重构。

## 14. 交付前检查清单

交付前，AI 必须逐项确认并报告“不适用”的事实依据：

- [ ] 已执行仓库格式化命令；仓库没有该命令时，已对本次全部 Go 文件执行 `gofmt -w <files>`，且 `gofmt -l <files>` 无输出。
- [ ] 已执行 `go vet ./...`，或报告无法执行的命令、原因与风险。
- [ ] 已执行 `go test ./...`，测试覆盖适用的成功、失败和边界路径。
- [ ] 对支持竞态检测的适用 Go 项目已执行 `go test -race ./...`，超时、取消和泄漏路径已检查；不适用时已记录平台、构建标签或工具链依据及未覆盖风险。
- [ ] 仅在存在可执行程序时执行了 `go build ./...`，启动失败和优雅关闭语义已验证。
- [ ] 已删除未使用的代码、导入、依赖、文件、配置和重复实现。
- [ ] 输入校验、鉴权授权、参数化 SQL、SSRF、路径和敏感信息处理已按改动范围检查。
- [ ] 涉及 WebSocket、SSE 或流式传输时，已验证握手/空闲超时、心跳、连接上限、有界缓冲、背压、慢消费者、断开取消、重连语义和关闭排空。
- [ ] 日志、指标和 Trace 不含秘密或高基数指标标签，并能定位关键失败。
- [ ] API 契约、README 或操作文档、无秘密示例配置已按需同步。
- [ ] 数据库迁移包含发布顺序、数据处理和回滚/前滚说明；不涉及 Schema 时已确认无迁移需求。
- [ ] 部署配置与 Readiness、Liveness、信号和资源关闭行为一致；容器细节已按仓库根目录 `AGENTS.md` 的部署约束检查。
- [ ] 已记录所有验证命令、结果、未覆盖环境和残余风险，未把警告当作通过。

## 15. 常见错误做法

- **万能公共包**：把无关函数放入 `utils`、`common` 或 `helpers`；应当按领域或具体职责归包，单次一行复用不创建抽象。
- **过度分层**：小功能机械创建 controller/service/repository 及一一对应接口；应当只保留能表达依赖边界或替换需求的层。
- **吞掉错误**：记录错误后返回 `nil` 或成功响应；必须返回、转换或在明确边界终止，并保持错误链。
- **无界 Goroutine**：为每个输入直接 `go func()` 且没有等待；必须设置并发上限、取消、退出和回收机制。
- **无超时 I/O**：使用默认客户端或无截止时间的数据库、网络调用；必须使用上层 Context 和明确超时预算。
- **后台 Context 绕过取消**：下层改用 `context.Background()` 让请求结束后仍工作；必须传递调用方 Context，独立后台任务需单独定义所有者和生命周期。
- **字符串匹配错误**：比较 `err.Error()` 判断错误类别；必须使用类型、哨兵错误和 `errors.Is`/`errors.As`。
- **日志泄密**：输出 Authorization、密码、连接串或完整请求体；必须删除、脱敏或使用不可逆关联标识。
- **所有错误返回 HTTP 200**：混淆协议状态与业务状态；必须选择合适 HTTP 状态码，并用稳定业务错误码补充语义。
- **接收方关闭 Channel**：多个发送者仍可能写入时由接收方关闭；必须由明确的发送所有者在发送完全结束后关闭。
- **事务中慢 I/O**：持有数据库锁时调用外部服务；应当重排流程、缩短事务，并明确一致性补偿。
- **缓存替代事实库**：只写缓存且没有持久性设计；必须以权威数据源为准，或正式定义缓存为权威存储并验证恢复能力。
- **依赖堆叠**：标准库或现有依赖可完成却新增同类库；必须通过选型门禁，并清理未使用依赖。
