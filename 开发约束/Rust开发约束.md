## 本项目补充约束

- Rust/Tauri 客户端遇到成熟、维护中且与当前版本兼容的 Crate 或官方 SDK 已经解决的能力时，必须优先使用，不得自行重新编写同类 HTTP、序列化、鉴权、加密、异步、文件、媒体播放或系统集成工具。
- 只有现有成熟方案无法满足明确需求时，才允许自行实现；实现前必须记录原因、边界、测试方式和后续替换路径。
- 新增 Crate 必须有真实调用点、版本策略、许可证和安全评估，不得为“以后可能用”保留依赖。

# Rust AI 开发规范

## 1. 文档目标与适用范围

本规范约束 AI 在现有或新建 Rust 项目中进行分析、设计、实现、审查与交付。适用项目包括 Library、CLI、Service、Worker 和由多个 Crate 组成的 Workspace；规则不绑定某个 Web 框架、异步运行时、数据库库或错误处理库。

- **必须**先识别项目类型、运行边界、发布方式和已有约定，再决定目录、依赖与实现方式。
- **必须**把正确性、安全性、可维护性和可验证性作为交付条件，而不是只以“能够编译”为完成标准。
- **应当**以最小必要改动完成需求；只有职责、复用范围、发布单元或依赖方向确有差异时才增加抽象和层级。
- **禁止**把本规范当成固定项目模板，或为了套用规范重排与本次需求无关的现有代码。
- 容器相关部署规则**必须**统一遵循仓库根目录 [`AGENTS.md`](../AGENTS.md)；本文只说明 Rust 进程的构建产物、启动、探针和退出语义。

## 2. 规则优先级

执行时按以下顺序处理约束：法律与安全要求、用户明确要求、仓库内说明与已确认设计、本规范、语言或工具的默认行为。发生冲突时，AI **必须**指出冲突、影响和采用的规则，**禁止**静默选择。

- **必须**：交付前不可跳过；无法满足时必须报告阻塞、替代验证和剩余风险。
- **应当**：默认遵守；偏离时必须记录适用场景和理由。
- **禁止**：会显著增加正确性、安全性或维护风险的做法；若受既有代码限制暂时无法消除，必须限制影响范围并报告技术债。

正文中的独立规则**必须**用以上三级关键词标明级别。“不得”“不能”“不可”归入**禁止**；“仅当……才可”表示条件**必须**成立，否则归入**禁止**。这些同义表达只能解释已标级规则，不构成第四种规则级别。

规则只在项目适用时执行。例如纯 Library 没有服务探针，未使用异步运行时的 CLI 不需要异步任务规则。AI **禁止**为触发一条不适用的检查而擅自引入框架、工具或长期依赖。

## 3. 开发前分析、框架与依赖选型

### 3.1 读取现状

开始修改前，AI **必须**读取并记录与本次需求有关的以下内容：

1. 用户需求、仓库说明、当前目录结构和验收条件。
2. 根目录及相关成员的 `Cargo.toml`、`Cargo.lock`，Workspace 成员、依赖来源、目标平台、Rust Edition、MSRV 与构建 Profile。
3. 已声明的默认 Feature、可选 Feature、Feature 依赖关系，以及 CI 实际覆盖的 Feature 组合。
4. `src/lib.rs`、`src/main.rs`、`src/bin/`、相关 Module、集成测试、单元测试、示例和基准目录。
5. 现有框架、运行时、错误类型、配置、Tracing、数据库、缓存和消息方案，避免重复建设。

AI **必须**据此判断项目属于 Library、CLI、Service、Worker 还是 Workspace，明确本次功能边界、非目标、外部输入、资源所有者、并发边界和兼容性要求。禁止在未理解现有结构时先创建 `utils`、`common`、`helpers` 或 `shared` 等宽泛模块。

### 3.2 选型门禁

标准库或现有依赖能够满足需求时，**应当**优先复用。确需新增或升级框架、Crate 时，AI **必须**：

1. 查询候选方案当前的官方文档和发布说明，不得只依赖旧记忆、流行度或个人偏好。
2. 检查维护状态、稳定版本、MSRV、Rust Edition 与目标平台兼容性。
3. 检查默认及可选 Feature、传递依赖、编译时间、二进制体积和运行成本。
4. 检查许可证、安全公告、已知不安全代码范围及与现有生态的兼容性。
5. 比较候选方案与标准库、现有依赖、较小 Crate 的实现成本和长期维护成本。
6. 向用户或交付报告说明选择理由、主要取舍、启用的 Feature 与验证方式。

- **禁止**仅为一个小功能引入大型框架。
- AI **必须**先检查依赖维护者支持的默认组合和最终解析的 Feature 图，可使用 `cargo tree -e features` 或项目等价命令留证。禁止为省事开启无关 Feature，也禁止无项目证据地统一设置 `default-features = false`；只有收益、兼容性和受支持组合明确且已验证时，才应当关闭默认 Feature 并显式选择能力。
- **禁止**同时保留职责重叠的 Crate 而没有迁移计划。
- **应当**在升级依赖前确认破坏性变更、MSRV 变化和锁文件影响，避免把无关升级混入功能改动。

## 4. Workspace、Crate、Module 与文件放置

### 4.1 Workspace 与 Crate

- 只有存在多个独立 Crate、不同发布单元或明确编译边界时，才**应当**建立 Workspace；单体项目禁止仅为“以后可能拆分”预建空成员。
- 新建且未在 `Cargo.toml` 自定义 Target 路径的 Package，单一二进制入口**必须**使用默认的 `src/main.rs`，多个独立二进制入口**应当**放在 `src/bin/`。已有项目通过 `[[bin]]` 等配置使用其他清晰路径时，AI **必须**尊重其发布名称与布局，禁止仅为套默认目录搬迁；每个入口都必须明确职责、配置和退出行为。
- 可被二进制、集成测试或其他 Crate 复用的公开能力**应当**由 `src/lib.rs` 暴露；`main.rs` 应保持为装配、启动和退出边界。
- 每个 Crate **必须**有单一、清晰的职责。跨 Crate 依赖应当单向且最小，禁止用“共享 Crate”收纳无关代码形成循环概念依赖。
- `build.rs`、过程宏 Crate 和自定义代码生成只在普通构建无法满足需求时使用；其输入、输出、重跑条件和目标平台约束**必须**可复现。

### 4.2 Module 与测试放置

- Module **应当**按业务能力或明确技术职责组织，并与调用边界一致；文件拆分以降低理解和变更耦合为目的，不按类型机械分层。
- **禁止**持续扩张的巨大 `mod.rs`、无边界 `utils.rs` 和过深模块树。出现多个无关职责时必须按能力拆分，并保留最短可理解路径。
- Module 文件名**必须**使用 `snake_case`；二进制、示例、基准和集成测试 Target 名称**应当**使用 `kebab-case`，已有兼容性名称除外。禁止同一层混用无法由 Cargo 约定或 Manifest 解释的命名风格。
- 与私有实现紧密相关的单元测试**应当**放在同一 Module 的 `#[cfg(test)]` 中；验证公共行为或多模块协作的测试放在 `tests/`。
- 存在公共 Library API 时，**应当**通过 Rustdoc 示例、Doctest、`examples/` 或项目文档中的至少一种受维护形式展示典型用法，不强制小型库创建独立 `examples/`；纯二进制项目的 `examples/` **允许**展示 CLI 或可执行程序用法。已提供的示例必须纳入适用验证；`benches/` **应当**只用于有明确性能问题或基线的场景，**禁止**存放无法编译、未维护的示例或基准。
- 数据库迁移、协议定义和生成文件必须放在项目已有约定位置，并明确生成源；禁止手工修改可再生成产物而不更新其源文件。

### 4.3 Feature 边界

- Feature **必须**表达可解释的能力或平台差异，名称、依赖关系和默认行为必须有文档。
- 新增 Feature **应当**保持能力可加、组合可用，禁止在没有平台或兼容性约束时用“启用一个 Feature 关闭另一能力”。受支持的 Feature 组合**必须**被 CI 或交付验证覆盖；确因目标平台或既有兼容性存在互斥 Feature 时，必须在构建时给出清晰错误并分别验证，禁止产生未测试的组合。
- **禁止**用 Feature 隐藏本应由运行时配置决定的业务行为，也禁止保留没有使用者的默认 Feature。

## 5. 类型、Trait、API 与模块边界

### 5.1 可见性与类型建模

- 项默认保持私有；只有真实调用者需要时才使用最小范围的 `pub(super)`、`pub(crate)` 或 `pub`。新增公开项**必须**说明稳定性和使用者。
- **应当**用 Enum、Newtype 和经过校验的构造函数表达有效状态，使非法状态难以构造；禁止使用魔法字符串或让 `String` 承担所有 ID、状态、金额、路径和 URL 类型。
- 公共 API 或调用点中多个布尔参数会产生歧义、顺序错误或非法组合时，**禁止**继续堆叠，必须改用具名配置结构、Enum 或状态类型。语义局部且参数名清晰的私有小函数允许保留少量布尔值，AI 应当根据调用可读性而不是数量机械重构。
- 外部传输结构与领域类型职责不同时**应当**分离，在转换边界完成校验；禁止让反序列化成功等同于业务输入有效。
- 泛型、关联类型和宏只在能减少真实重复或表达编译期约束时使用；若具体类型更清晰，禁止为假想复用增加类型体操。

### 5.2 Trait 与公共 API

- Trait **必须**由真实调用边界、多实现需求或测试替身需求驱动，通常由使用者一侧定义最小行为。
- **禁止**为每个结构体创建同名 Trait，禁止为了“可扩展”预留没有第二个调用方或实现的抽象层。
- 使用静态分发还是 `dyn Trait` **必须**根据对象安全、代码体积、性能和运行时替换需求决定；不得无依据统一选择。
- 公共 API 的所有权、借用、生命周期、错误、线程安全、取消和阻塞语义**必须**稳定、清晰并有文档。
- 公共函数**应当**接收满足需求的最弱约束，避免无必要地取得所有权或要求 `'static`；返回借用时必须让生命周期关系在 API 上可理解。
- 破坏公共 API、序列化格式、错误分类或 Feature 行为前，**必须**确认版本策略、下游使用者和迁移方式。

## 6. Option、Result、错误上下文与 Panic 边界

### 6.1 缺失与失败

- 值可能合理缺失时**必须**使用 `Option<T>`；操作可能失败时**必须**使用 `Result<T, E>`。禁止用空字符串、零、负数或其他魔法值表达缺失或失败。
- Library **应当**返回调用方可匹配、可分类的结构化错误，并只暴露稳定且有用的信息；Application 可以在进程、请求、任务等边界增加操作上下文，但**禁止**丢失原始错误链。
- 错误转换**必须**保留错误来源和必要上下文；禁止把不同原因全部压缩成字符串、布尔值或同一个无信息错误。
- 错误正文和日志**禁止**包含 Secret、凭据、完整令牌、敏感查询参数或不必要的个人数据。
- 外部 API 的状态码、公开错误码和内部错误必须分层映射；对调用方提供可行动信息，同时禁止泄露堆栈、SQL、文件系统布局等内部细节。

### 6.2 `unwrap`、`expect` 与 Panic

- **禁止**在正常错误路径使用 `unwrap`、`expect` 或 `panic!`，包括配置缺失、输入非法、网络失败、数据库失败和 Channel 关闭。
- 使用 `unwrap`/`expect` 的**必须**条件是：不变量已经由同一段代码证明，或测试代码中的失败明确表示测试前提错误；不满足条件时**禁止**使用。`expect` 信息**必须**描述不变量，而不是重复“失败了”。
- `panic!` **必须**只表示程序缺陷或不可恢复的不变量破坏，**禁止**替代业务错误。Library **禁止**让可预期输入触发 Panic。
- **禁止**把捕获 Panic 作为通用错误处理。隔离 Panic 的**必须**条件是处于 FFI、插件或任务隔离等明确边界，并且能够证明展开安全、恢复到一致状态；隔离后**必须**记录并使该工作单元失败。
- 禁止使用空的 `match` 分支、丢弃 `Result` 或只记录后继续运行来吞掉错误。确需忽略时必须说明为何无害，并以显式代码表达。

## 7. 所有权、异步、并发与资源生命周期

### 7.1 所有权与生命周期

- **应当**先明确数据所有者、借用范围和生命周期，再选择复制或共享方式。禁止为绕过借用检查器无条件增加 `clone`、`Arc`、`Mutex`、`Box::leak` 或 `'static`。
- 复制成本、共享频率和可变性**必须**与调用边界匹配；大对象热路径上的 Clone 应有测量依据，小型 Copy 值无需为避免复制引入共享状态。
- 文件、Socket、连接、临时文件和其他资源**必须**有明确所有者，并优先依靠 RAII 释放；需要异步关闭、刷盘或协议握手时，必须显式执行并处理结果。

### 7.2 异步任务与取消

- 每个异步任务**必须**有所有者、取消路径、超时策略、Join 处理和错误传播方式；禁止创建无人管理的后台任务。
- `JoinHandle` 或等效句柄必须被等待、集中监督或显式移交给生命周期管理器，禁止静默丢弃 Join 错误或 Panic。
- 取消可能发生的每个 `.await` 边界**应当**检查取消安全性；对部分写入、领取消息、事务和状态变更定义提交、回滚或补偿语义。
- 阻塞 I/O 或 CPU 密集工作不得直接阻塞异步执行器线程；必须使用运行时提供的阻塞隔离、专用线程池、独立 Worker 或同步边界，并设置并发上限。
- 超时只表示停止等待，不自动保证底层工作已终止。AI **必须**确认取消信号能到达任务，或记录后台工作继续运行的后果。

### 7.3 共享状态、锁与 Channel

- 共享状态**应当**优先使用不可变数据、所有权转移或消息传递；只有确有共同可变状态时才使用锁。
- 使用锁时**必须**缩小临界区，禁止跨 `.await` 持有同步锁；多个锁必须定义固定获取顺序，并明确锁中毒后的失败、恢复或进程退出策略。
- 选择同步锁、异步锁、读写锁或原子操作前，必须依据竞争模式和持锁行为；禁止假定读多就一定适合读写锁。
- Channel **必须**设置容量；确需无界 Channel 时必须给出内存上界的外部保证和严格理由。发送方、接收方、关闭、背压、积压监控及接收方退出后的行为必须明确。
- `Send`、`Sync` 和 `'static` 约束必须来自线程或任务运行边界。**禁止**通过不安全实现伪造线程安全，也禁止为了满足过宽函数签名而把所有数据强制包装成 `Arc<Mutex<_>>`。

### 7.4 `unsafe` 边界

- `unsafe` **必须**最小化并封装在安全 API 后；每个 `unsafe` 块必须紧邻写明调用方与实现方依赖的不变量。
- 新增 `unsafe` 前必须证明安全 Rust 或已有受审查依赖不能合理满足需求，并说明别名、对齐、初始化、生命周期、线程安全、释放和 Panic 等风险。
- 新增或修改 `unsafe` **必须**有针对边界值和不变量的测试及独立审查说明；适用时使用项目已采用的内存模型、模糊测试或 Sanitizer 工具验证。
- **禁止**无依据实现 `unsafe impl Send` 或 `unsafe impl Sync`，禁止让裸指针和未验证数据越过安全封装边界。

## 8. HTTP、数据库、缓存与消息

### 8.1 HTTP 与外部输入

- 所有外部输入均视为不可信。反序列化入口**必须**限制请求体大小、嵌套深度、字符串长度和集合数量，并在进入领域逻辑前完成格式、范围和业务校验。
- 外部字符串、文件名、路径和 URL **必须**按用途验证；路径需规范化并限制在允许根目录内，出站 URL 需限制协议、主机、端口、重定向和解析后的地址，防止路径穿越与 SSRF。
- 普通有限 HTTP 请求**必须**定义读取、处理、写入、空闲和总请求超时；客户端断开或请求取消应传播到可取消的下游操作。
- WebSocket、SSE、流式上传/下载等长连接**禁止**机械套用普通请求总超时；必须分别定义握手超时、读写或心跳空闲超时、可选的最大连接寿命，以及协议允许的续期或重连行为。
- 长连接必须设置进程级及主体/租户级连接或订阅上限、单连接有界缓冲和背压；必须定义慢消费者处置、断开取消、心跳失效、重连重放与顺序语义，以及优雅关闭时停止新连接和排空在途消息的边界。
- 状态码与业务错误码必须表达真实结果，禁止所有响应都返回成功状态。分页、排序、筛选、API 版本和序列化变更必须有上限及兼容策略。
- 项目采用 OpenAPI、Protobuf 或等价契约时，必须明确唯一事实源、生成命令和兼容性检查；禁止同时手工维护多份会漂移的 Schema，也禁止直接修改可再生成产物。
- 会产生副作用的接口**必须**定义幂等键、唯一约束、状态机或等效防重机制；不得把客户端重试假设为“只会执行一次”。
- 文件上传必须限制大小、数量和允许类型，使用服务端生成的存储名，并在解析与落盘边界再次验证；禁止信任扩展名或客户端 MIME 声明。

### 8.2 数据库与事务

- SQL **必须**参数化；禁止拼接不可信值。动态表名、列名或排序字段必须从固定白名单映射，不能作为普通参数直接放行。
- 连接池必须设置上限、获取超时、连接/查询超时和健康策略，并监控等待与耗尽；请求取消应尽可能传递到数据库操作。
- 事务**应当**短小，只覆盖必须原子提交的数据库操作；禁止在事务或持有数据库锁期间执行无界网络调用、等待用户输入或长时间 CPU 工作。
- 多资源写入必须明确一致性边界。数据库与消息协作时应采用 Outbox、幂等消费或项目已有的可靠模式，禁止宣称不存在的跨系统原子性。
- 锁顺序、隔离级别、死锁重试和乐观并发策略必须与业务不变量对应；重试前必须确认操作幂等，并采用有上限、带抖动的退避。
- 查询必须设置结果上限，检查 N+1、循环逐条写入和连接池等待；慢查询或关键查询必须结合代表性数据检查预期索引与执行计划，禁止只因测试数据量小就宣称性能可接受。
- 迁移必须可审查并考虑回滚或前向修复、锁表时间、旧版本兼容和大表影响；禁止把破坏性迁移与依赖它的新代码无协调地同时上线。

### 8.3 缓存

- 引入缓存前**必须**定义数据源、Key 空间、TTL、容量、淘汰和一致性要求；禁止把缓存作为唯一事实来源，除非业务明确接受数据丢失。
- 缓存穿透必须通过输入校验、负缓存或等效策略处理；热点 Key 击穿必须使用请求合并、互斥重建或可接受的陈旧读取策略；雪崩必须使用 TTL 抖动、限流和分批恢复等措施。
- 写入、失效、重建顺序及失败补偿必须明确。分布式锁必须包含租约、唯一持有者标识和安全释放，禁止假定锁永不超时或客户端永不暂停。
- 锁租约可能过期但旧持有者仍能写入下游时，必须使用 fencing token、版本条件写入或等价机制拒绝陈旧持有者；禁止仅凭“已成功加锁”推断后续副作用仍受保护。

### 8.4 消息

- 生产与消费**必须**明确投递语义、消息版本、确认时机、顺序要求和最大消息大小。
- 消费者**必须**根据投递契约设计幂等键、去重状态或明确的丢失接受边界；处理结果**必须**在确认、拒绝或重试前分类为瞬时失败、永久失败、业务拒绝或结果未知。
- 使用有上限、带退避与抖动的重试，其**必须**前提是失败属于瞬时失败且操作可安全重试；不满足该前提时**禁止**进入常规重试循环。
- 永久失败**必须**按投递契约拒绝、进入死信或记录丢失；**禁止**对未改变的消息机械重试。业务拒绝**必须**作为已判定的业务结果处理，按契约确认或拒绝并记录原因，**禁止**伪装成瞬时失败重试。
- 结果未知且操作可能产生副作用时，重试前**必须**证明操作幂等，或具备可执行的补偿、去重机制；无法证明时**禁止**机械重试，并**必须**进入状态核对或人工处理边界。
- 交付契约要求至少一次或不可丢失时，处理成功前确认属于**禁止**行为；明确采用 at-most-once 时**允许**预确认，但**必须**记录丢失窗口、业务接受依据、监控与补偿边界。
- **必须**监控积压、失败分类、重试、死信、记录丢失和处理耗时，并定义接收方关闭时未完成消息的确认或重新投递语义。
- **禁止**把无限重试当作可靠性方案，**禁止**在没有版本兼容策略时直接变更已发布消息结构。

## 9. 配置与安全

### 9.1 配置边界

- 配置来源、覆盖顺序和环境差异**必须**明确；启动时必须一次性校验必填项、格式、范围和相互约束，错误信息应定位配置项但不得回显 Secret。
- 配置结构应使用有语义的类型和单位，禁止用裸整数混淆毫秒、秒、字节和数量，禁止在业务代码各处直接读取环境变量。
- 动态配置必须定义更新原子性、失败回退和可观测性；不能安全热更新的配置应要求重启。

### 9.2 Secret 与访问控制

- Secret **禁止**进入源码、日志、Tracing 字段、镜像层、错误正文、测试快照或可提交配置；必须通过项目认可的 Secret 管理方式注入，并支持轮换。
- 身份认证与授权必须分离：认证成功不代表有资源权限。每个受保护操作必须在服务端校验主体、动作和资源范围，防止横向或纵向越权。
- 密码、令牌、会话、API Key 和签名必须采用当前受维护的安全库及合适参数；禁止自创密码学、明文存储或把长期令牌暴露给不必要组件。
- Cookie 场景必须按威胁模型设置 Secure、HttpOnly、SameSite 并处理 CSRF；CORS 必须使用最小允许源、方法和 Header，禁止在携带凭据时放开任意源。
- 所有出站请求、文件访问、模板输出和富文本返回必须根据上下文处理 SSRF、路径穿越和 XSS 风险。
- 进程、数据库、消息和对象存储凭据应遵循最小权限；禁止以管理员权限弥补权限模型缺失。

### 9.3 依赖与供应链

- 新依赖必须固定在项目可复现的版本策略内并审查来源、许可证和安全记录；Git 依赖必须固定提交，禁止依赖可移动分支。
- 发现安全公告时必须判断实际可达性、修复版本和升级影响，不能只按告警数量下结论，也不得无说明忽略。

## 10. 日志、Tracing 与可观测性

- 服务和 Worker **必须**使用结构化 Tracing，并传播请求 ID 或 Trace 标识到异步任务、数据库、缓存、消息和出站请求边界；外部传入标识应校验格式，必要时重新生成。
- 事件字段应使用稳定名称，记录操作、结果、耗时和必要上下文；禁止拼接难以查询的整段文本，禁止记录 Secret、完整请求体或无必要的个人数据。
- 错误应在最有行动价值的边界记录一次并保留错误链；禁止每层重复记录同一错误造成噪声。
- 指标必须覆盖请求量、错误率、延迟、资源使用、连接池、队列积压和取消/超时等关键状态。标签必须来自有界集合，禁止使用用户 ID、原始 URL、错误全文等高基数值。
- Readiness 和 Liveness 只能表达各自语义：Readiness 表示是否可接收流量，Liveness 表示进程是否需要重启；禁止把短暂下游故障直接当作进程死亡。
- 性能优化前**必须**使用基准、Tracing、指标或 Profiler 定位瓶颈并保存基线；禁止只凭直觉引入 `unsafe`、缓存、复杂并发或自定义分配策略。
- 优化后必须在代表性数据和构建 Profile 下复测吞吐、延迟、内存与正确性，确认收益大于复杂度和回归风险。

## 11. 测试、基准与质量门禁

### 11.1 测试范围

- 测试**必须**覆盖公共行为及所有权边界体现出的转移、借用和资源释放结果，同时覆盖成功、错误、`None`、超时、取消、并发、解析器和不可信输入。
- 修复缺陷前**应当**先增加能够稳定复现的测试；新增行为必须覆盖验收条件和关键失败路径。
- 异步与并发测试应使用可控时钟、有限容量、明确超时和确定的同步点，禁止依赖任意休眠或无限等待掩盖竞态。
- Parser、协议和反序列化边界应根据风险采用属性测试或 Fuzz；`unsafe` 边界必须测试空值、边界长度、对齐、别名和生命周期不变量中适用的部分。
- 集成测试必须隔离外部状态并可重复执行；真实数据库、缓存或消息组件的要求必须在命令和环境说明中写清，禁止静默访问生产资源。
- 基准测试必须说明输入、环境、构建 Profile 和基线；无稳定测量条件时不得用单次耗时宣称性能提升。

### 11.2 必执行检查

在适用的 Rust 项目中，交付前**必须**从 Workspace 根目录运行：

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --all-features
cargo check --workspace --all-targets --all-features
```

- 项目不是 Workspace 时，仍可使用 Cargo 支持的 Workspace 参数；若仓库已有更严格、已验证的等效命令，**应当**同时遵循仓库约定。
- 如果 Feature 互斥或 `--all-features` 不是受支持组合，**禁止**机械运行上述全 Feature 命令。必须按受支持组合分别执行 `clippy`、`test` 和 `check`，并记录组合、命令及不能使用 `--all-features` 的原因。
- 目标平台或原生依赖无法在当前环境验证时，必须运行可行的本地检查，记录缺失环境和替代证据；禁止把未运行写成通过。
- 使用 `cargo audit`、`cargo deny` 或等效工具前，必须确认项目已经采用或得到用户同意；禁止为一次检查擅自增加长期依赖、配置或 CI 步骤。
- 检查产生的 Warning、未使用代码、依赖、导入、Feature 和配置必须清理；不能清理时必须说明其真实使用方和保留理由。

## 12. 构建、启动与优雅关闭

### 12.1 构建与启动

- 构建必须遵循仓库锁文件、目标平台、MSRV、Feature 和 Profile 约定；禁止在没有测量依据时修改 Release Profile 或启用面向本机的不可移植 CPU 特性。
- 二进制与部署产物必须能够追溯源码版本、依赖锁定和启用的 Feature。Library 发布前必须确认公共 API、文档、许可证和包内容。
- 进程启动时必须先校验配置，再按依赖顺序初始化资源；初始化部分失败时必须释放已创建资源并返回非零状态，禁止以“半可用”状态继续启动。
- Service 必须区分启动完成、Readiness 和 Liveness；只有必要依赖满足服务契约后才能进入 Ready。

### 12.2 优雅关闭

- Service、Worker 和长运行 CLI **必须**处理目标平台支持的终止信号，并将停止原因传播到任务所有者。
- 关闭顺序必须明确：停止接收新请求或新消息，触发取消，等待在途任务，在允许的语义下确认或回滚工作，刷出必要数据，关闭连接和其他资源。
- 必须设置总关闭超时以及各阶段预算；超时后应记录未完成任务和资源状态，并以符合部署契约的状态退出，禁止无限等待。
- 后台任务、连接池、Tracing 导出器和临时资源必须纳入关闭流程；测试必须覆盖正常关闭、任务失败和超时强制退出。
- 容器的 Dockerfile、基础镜像、用户、文件系统、健康检查、PID 1、信号转发和镜像发布细节统一遵循仓库根目录 [`AGENTS.md`](../AGENTS.md) 中的部署约束，本文禁止复制另一套容器规则。

## 13. AI 开发执行流程

AI **必须**按以下顺序工作，并在交付报告中留下可核查证据：

1. 阅读需求、仓库说明、Cargo 配置、入口、测试和相关代码。
2. 明确功能边界、非目标、验收条件、兼容性和风险输入。
3. 判断项目类型，检查现有 Module、依赖、Feature 和编码约定。
4. 确定新文件职责、放置位置、可见性、所有权与资源生命周期。
5. 必要时按第 3 章完成框架或 Crate 调研，并说明选型取舍。
6. 先设计或补充可验证行为的测试；文档或纯配置任务应定义等效的静态与行为验证。
7. 实现满足需求的最小改动，不顺带重构无关区域。
8. 逐项检查错误、`None`、超时、取消、并发、背压、资源释放和不可信输入。
9. 删除本次改动产生或暴露的未使用代码、依赖、导入、Feature 和配置。
10. 执行格式化、Clippy、测试、Check 及项目已有门禁，并如实记录命令和结果。
11. 检查公共文档、配置样例、迁移、协议和部署适配是否需要同步更新。
12. 汇报变更文件、行为变化、验证结果、未验证项、剩余风险和必要后续动作。

如果执行中发现需求与现有契约冲突、数据迁移不可逆、需要新增外部系统或无法验证关键安全假设，AI **必须**停止扩展实现并向用户确认，不得擅自扩大授权。

## 14. 交付前检查清单

以下条目只勾选已经验证的内容；不适用项必须标记原因，禁止默认视为通过。

- [ ] 已识别 Library、CLI、Service、Worker 或 Workspace 类型，并读取相关 Cargo、入口、Feature 与测试。
- [ ] 新文件位于职责匹配的位置；可见性、Trait、类型和公共 API 均保持最小且有真实调用者。
- [ ] `Option`、`Result`、错误链和 Panic 边界清晰，没有正常路径的 `unwrap`/`expect`。
- [ ] 所有任务均有所有者、取消、Join 和错误传播；锁、Channel、`Send`/`Sync` 与资源释放语义已验证。
- [ ] 新增 `unsafe` 已最小封装、记录不变量、补充边界测试并完成独立审查；未新增则明确记录。
- [ ] HTTP、数据库与缓存边界已处理大小限制、超时、幂等、背压和事务等适用风险；消息结果已按四类失败语义核验确认、拒绝、重试、死信、记录丢失、去重与补偿边界。
- [ ] 涉及 WebSocket、SSE 或流式传输时，已验证握手/空闲超时、心跳、连接上限、有界缓冲、背压、慢消费者、断开取消、重连语义和关闭排空。
- [ ] 配置启动即校验；Secret、认证授权、路径、URL 和依赖供应链符合第 9 章规则。
- [ ] Tracing、指标和探针能够定位错误、延迟、积压与资源耗尽，且无 Secret 或高基数标签。
- [ ] 已按受支持 Feature 组合执行格式化、Clippy、测试和 Check，并记录所有未验证目标。
- [ ] 启动、Readiness、Liveness、信号、在途任务、总关闭超时和资源释放语义均已明确。
- [ ] 已删除未使用代码、依赖、导入、Feature 和配置；文档、迁移及仓库根目录 `AGENTS.md` 的部署约束适配已同步检查。
- [ ] 交付报告准确列出改动、命令结果、剩余风险，不把跳过或失败的检查写成通过。

## 15. 常见错误示例

| 错误做法 | 风险 | 应当改为 |
| --- | --- | --- |
| 遇到借用错误就 Clone 整个对象 | 隐藏所有权设计问题并增加热路径分配 | 先缩短借用、拆分所有权或只复制必要字段；测量后再保留 Clone |
| 到处使用 `Arc<Mutex<_>>` | 扩大共享可变状态、锁竞争和死锁面 | 明确单一所有者，优先不可变数据或消息传递，只锁最小状态 |
| 持有同步锁跨越 `.await` | 阻塞执行器线程并可能形成死锁 | 在 `.await` 前释放锁，或重构为所有权转移；确需异步锁时缩短临界区 |
| 使用无界 Channel | 消费变慢时内存无限增长 | 设置有依据的容量、背压、积压指标和关闭语义 |
| 创建任务后丢弃 `JoinHandle` | 任务失败、Panic 和泄漏不可见 | 由监督器持有、取消并 Join，统一传播错误 |
| 在正常路径滥用 `unwrap`/`expect` | 可预期输入或依赖故障导致进程崩溃 | 返回 `Option`/`Result`，在边界分类并增加上下文 |
| 把所有实现塞进巨型 `mod.rs` 或 `utils.rs` | 职责、可见性和依赖方向失控 | 按业务能力或单一职责拆分为浅层 Module |
| 每个结构体都创建同名 Trait | 增加无用间接层、泛型和 Mock 成本 | 仅在真实调用边界或多实现需求处定义最小 Trait |
| `unsafe` 无说明或散落在调用方 | 安全不变量无法审查，未定义行为扩散 | 最小化并封装为安全 API，逐块记录不变量并测试边界 |
| 手写 `unsafe impl Send/Sync` 解决编译错误 | 伪造线程安全并引入数据竞争 | 重新设计线程边界；只有证明全部字段和不变量安全时才审查实现 |
| 所有消息处理失败都机械重试 | 永久失败耗尽资源、业务拒绝形成毒循环、结果未知导致副作用重复 | 先分类；只重试瞬时且可安全重试的失败，其他类型按投递契约拒绝、死信、记录丢失、核对或补偿 |
| 未检查解析后的 Feature 图就保留或关闭默认 Feature | 可能增加攻击面，也可能进入上游未充分支持的组合 | 先用 `cargo tree -e features` 或等价方式核实；只有收益、兼容性和受支持组合明确时才调整默认 Feature |
