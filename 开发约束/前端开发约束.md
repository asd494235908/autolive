## 本项目补充约束

- React 管理端统一使用 Ant Design。
- Ant Design 已经提供的组件能力必须直接复用，不得重新实现同类按钮、表单、表格、弹窗、抽屉、分页、通知或反馈组件。
- 不得修改 Ant Design 组件内部样式，不得覆盖 `.ant-*` 选择器或通过 CSS 强行改变组件内部行为。
- 页面布局优先使用 Ant Design 官方组件、Props 和公开配置；官方能力不足时，先说明原因和替代方案，再确认是否增加自定义实现。
- 前端需要复杂能力时优先使用成熟第三方库或项目已有依赖，不得自行编写已有成熟方案可以解决的工具。

# 前端 AI 开发规范

本文用于约束 AI 在前端项目中的分析、设计、实现、验证与交付行为。主要适用于 Vue、React Web 项目；组件设计、TypeScript、状态管理、测试、可访问性和安全规则，可按运行环境复用于桌面壳或跨端项目。

## 1. 使用方式与规则级别

### 1.1 规则级别

- **必须**：交付前不可跳过。无法满足时，必须停止相关改动并说明阻塞、影响与可选方案。
- **应当**：默认遵守。只有仓库事实、兼容要求或任务边界不允许时才可偏离，并说明理由。
- **禁止**：容易造成正确性、安全、性能、可访问性或维护问题的做法，不得以“先跑起来”为由绕过。

### 1.2 冲突处理

规则发生冲突时，必须按以下优先级判断：

1. 用户当前明确要求、验收条件和安全限制。
2. 仓库内适用于当前路径的说明、既有架构和质量门禁。
3. 当前框架、运行时及依赖版本的官方文档。
4. 本规范的通用规则。

不得为了套用本规范而迁移框架、重排任务范围外目录、替换成熟依赖或扩大需求。发现既有实现与本规范不同，应当先确认它是有意约定、历史兼容还是技术债，再决定沿用或局部修复。

### 1.3 适用边界

- Web 项目必须结合 SPA、SSR、SSG、混合渲染、组件库或前端 SDK 等实际形态执行规则。
- 桌面壳只复用适用的组件、类型、状态、异步、测试、可访问性和安全规则，并额外检查 IPC、权限、文件系统及主进程与渲染进程边界。
- 跨端项目只复用适用的工程规则，并额外检查触摸交互、安全区域、平台导航、权限和应用生命周期。
- DOM、Cookie、CORS、Service Worker、SEO、Web Vitals 等浏览器专属规则，禁止机械套用到不存在这些能力的运行时。
- 本规范必须能够独立执行；不得假定开发者还会读取其他本地说明才能理解规则。

## 2. 开发前项目分析

### 2.1 先读项目，再设计改动

开始编码前，AI 必须检查并记录与任务有关的事实：

- 包管理器、锁文件、工作区或单仓结构，以及项目实际支持的运行时版本。
- 框架、元框架、构建工具、TypeScript、路由、状态、请求、样式和测试方案及其版本。
- 应用入口、路由边界、页面布局、组件层次、状态所有者、API 客户端和错误处理入口。
- 渲染模式、服务端与客户端边界、水合要求、浏览器目标及必要的兼容策略。
- 设计系统、现有组件、Design Token、图标、国际化、埋点和可观测性能力。
- 测试命令、格式化、Lint、类型检查、构建、产物目录和交付流程。
- 认证方式、权限模型、数据敏感级别、第三方脚本及浏览器或平台权限。
- 若为桌面壳或跨端项目，检查运行时、进程模型、桥接层、平台差异和生命周期。

禁止仅凭文件名猜测架构。必须阅读相关配置、入口和邻近实现，并用搜索确认某个组件、类型、状态或工具是否已存在。

### 2.2 整理功能边界

编码前必须明确：

- 用户是谁，要完成什么流程，成功、失败、取消和恢复分别是什么结果。
- 页面、功能、组件和 API 的职责边界；哪些属于本次任务，哪些明确不改。
- 数据从哪里来、由谁拥有、何时失效、是否持久化、是否包含敏感信息。
- 加载、空状态、部分成功、校验错误、无权限、离线、超时和重试行为。
- 键盘、焦点、读屏、触摸、缩放和响应式等适用的交互要求。
- 可被自动验证的验收条件，以及无法自动验证时所需的人工检查。

需求有歧义但可通过仓库事实推断时，应当采用最小且可逆的实现并说明假设。会改变产品行为、数据契约、安全模型或技术栈的歧义，必须先向用户确认。

### 2.3 影响面检查

必须搜索所有直接消费者和生产者，包括导入、路由、事件、状态、API 类型、样式选择器、测试、分析事件与公共导出。修改公共组件或契约时，应当列出受影响页面和兼容方式。

禁止只修复可见页面而忽略复用点，也禁止借机清理与任务无关的大范围历史代码。

## 3. 框架、构建工具与依赖选型

### 3.1 选型门禁

引入、替换或升级框架、构建工具、状态库、请求库、UI 库、样式方案、编辑器、图表、测试工具或浏览器依赖前，AI 必须：

1. 检查标准 Web API、当前框架能力和现有依赖能否满足需求。
2. 查阅候选方案当前版本的官方文档、发布说明、迁移说明和已知限制。
3. 核对维护状态、许可证、安全记录、发布节奏和生态稳定性。
4. 核对框架版本、运行时、浏览器、SSR/水合、TypeScript、可访问性和测试兼容性。
5. 评估安装体积、实际打包体积、Tree Shaking、副作用、传递依赖和按需加载能力。
6. 评估学习、迁移、配置、调试、升级和长期维护成本。
7. 比较至少一个“不新增依赖”的方案；没有可行替代时说明原因。
8. 向用户或评审者说明选择、主要代价、版本范围、替代方案和验证证据。

禁止仅凭流行度、旧经验、非官方教程或 AI 记忆决定技术栈。技术信息可能变化时，必须以当前官方资料复核。

### 3.2 选择原则

- 应当优先沿用项目已经稳定使用且能满足需求的能力。
- 成熟第三方库能可靠解决安全敏感或复杂标准问题时，应当优先评估成熟库，避免自行实现净化器、解析器、加密、日期时区或协议客户端。
- 小需求禁止为了“以后可能复用”引入大型状态层、设计系统、插件体系或二次封装。
- 新依赖必须有明确所有者、真实调用点和移除路径；不得只安装不使用。
- 同类能力原则上保持一种主方案。确需并存时，必须说明边界和迁移策略。
- 升级依赖必须阅读破坏性变更并运行受影响验证，禁止无关批量升级。

### 3.3 不固定技术栈

本规范不强制任何具体框架、元框架、路由、状态、请求、CSS 或测试工具。AI 必须根据产品形态、现有仓库、团队能力、运行环境和维护成本选择合适方案，不得为符合个人偏好改造项目。

当新项目尚未确定技术栈时，AI 必须先整理页面交互复杂度、SEO 与渲染要求、数据更新方式、目标浏览器或平台、离线能力、团队经验、部署环境和维护周期，再寻找当前合适的候选框架。输出应当包含候选项、适配理由、主要限制、成本、风险和验证原型；会显著影响项目结构的选择必须得到用户确认后再搭建。

已有项目原则上沿用现有框架。只有当前方案无法满足明确需求，或维护、安全和兼容风险已经被证据证实时，才应提出迁移，并把迁移作为独立决策处理。

## 4. 目录、文件、命名与模块边界

### 4.1 放置位置

- 必须先遵循项目现有目录约定。约定不清时，按功能、路由或业务领域组织，并让依赖方向清晰。
- 只服务一个功能的组件、样式、测试、局部类型和示例，应当在便于共同修改时就近放置。
- 只有被多个真实功能复用、语义稳定且不依赖具体业务流程的代码，才应进入共享层。
- API 生成类型、生成客户端和其他生成产物必须与手写代码隔离，标明生成入口，并禁止手工修改。
- 静态资源应当按所有权放在组件、功能或公共资源位置，避免同一资源出现多份来源不明的副本。

禁止创建没有准入规则的巨型 `utils`、`common`、`shared`、`components` 或 `hooks` 目录。目录名必须表达职责，不能成为暂存区。

### 4.2 模块边界和依赖方向

- 功能模块必须通过明确的公共入口暴露稳定能力，内部文件不得被外部随意深层导入。
- 下层通用模块禁止反向依赖具体页面或业务功能。
- 必须检查循环依赖、隐式初始化顺序和模块级副作用；发现后优先修正所有权或抽取真正中立的契约。
- 公共入口应当只导出消费者需要的内容。禁止为“方便”导出全部内部实现。
- 延迟加载边界应当对应路由、重功能或明确运行边界，不得把每个小组件都拆成异步模块。

### 4.3 文件和命名

- 必须沿用仓库已有的大小写、组件、Hook/Composable、测试、样式和类型命名习惯。
- 名称应表达业务语义和职责；禁止使用 `data`、`info`、`manager`、`helper` 等无法区分用途的宽泛名称。
- 布尔值应当表达状态或能力，事件应当表达已经发生的动作，处理函数应当表达响应关系。
- 一个文件是否拆分由职责、依赖和共同修改频率决定，不以机械行数作为唯一标准。
- 重命名必须同步导入、测试、样式、分析事件和公共 API，并检查大小写敏感文件系统差异。

## 5. TypeScript、数据模型与 API 契约

### 5.1 类型检查

- 新增 TypeScript 代码必须通过项目现有严格检查，不得通过放宽全局配置掩盖错误。
- 新项目应当启用严格模式；现有项目新增更严格选项前，必须评估影响并单独处理迁移范围。
- 项目兼容时，应当评估启用捕获错误为 `unknown`、索引访问包含 `undefined`、精确区分可选属性等严格选项；禁止一次开启大量选项后用断言批量压平错误。
- `any` 只能在无法立即消除的第三方边界局部使用，并注明原因和收窄出口；业务代码禁止传播 `any`。
- `unknown`、捕获到的错误、索引读取和可选数据必须先收窄，再读取属性或执行操作。
- 应当使用可辨识联合、穷尽检查和明确状态模型，避免多个互相矛盾的布尔值组合。
- 非空断言和类型断言只能用于已经由运行时事实保证、但编译器无法推断的局部位置，并说明不变量。

禁止用类型断言把错误“改成正确”，禁止为了通过检查把值断言为更宽或更窄的任意类型。

### 5.2 外部数据与运行时校验

TypeScript 类型在运行时不存在。来自 API、路由、存储、消息、文件、表单、第三方脚本和桌面 IPC 的数据都必须视为不可信输入，并在信任边界进行运行时校验、归一化和错误处理。

复杂或安全敏感的结构应当使用项目已有或成熟的校验方案。简单结构可使用清晰的局部守卫，但禁止自行堆砌一个难以审计的通用校验框架。

### 5.3 模型分层

- API DTO 必须反映传输契约，不应直接承担全部 UI 语义。
- 领域模型应当表达业务规则；表单状态应当表达编辑、脏值和字段错误；视图模型应当表达展示需要。
- 转换应当发生在明确边界并可测试，禁止在多个组件里重复拼装同一结构。
- 日期、金额、枚举、可空字段和标识符必须明确格式及语义，禁止依赖隐式字符串约定。
- 不得重复定义已有契约；确需衍生类型时，应当保持来源和转换关系清楚。

### 5.4 API 契约

- OpenAPI、GraphQL、Protobuf 或等价契约必须明确唯一事实源、生成方式、版本兼容和失败策略。
- 生成客户端的版本必须与服务端契约兼容；生成结果变化应当经过审查，不得直接接受大面积未知差异。
- 资源命名、HTTP 状态、业务错误、分页、排序、筛选和版本策略必须与服务端契约一致；禁止假设所有错误都以成功状态返回。
- 契约变更必须判断向后兼容性、客户端发布节奏和旧版本存活时间；删除或改义字段前必须有迁移安排。
- 公共函数、组件和 Hook/Composable 的输入输出类型必须稳定、最小且可理解。
- 错误不得统一丢成字符串。应当保留可安全使用的错误类别、状态、字段问题和因果信息，同时避免向界面或日志泄露敏感细节。

## 6. 组件设计及 Vue/React 组合逻辑

### 6.1 组件职责与契约

- 组件必须有清晰职责、输入、输出、状态所有者和副作用边界。
- Props、事件、插槽或 `children` 必须表达稳定契约；禁止依赖消费者猜测隐含顺序或内部 DOM。
- 可推导值应当在渲染或计算阶段得到，不要复制成第二份状态。
- 受控与非受控模式必须明确。一个状态不能同时由父级和内部任意写入。
- 列表 Key 必须代表稳定业务身份；禁止在可重排、插入或删除的列表中使用索引或每次生成的新值。
- Ref 和命令式 API 只暴露无法用声明式数据流合理表达的最小能力。

组件拆分应当由职责、复用、变更原因、性能边界或测试边界驱动。禁止只因文件较长就制造无语义的包装组件，也禁止把路由、请求、表单、权限和所有展示塞进一个巨型组件。

### 6.2 Vue 规则

- Props 必须视为只读；子组件通过事件或明确的双向契约请求上层变更。
- 可推导数据应当使用计算能力；Watcher 只用于与响应式状态变化同步外部系统或执行必要副作用。
- Watcher 必须声明准确来源、执行时机和清理逻辑，异步回调必须处理过期结果。
- Vue 3.5 及以上可使用 `onWatcherCleanup`，但必须在同步执行阶段注册；需要兼容更早版本或异步阶段时，应使用 Watcher 回调提供的清理入口，并以项目实际版本为准。
- Composable 应当在组件作用域同步注册生命周期能力；SSR 中访问 DOM 或浏览器 API 的操作必须放在客户端生命周期内。
- 解构响应式对象前必须确认当前 Vue 版本和 API 的响应性语义，禁止因错误解构丢失响应更新。

### 6.3 React 规则

- 渲染必须保持纯净；禁止在渲染阶段发请求、改外部对象、订阅或写共享状态。
- Hook 必须在组件或自定义 Hook 顶层稳定调用，禁止放入条件、循环、事件回调或普通工具函数。
- Effect 只用于把 React 状态与外部系统同步，例如网络、DOM 小部件、订阅或浏览器 API。
- 由 Props/State 可推导的值应当在渲染中计算；由用户动作触发的逻辑应当放在事件处理器，禁止用 Effect 绕一圈触发。
- Effect 依赖必须真实完整，设置与清理必须对称；禁止通过关闭依赖检查隐藏陈旧闭包。
- 组件卸载、依赖变化和开发期重复执行时，Effect 都必须保持可清理、可重入或幂等。

### 6.4 Hook 与 Composable 抽取

只有出现真实复用、复杂状态机、外部资源生命周期或需要隔离测试的逻辑时，才应抽取 Hook/Composable。抽取后仍必须保留清晰输入、输出、错误和清理语义。禁止只为减少组件行数，创建透传参数且难以命名的薄封装。

## 7. 本地状态、服务端状态与数据流

### 7.1 状态分类

新增状态前必须判断它属于：

- 组件局部交互状态，例如展开、临时输入和当前焦点语义。
- URL 状态，例如筛选、分页、排序、选中资源和可分享导航位置。
- 跨组件客户端状态，例如会话外观、受控工作流或真正跨路由的客户端数据。
- 服务端状态，例如查询结果、缓存、失效时间、后台刷新和提交状态。
- 外部运行时状态，例如网络、可见性、媒体查询、桌面窗口或平台生命周期。

应当把状态放在能够拥有它的最近稳定边界。禁止默认把所有状态放入全局 Store，也禁止把服务端缓存复制到多个 Store 后手工同步。

### 7.2 单一事实源与更新

- 同一事实必须只有一个权威来源，其余值应当推导。
- 状态更新必须保持框架要求的不变性或响应性，禁止绕过状态入口直接修改内部对象。
- 多字段必须一起满足不变量时，应当使用单次事务、Reducer、状态机或等价明确机制。
- 大型集合只有在真实更新、查找或一致性需求下才归一化，禁止为形式统一增加映射层。
- 持久化状态必须定义版本、迁移、过期、清除和隐私策略；禁止持久化可重新获取或敏感的数据而无理由。

### 7.3 服务端状态

- 查询必须表示初次加载、后台刷新、成功、空结果、错误、取消和过期状态，避免用单个 `loading` 覆盖所有语义。
- 缓存 Key 必须包含影响结果的全部参数，失效规则必须与业务写入一致。
- 去重、重试、预取和轮询必须有收益依据；禁止所有错误无限自动重试。
- 乐观更新必须定义临时身份、并发冲突、服务端拒绝、回滚和最终一致行为。
- 写请求是否可安全重试取决于幂等性和服务端契约，禁止仅凭 HTTP 方法名称假设安全。

## 8. Effect、异步任务与资源生命周期

### 8.1 副作用边界

Effect 或 Watcher 必须用于同步组件状态与外部系统，而不是替代普通计算、事件处理或状态建模。每个副作用都必须回答：由什么触发、启动什么资源、如何处理错误、何时过期、如何取消、何时清理。

禁止让多个 Effect/Watcher 通过相互修改状态形成隐式流程。多步骤业务流程应当由事件、明确状态机或可追踪的异步函数驱动。

### 8.2 请求、竞态和取消

- 可取消的 Web 请求应当使用 `AbortController` 或所用客户端等价机制，并把取消与真实错误区分。
- 不能取消的操作必须使用请求序号、版本标记或忽略过期结果的机制，保证旧响应不能覆盖新状态。
- 搜索、联想、分页切换和快速路由变化必须测试乱序响应。
- 异步任务完成前组件卸载或运行环境暂停时，禁止继续写入已经失效的状态所有者。
- 超时必须真正终止或隔离底层工作；禁止只在界面显示超时，却让请求继续占用资源并回写。

### 8.3 资源清理

创建以下资源时，必须在依赖变化、卸载、路由离开或平台生命周期结束时执行对称清理：

- DOM、窗口、文档或系统事件监听器。
- 定时器、动画帧、空闲回调、轮询、订阅和消息通道。
- Resize/Intersection/Mutation 等 Observer。
- Worker、对象 URL、媒体流轨道、音视频上下文和设备句柄；对象 URL 使用结束后必须调用等价的撤销能力。
- WebSocket、SSE、流式读取、浏览器或桌面本地数据库连接，以及桌面 IPC 订阅。

防抖和节流函数必须定义取消、刷新和最后一次调用语义。禁止每次渲染都创建无法移除的新监听函数。

### 8.4 长连接

- WebSocket、SSE 和流式响应必须定义连接状态、认证更新、心跳、超时、断线和人工关闭。
- 自动重连必须使用有上限的退避和随机抖动，并在离线、后台或明确退出后暂停。
- 必须处理重复消息、乱序、断点恢复、慢消费者和背压；协议不支持时应当明确丢弃或降级策略。
- 禁止多个组件无意间创建同一连接；共享连接必须有明确所有者和引用生命周期。

## 9. 路由、请求、认证与错误处理

### 9.1 路由与导航

- 路由参数、Query、Hash、History State、Deep Link 和外部跳转目标都必须视为不可信输入。
- 必须校验类型、允许值、长度和格式，并正确编码路径与查询参数。
- 外部跳转必须限制协议和目标；重定向参数必须防止开放重定向。
- 页面必须定义加载、空状态、无权限、资源不存在和未知路由行为。
- 路由切换应当按产品语义处理滚动位置、页面标题、焦点移动、未保存内容和返回行为。
- 客户端路由守卫只控制体验，禁止把它当作服务端授权。

### 9.2 请求与响应

- API 基地址、环境变量和代理行为必须来自项目配置，禁止在业务组件散落硬编码地址。
- 必须了解目标环境的 HTTPS、DNS、反向代理、CDN 和应用基础路径如何影响请求与静态资源；禁止在安全页面引入不安全资源或依赖仅在开发代理下成立的路径。
- 请求层必须区分网络中断、超时、主动取消、认证失败、权限拒绝、业务校验失败、限流和服务端错误。
- 错误展示必须可行动、可恢复且不泄露内部堆栈、令牌、查询或个人数据。
- 重试必须受错误类型、幂等性、次数、退避和用户意图约束；校验失败和权限拒绝通常不应自动重试。
- HTTP 缓存、条件请求和客户端缓存必须明确各自事实源、过期与重新验证规则，禁止叠加多层缓存后无法解释数据为何陈旧。
- 表单提交和关键操作应当防止用户误触导致的重复请求；真正的重复提交与重放防护必须依赖服务端幂等契约，不能只靠禁用按钮。
- 上传必须处理类型、大小、进度、取消、失败和服务端最终校验；客户端校验只改善体验，不构成安全控制。
- 下载必须处理文件名、内容类型、大小、失败和对象 URL 释放，禁止盲目信任响应头或用户提供的文件名。
- 离线能力、缓存和后台同步只能在产品需要时启用，并定义陈旧数据、冲突和版本更新策略。

### 9.3 认证与授权

- Cookie、令牌、刷新机制和持久化位置必须依据威胁模型与服务端契约决定。
- 禁止默认把长期令牌写入 Web Storage；选择任何存储方式都必须分析 XSS、CSRF、跨标签、退出和设备共享风险。
- 刷新令牌流程必须避免多个请求并发刷新、死循环和旧会话覆盖新会话。
- 使用 Cookie 认证的状态变更请求必须与服务端共同实现 CSRF 防护；SameSite 只能按适用条件作为纵深防御，不能无分析地作为唯一措施。
- CORS 是服务端或网关响应策略，前端不能用它替代身份认证、授权或 CSRF 防护。
- 界面隐藏按钮只能改善体验。所有敏感操作必须由服务端重新授权。

### 9.4 错误边界与恢复

- 页面级和功能级错误边界应当隔离可恢复故障，提供重试、返回或联系支持等明确出口。
- 禁止吞掉 Promise 拒绝、只打印控制台或统一显示“发生错误”而丢失可操作信息。
- 全局错误处理只负责兜底、上报和统一策略，不得覆盖局部上下文和恢复能力。
- 用户取消、预期校验失败与程序缺陷必须分开记录，避免制造无意义告警。

## 10. 样式、响应式、资源、可访问性与国际化

### 10.1 样式边界

- 必须沿用项目现有 CSS 组织、作用域、层叠和主题策略。
- 颜色、间距、字号、层级、圆角和动效等稳定设计值应当使用现有 Design Token，禁止散落难以追踪的魔法值。
- 选择器应当保持低耦合，禁止依赖深层 DOM 结构、全局标签覆盖或无约束的高优先级规则。
- 组件必须覆盖默认、悬停、焦点、激活、禁用、加载、错误和只读等适用状态。
- 主题切换必须验证对比度、系统偏好、首次渲染闪烁和持久化行为。

### 10.2 响应式与跨端

- 布局应当由内容和容器能力驱动，并在实际目标尺寸、缩放和文本扩展下验证。
- 禁止只按少数设备宽度截图判断响应式；必须检查极窄、极宽、横竖屏、浏览器缩放和系统字号。
- 移动或跨端界面必须检查触摸目标、手势冲突、安全区域、软键盘和平台返回行为。
- 桌面壳必须检查窗口最小尺寸、缩放、多屏、系统主题和原生菜单或快捷键冲突。

### 10.3 资源

- 图片和视频必须明确尺寸或宽高比，避免布局偏移；按场景选择格式、压缩、响应式资源和加载优先级。
- 有信息含义的图片必须提供等价替代文本；装饰图应当从辅助技术中隐藏。
- 图标按钮必须有可访问名称，不能只依赖图形或颜色表达含义。
- 字体必须检查许可、字符覆盖、加载失败、回退指标和对首屏性能的影响。
- 第三方资源必须定义失败、超时、隐私和撤回策略，禁止让非核心资源阻断主要流程。

### 10.4 可访问性

- 必须优先使用语义化 HTML 和原生控件；ARIA 只补足缺失语义，不能替代原生行为。
- 所有交互必须可用键盘完成，并具备清晰可见的焦点；禁止只响应鼠标事件。
- 焦点顺序必须符合视觉和任务顺序。打开模态框时焦点进入框内并限制在有效范围，关闭后返回触发点或合理后继位置。
- 表单控件必须有可感知标签、说明和错误关联；动态状态必须在需要时通过合适的实时区域播报。
- 必须检查颜色对比、非颜色提示、页面缩放、文本换行、焦点不被遮挡、触摸目标尺寸和减少动画偏好。
- 拖拽、多点手势、验证码或认知测试必须提供适用的替代操作；认证流程不得仅依赖难以完成的认知任务。
- 自动化检查不能代替键盘、焦点、缩放和必要的读屏人工验证。

### 10.5 国际化

- 用户可见文本不得无计划地散落硬编码；是否接入国际化由项目范围决定，但文本必须易于提取和替换。
- 必须使用适合区域的日期、数字、货币、复数和相对时间格式，并明确时区来源。
- 布局必须容纳文本扩展，禁止用固定宽高截断关键信息。
- 应当检查 RTL、混合方向文本、姓名和地址差异；禁止拼接句子假设所有语言语序一致。
- ID、代码、品牌名和用户数据应当与可翻译文本区分，避免误翻译。

## 11. 渲染性能、浏览器行为与可观测性

### 11.1 先测量后优化

- 性能优化前必须用浏览器性能工具、框架 Profiler、网络瀑布、Bundle 分析或真实用户数据定位瓶颈。
- Web 项目应当按场景关注 LCP、INP、CLS；阈值和采集方式可能变化，必须以当前官方定义和产品目标为准。
- 实验室数据应当用于复现和对比，真实用户数据用于判断实际设备、网络和交互；不得用单次本机跑分代表用户体验。
- 性能预算应当覆盖关键资源、脚本体积、长任务、首屏和关键交互，并在有业务依据时纳入门禁。

### 11.2 渲染与资源性能

- 必须检查无意义重复渲染、昂贵计算、布局抖动、同步大任务、重复请求和内存增长。
- Memo、缓存、虚拟化、预加载和懒加载必须有测量证据；禁止把它们作为默认装饰。
- 代码分割应当放在路由、重功能或低频能力等有意义边界，并处理加载、失败和重试界面。
- 图片、字体和第三方脚本应当按关键程度加载；禁止把非关键资源放在首屏阻塞路径。
- 大列表只有在数据规模和交互性能确有问题时才虚拟化，并验证键盘、读屏、滚动定位和动态高度。

### 11.3 SSR、水合与浏览器边界

- SSR/SSG 项目必须保证服务端首屏与客户端首次渲染可确定一致，避免依赖随机值、本地时区或仅浏览器存在的状态直接生成不同结构。
- DOM、窗口、存储、媒体查询和浏览器权限 API 必须只在客户端可用阶段访问，并处理能力不存在或被拒绝。
- 兼容目标、Polyfill 和语法转换必须来自项目支持矩阵，禁止无依据支持所有旧浏览器。
- Service Worker、离线缓存和更新提示必须有版本、回滚、失效和数据一致策略；不需要离线能力时禁止引入。

### 11.4 可观测性

- 错误、性能和关键业务事件必须包含足够定位信息，但禁止记录密码、令牌、完整请求体、个人数据或敏感 URL 参数。
- 应当记录经过脱敏的发布版本、运行环境、页面或功能边界和关联请求标识，使前端错误能够与服务端日志和链路追踪关联。
- Source Map 的生成、上传和访问必须与部署环境及权限匹配，禁止把内部源码或密钥暴露在公开产物。
- 事件命名和属性必须稳定、有所有者、有数据字典，并遵守最小收集、同意和保留期限。
- 上报失败不得阻断主流程；采样、限流和去重必须防止错误风暴。

## 12. 前端安全、隐私和第三方代码

### 12.1 内容与 DOM 安全

- 来自用户、API、URL、存储、消息和第三方的内容必须按输出上下文处理。
- 应当使用安全的文本和属性 API。使用 `innerHTML`、`dangerouslySetInnerHTML`、`v-html` 或等价 HTML 注入能力前，必须证明业务必要，并使用经过维护、配置正确的成熟净化方案。
- 禁止自制通用 HTML 净化器，禁止净化后再用字符串拼接把不可信内容插回危险上下文。
- 动态 URL 必须限制允许的协议、主机和用途；禁止允许 `javascript:`、危险数据 URL 或未经校验的跳转目标。
- 禁止使用 `eval`、动态代码构造或把不可信数据解释为模板、选择器、脚本或样式。

### 12.2 页面与通信安全

- 打开新窗口时必须通过 `noopener` 或等价隔离防止反向控制 opener，并按隐私策略决定是否使用 `noreferrer`、是否发送 Referrer。
- `postMessage` 必须指定精确目标 Origin；接收方必须校验来源、Origin 和消息结构，禁止使用通配符处理敏感消息。
- 点击劫持、CSP、Trusted Types 和框架嵌入策略必须由服务端头、页面策略与实际兼容性共同实施。
- 客户端禁止包含 Secret。构建变量、静态资源、日志和 Source Map 都应当视为可能被用户读取。
- 路径、文件名和上传内容必须在服务端重新校验；客户端过滤不能替代服务端安全控制。

### 12.3 第三方脚本与供应链

- 第三方脚本拥有与页面代码相近的读取和执行能力，引入前必须评估数据访问、维护者、加载来源、更新方式和故障影响。
- 固定外部静态资源时，应当按兼容性采用 SRI；应当通过 CSP、沙箱 iframe、权限策略或隔离域限制第三方能力。
- 标签管理器、客服、分析、广告和实验脚本必须有所有者、同意机制、数据清单、禁用开关和故障降级。
- 依赖必须锁定可复现版本，审查安装脚本、传递依赖和安全告警；禁止自动合并未经验证的高风险升级。
- 发现漏洞时必须判断可达性、影响版本和缓解措施，不能只看告警数量，也不能无依据忽略。

### 12.4 隐私

- 数据收集、缓存、日志、埋点和持久化必须遵循最小必要、目的限定、明确同意、访问控制和保留期限。
- 必须提供适用的退出、删除或撤回机制，并确保关闭追踪后不再继续发送。
- 敏感数据在错误信息、截图、录屏、分析事件和调试工具中必须脱敏。
- 禁止用浏览器指纹、隐蔽标识或跨域关联绕过用户选择。

### 12.5 桌面壳与跨端安全

- 渲染层必须按不可信界面处理，不得默认获得进程、Shell、文件系统或系统密钥访问能力。
- IPC 必须使用允许列表、明确命令、输入校验、权限检查和最小返回值；禁止暴露任意执行或任意文件路径接口。
- 外部链接、协议唤起、自动更新、剪贴板、通知和文件选择必须校验来源并遵循平台权限。
- 跨端桥接和插件必须按平台逐项审查，浏览器中的安全假设不得直接替代原生侧授权。

## 13. 测试、构建与质量门禁

### 13.1 测试策略

- 测试必须按风险分层：纯逻辑使用单元测试，组件行为使用组件测试，跨模块流程使用集成测试，关键用户旅程使用少量 E2E。
- 测试应当验证用户可观察行为和公共契约，禁止过度断言内部状态、私有方法或具体 DOM 层次。
- 快照只能辅助审查稳定结构，禁止用大量快照替代行为断言。
- 必须覆盖适用的成功、加载、空状态、校验失败、网络失败、无权限、取消、竞态、重试和恢复路径。
- 网络应当在边界模拟，内部实现尽量使用真实协作；禁止把所有依赖都 Mock 到测试失去意义。
- 异步测试必须等待可观察条件或可控时钟，禁止依赖任意睡眠时间和不稳定执行顺序。

### 13.2 交互与兼容验证

- 可访问性必须结合自动扫描与人工键盘、焦点、缩放和必要的读屏验证。
- 浏览器和设备矩阵必须来自项目支持范围；关键流程应当在代表性环境验证。
- 视觉回归只在布局稳定且维护成本合理时使用，并设置清晰基线审查流程。
- 桌面壳或跨端项目必须验证窗口/平台生命周期、权限拒绝、离线、恢复、升级和桥接失败等适用场景。

### 13.3 质量命令

交付前必须根据仓库现状执行：

1. 格式化或格式检查。
2. Lint。
3. TypeScript 类型检查。
4. 受影响测试，必要时再运行完整测试。
5. 本地生产构建或项目允许的等价本地验证。

禁止为了验证把代码临时上传到服务器构建，也禁止擅自触发远程构建。若本地环境无法执行，必须报告未验证项、原因和风险，不能声称已经通过。

### 13.4 清理门禁

- 必须检查并删除本次改动产生或暴露的未使用组件、函数、类型、导入、导出、样式、资源、依赖和配置。
- 必须删除调试日志、临时开关、假数据、无效注释和已被替代的重复实现。
- 删除前必须搜索动态导入、字符串引用、模板引用、路由注册和插件注册，避免误删隐式入口。
- 禁止保留“以后可能用”的抽象或兼容层；真实迁移需要时，应当标明所有者和移除条件。

## 14. AI 开发流程与交付检查清单

### 14.1 标准执行流程

AI 必须按顺序执行：

1. 阅读需求、仓库约束、依赖、配置、入口和邻近实现。
2. 整理功能边界、用户流程、状态、错误和验收条件。
3. 搜索已有组件、Hook/Composable、工具、Token、契约和测试能力。
4. 确定文件放置、职责、依赖方向、公共 API 和运行环境边界。
5. 需要选型或升级时，查询当前官方资料并完成选型门禁。
6. 先确定可验证行为和测试层级，再编写最小实现。
7. 遵循现有架构完成改动，不顺手扩大重构范围。
8. 检查状态所有权、Effect/Watcher、竞态、取消、清理和错误恢复。
9. 检查响应式、可访问性、性能、安全、隐私和平台差异。
10. 删除未使用、重复、临时和与任务无关的内容。
11. 执行项目规定的本地格式、Lint、类型、测试和构建验证。
12. 汇报改动、验证证据、未验证项、兼容影响和剩余风险。

### 14.2 开发前清单

- [ ] 已确认框架、版本、渲染模式、运行环境和浏览器或平台目标。
- [ ] 已明确任务范围、非目标、用户流程和可验证验收条件。
- [ ] 已找到现有相似实现、可复用组件和数据契约。
- [ ] 已确定文件位置、模块边界、状态所有者和错误边界。
- [ ] 新增或升级依赖已通过官方资料、兼容性、安全和成本评估。
- [ ] 已识别敏感数据、不可信输入、权限和第三方代码。

### 14.3 实现中清单

- [ ] 类型没有掩盖运行时不可信输入，错误和空值均被明确处理。
- [ ] 组件契约、Key、事件、Ref、受控/非受控语义稳定。
- [ ] 没有重复状态、滥用全局状态或把服务端缓存多处复制。
- [ ] Effect/Watcher 只处理必要副作用，依赖、竞态、取消和清理完整。
- [ ] 路由、网络、认证、上传下载和长连接包含失败与恢复路径。
- [ ] 键盘、焦点、语义、对比、缩放和响应式按场景实现。
- [ ] 没有危险 HTML、危险 URL、泄露 Secret 或越权客户端假设。
- [ ] 桌面壳或跨端代码明确区分浏览器与平台能力。

### 14.4 交付前清单

- [ ] 成功、加载、空、错误、权限、取消、竞态和恢复路径已验证。
- [ ] 格式化、Lint、类型检查、受影响测试和适用本地构建已执行。
- [ ] 可访问性自动检查与必要人工检查已完成。
- [ ] 性能改动有前后数据，未凭感觉增加缓存、Memo 或懒加载。
- [ ] 未使用代码、样式、资源、依赖、导出、配置和调试内容已删除。
- [ ] API、分析事件、国际化、配置和交付说明已按需同步。
- [ ] 已记录实际执行命令、结果、未验证项和剩余风险。

## 15. 常见错误做法

| 错误做法 | 主要风险 | 正确做法 |
| --- | --- | --- |
| 未读项目就套固定目录和技术栈 | 破坏既有边界，增加迁移成本 | 先分析仓库，再按现状选择最小改动 |
| 为小需求引入大型依赖或抽象层 | 包体、维护和升级成本失控 | 先检查平台、框架和现有依赖能力 |
| 把所有文件放进通用目录 | 所有权不清，形成循环依赖 | 按功能或领域就近放置，严格共享准入 |
| 用 `any`、断言或关闭规则消除类型错误 | 把运行时缺陷藏到类型系统之后 | 收窄输入、修正模型并保留边界校验 |
| 把 API DTO 直接当表单和视图模型 | 传输变化扩散到整个界面 | 在明确边界转换不同语义模型 |
| Props 复制进状态并双向修改 | 出现两个事实源和陈旧数据 | 明确状态所有者，其余值按需推导 |
| React 用 Effect 计算派生值或处理点击 | 多一次渲染，流程隐晦且易循环 | 渲染时计算，用户动作放事件处理器 |
| Vue 用 Watcher 串联普通业务计算 | 依赖隐蔽，清理和顺序难以控制 | 使用计算值、事件或明确流程函数 |
| 忽略请求乱序、取消和卸载 | 旧响应覆盖新状态，产生泄漏 | 取消任务或拒绝过期结果并对称清理 |
| 所有数据都塞进全局 Store | 所有权丢失，缓存难以失效 | 区分局部、URL、客户端和服务端状态 |
| 所有错误都自动重试 | 重复写入、放大故障、困扰用户 | 按错误类别、幂等性和次数决定重试 |
| 用路由守卫或隐藏按钮做授权 | 攻击者可绕过客户端 | 服务端执行最终认证和授权 |
| 长期令牌默认写入 Web Storage | XSS 后令牌易被读取并长期滥用 | 基于威胁模型与服务端契约选择方案 |
| 直接渲染 HTML 或自行写净化器 | DOM XSS 和绕过风险 | 使用文本 API；必要时采用成熟净化方案 |
| 用 ARIA 重做已有原生控件 | 键盘、焦点和语义容易缺失 | 优先语义 HTML 和原生行为 |
| 只做自动可访问性扫描 | 漏掉键盘、焦点和读屏流程问题 | 自动检查结合必要人工验证 |
| 未测量就到处加 Memo、缓存和懒加载 | 复杂度上升且可能更慢 | 用真实证据定位瓶颈后局部优化 |
| SSR 首屏读取浏览器状态 | 水合不一致和界面闪烁 | 保持首次渲染确定，客户端阶段再同步 |
| 第三方脚本直接获得页面全部能力 | 数据泄露、供应链和可用性风险 | 最小化、隔离、限制来源并提供关闭机制 |
| 测试只断言内部实现或大量快照 | 重构脆弱，不能证明用户行为 | 按风险测试公共契约和关键流程 |
| 为验证临时上传服务器构建 | 扩大数据和代码暴露范围 | 使用项目允许的本地验证并报告缺口 |
| 保留未使用代码和“未来扩展点” | 增加阅读、维护和攻击面 | 搜索确认后删除，真实需要时再实现 |
