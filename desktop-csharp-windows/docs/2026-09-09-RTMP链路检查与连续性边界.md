# RTMP 链路检查与连续性边界

本记录对应 2026-09-09 音画不同步、卡顿与视频切换排查。仅检查当前 C# Windows 链路；不修改 Rust、服务器、推流协议或媒体资源。使用 ponytail 原则：有真实根因才改参数，不因怀疑增加缓存、队列或重试。

## 当前链路与已确认问题

`MainWindow.StartRtmpCoreAsync` 校验轨道和运行资源，探测 H.264 编码器，再捕获活动最终 PCM 的首帧源位置；`WindowsRtmpAudioSession` 接入共享总线，`WindowsRtmpFinalPcmPump` 串行写入受管 FFmpeg 的 stdin。视频由同一 FFmpeg 从源文件独立读取，通过 `-ss` 对齐声音起点、`-re` 限速和 `-stream_loop -1` 循环。声音只编码最终 PCM，不重新取源音轨。总线保留本机/RTMP 独立读指针，候选边界和起点沿用 9 月 7 日修复。

本机 mpv 与 RTMP 不是同一个画面输出：本机可动态执行 GPU83，C# RTMP 当前只接入 CPU4 启动快照。主窗口明确选择 CPU4，命令构造器拒绝 GPU83；播放中参数周期不会自动修改已运行的 RTMP 滤镜。不得把本机 GPU83 真实像素验收用于证明推流 GPU83 已生效。

排查时确认，手动切换与 EOF 自动切换都会先调用 `StopRtmpForMediaMutationAsync`，等待旧发布退出并清空活动配置；原调用链未恢复新源发布。这既让媒体切换等待 RTMP 清理，也让直播停止。主线程负责将手动/自动换源成功后的续推接回既有启动入口；其代码与验收以本次主报告为准。

即使续推接通，当前命令仍固定绑定单个文件，切源需要结束旧 FFmpeg 并重新建立发布连接。正常关闭最长占 1.5 秒，总收尾预算 2 秒，再加设备/编码器启动和远端重新缓冲，不能承诺 RTMP 跨文件零断流、零停帧。本机保留旧画面的机制只覆盖预览 HWND。跨文件持续 RTMP 需要改变当前固定源发布架构，不能通过增大缓冲或重复重连冒充完成。

## 最小真实对照

使用仓库已有 FFmpeg `n8.1.2-44`，不发送网络数据、不访问用户媒体：

- 生成 4 秒、2fps 的 64×64 `testsrc2`/FFV1 素材，执行 `-stream_loop 1 -ss 2 -f framemd5`，输出 12 帧。首轮为源后 2 秒，第二轮完整回到源零点，排除“每轮都重复从非零起点开始”的假设，没有修改循环参数。
- 以 48kHz 双声道 float PCM，每次 960 帧、间隔 20ms，比较默认输入探测与 `-probesize 32 -analyzeduration 0`。首次 progress 分别为 580ms 和 552ms，均正常退出 0。该结果包含 FFmpeg progress 默认上报周期，不是首个可听采样延迟；不足以证明默认探测是故障根因，因此未新增探测参数。
- 上述探针位于本地忽略目录 `artifacts/repair-20260907/probe-rtmp-pcm-startup.ps1` 和 `rtmp-loop-probe.mkv`，只用于本次诊断。
