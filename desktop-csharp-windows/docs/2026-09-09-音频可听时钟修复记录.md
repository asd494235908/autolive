# 音频可听时钟修复记录

范围：C# Windows 主声音 → FFmpeg PCM → 最终 PCM 总线 → 主轨/插话混音 → PortAudio；保持既有 N/N+1、单输出流和 RTMP 共享分支。

确认的缺陷：输出先于解码启动，欠载补零计入硬件写帧，可听时钟因此提前；本地独立插话同样不能代表主媒体推进。输出快照保留硬件写帧诊断，媒体时钟使用实际主源帧；初始化与候选重锚使用相同坐标。可听快照同时公开当前已生效音轨速率，供视频同步消费。

声音周期按可听位置计算到目标的剩余量时，已经排入 DAC 的帧必须扣除，旧实现反而加上延迟，使切换晚了两倍输出延迟；现按剩余主源输出帧提交。

没有新增依赖、缓存、队列或重试。保留设备错误、取消、受管退出和缓冲上限。

首轨解码原先保留 `-re`，N+1 才移除该输入限速；现在首轨在已有最终 PCM 容量背压时复用同一移除入口，使解码能够预填有界缓冲，避免大于 1 倍速时输入供给低于输出消费。没有最终 PCM 背压的旧独立环缓循环仍保留 `-re`，避免快读造成丢帧。

联合实机验证仍发现首次启动 video=433ms、audio=133ms：启动原先只等待 `DecodedFrames>0`，解码写入环缓不等于设备消费。启动现使用原有 3 秒预算等待 `MediaFramesWritten` 超过启动锚点，保留已观测的首帧快照直接返回；不等待 DAC timeInfo，短音频即使已经自然完成，累计主源输出帧仍可证明它真正进入设备回调。真实声音夹具新增启动返回时主源帧必须大于零的断言；此轮未自行构建，由主任务联合验证。

验证：启动与后续欠载红测确认预期 2000ms、原实现 2100ms（`artifacts/repair-20260909/audio-clock-red.trx`）；首轮 Windows 可听时钟、声音控制器与输出流定向 31/31（`audio-clock-green.trx`）。此后追加独立插话、DAC 调度和首轨限速回归，最终集成结果由主任务统一记录。

本地命令：`.tools/dotnet/dotnet.exe test tests/GpAutoLive.Windows.Tests -c Release -p:Platform=x64 --no-restore --filter 'FullyQualifiedName~WindowsAudibleAudioClockTests|FullyQualifiedName~WindowsAudioPlaybackControllerTests|FullyQualifiedName~WindowsPortAudioOutputStreamTests' --logger 'trx;LogFileName=audio-clock-green.trx' --results-directory artifacts/repair-20260909`。修改文件 `git diff --check` 无空白错误，仅 CRLF 提示。

正在进行消融实验。完成检查后保留的新增状态只有主轨实际输出计数；它用于排除独立插话，不能用硬件总帧替代。调度复用现有 PCM 容量背压，没有新增队列、重试、缓存或依赖，没有删除无关代码。

该定向单元测试不代表真实声卡听感、逐帧同步、长稳和跨设备验收；未运行全量测试、完整应用构建、容器检查、页面点击或外部模型调用，本分支无外部模型业务。实际业务结果由主任务联合媒体验证报告。

## PCM 环缓临界区批量复制（2026-09-10）

真实联合播放仍记录到以 256 帧为单位的累计欠载。只读检查确认，实时读取拿不到现有锁时会返回 `ConsumerBusy`，而生产/消费此前在锁内逐帧复制并逐帧取模。该机制是候选原因，尚不能单凭欠载总数确认所有缺帧都来自锁碰撞。

本次只将 `TryWriteLocked`、`TryReadLocked` 的逐帧循环替换为至多两段 `Span.CopyTo` 与一次游标取模，与已有 `CopyPendingTo` 的环绕复制方式一致。容量、覆盖最旧帧、丢帧计数、关闭、连续读取校验、现有锁与实时 `TryEnter` 非阻塞语义均不变；不新增缓冲层、依赖、回调等待或重试。

先保存旧实现并执行独立纯 CPU 基线，再修改产品并运行同一对照：`.NET 10.0.11`、`DOTNET_TieredCompilation=0`、48000 帧/双声道环缓，每块写入 4096 帧后以 256 帧读取 16 次，预热 3000 块、七轮各 20000 块。每次读取核对交错样本顺序，每轮确认余量与丢帧为零。每块写读总耗时中位数从 **45.139645μs** 降至 **1.460370μs**（约 31 倍）；这是单线程纯复制/锁入口开销，不是实时回调成功率或声音连续性结论。

证据保留在 `artifacts/pcm-copy-benchmark`：`baseline.log`、`optimized.log`、冻结的 `AudioPcmRingBuffer.baseline.cs.txt` 与无依赖控制台源。旧源 SHA-256 为 `9C4EE94E497FF3D9583E7087D3568516FA813D00FDB6269FE16C9B2B19A01AE1`。实际命令两次均为 `.tools/dotnet/dotnet.exe run --project artifacts/pcm-copy-benchmark/pcm-copy-benchmark.csproj -c Release -- <baseline或optimized>`，输出退出码均为 0；该独立目录未触碰产品 bin/obj。

现有环绕顺序、超容量覆盖、关闭与实时读写测试继续复用；新增不足目标时保留尾部、清空后读取及超容量环绕写入同时统计旧帧/输入前缀的两个边界回归。产品目标过滤为 `AudioPcmRingBufferTests|AudioPcmMixerTests|AudioPcmTrackSwitchOutputSourceTests|FinalPcmBusTests|FinalPcmBusTrackSwitchTests`，由主任务统一执行并复验真实播放欠载；本子任务未运行播放器。

正在进行消融实验。仅移除重复的逐帧复制/取模工作；必要环绕、容量、丢帧、实时非阻塞和生命周期边界完整保留。没有将性能基线改善表述为真实声音卡顿已解决。
