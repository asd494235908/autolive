## 用户确认的边界

- 2026-09-09 用户要求虚拟摄像头输出跟随源视频分辨率，不随最终效果窗口的缩放变化，也不固定为 1280×720。

## DirectShow 注册 0x8000ffff 根因（2026-09-10）

用户按双架构显式注册执行后，x64 regsvr32 报 DllRegisterServer 失败 `0x8000ffff`。本机普通权限的无注册表写入探针确认：regsvr32 调用导出函数时 COM 为 MAINSTA（type=3），上游强制 `CoInitializeEx(MTA)` 返回 `0x80010106 / RPC_E_CHANGED_MODE`。原 registerFilter 退出错误分支却仍 CoUninitialize，破坏调用方计数；createDevice 把失败统一转为 E_UNEXPECTED 并回滚。证据在 `artifacts/vcam-validation/registration-apartment/result.txt`。不再以 MF 路径推测解释该故障。

固定版本补丁 `0003-directshow-com-apartment.patch` 让注册/注销兼容已有 STA，仅本次初始化成功时平衡释放，并修复 RegisterFilter HRESULT 假成功和返回 moniker 泄漏。两个本地构建入口都沿用既有补丁应用/反向校验机制，不新增注册宿主。

## DirectShow 输出 pin 识别修复（2026-09-10）

双架构注册成功后，FFmpeg 能列出 `GpAutoLive Camera` 但标为 `(none)`，取流报 `Could not find output pin from video capture device`。无写入 COM 探针实际确认：绑定与 EnumPins 成功，存在一个 OUTPUT pin 和一个 720p YUY2 视频类型；但 IKsPropertySet 返回 E_NOINTERFACE。证据为 `artifacts/vcam-validation/pin-probe/result.txt`。因此此错误不能解释为未创建 pin 或未配置格式。

本地 FFmpeg 固定提交 [7c533d0f86 的 dshow.c](https://raw.githubusercontent.com/FFmpeg/FFmpeg/7c533d0f86/libavdevice/dshow.c) 要求 IKsPropertySet 读取 AMPROPERTY_PIN_CATEGORY 为 PIN_CATEGORY_CAPTURE，否则跳过该 pin。按 [Microsoft Pin Property Set](https://learn.microsoft.com/en-us/previous-versions/ms787483%28v%3Dvs.85%29) 的只读类别契约，新增固定版本补丁 `0004-directshow-capture-pin-category.patch`，仅给既有 Pin 加 IKsPropertySet：Get 返回 capture 类别并支持长度查询；短缓冲拒绝且不写；QuerySupported 仅 GET；Set 拒绝；未知属性集/ID 和空参数明确报错。两构建入口和源码清单同步。

最小回归命令 `test-directshow-pin-category.ps1 -SourceDirectory <staged-upstream-root> -OutputDirectory <local-test-output>`：旧源码先因缺失接口失败；补丁后实际三个方法的成功、长度查询、短缓冲保护、未知属性和只读边界通过。补丁正向/反向 check 通过。此子任务没有修改已安装二进制或执行注册；真实接收画面仍需主线程继续，不能把接口边界回归当作真实业务结果。
