状态：功能链路与计划独立评审通过，A～E 已实施并完成集成复核。验收结果与未完成门禁见 [2026-09-08 修复验收记录](./2026-09-08-CSharp媒体链路修复验收记录.md)。用户已明确授权“计划评审完毕后开始实施修复”，未增加重复确认步骤。

## 功能链路与边界

1. 播放池/播放命令串行入口 → mpv 视频会话与 FFmpeg 声音解码 → FinalPcmBus → PortAudio 可听输出；声音 N/N+1 候选共享输出流，视频处理仍使用既有 GPU83/CPU4/Original。
2. 插话文件 → 同一受管 PCM 解码器 → overlay 环缓 → 本地/RTMP 混音。麦克风 → PortAudio 输入 → RMS 迟滞门控 → PCM bridge → overlay 与音频优先级。
3. RTMP 启动 → 编码器探测 → 首 PCM 源位置绑定 → 直接读取源的视频 FFmpeg 与最终 PCM stdin → 用户指定 RTMP；普通声音、插话和麦克风继续复用最终总线。
4. 窗口关闭/停止/换源 → 取消新工作 → Join 旧任务 → 停止 native/子进程 → 释放 token/句柄。超时不得清空仍运行的 owner 或回报成功。

只改 C# 桌面相关源码、测试和文档。不改 Rust/Go、UI 外观、登录行为、服务器配置，不使用 worktree，不新增媒体协议或编解码实现。既有脏改动保留。未使用字段若属于缺失功能（如麦克风停止阈值），恢复功能而非删除；不开展无关代码清理。

C 的时间轴变化处理：暂停/seek 必须停止旧发布，seek 同时对齐本地声音；恢复/重连使用新锚点。正常同速声音周期保持推流，不靠每周期停流掩盖同步错误。当前 WPF 自动声音参数实际始终 PlaybackSpeed=1，PitchShift 经反向 atempo 保持时长，因此本轮不引入动态视频变速框架；底层非1倍速音画组合必须明确拒绝不匹配，不能假装同步。启动阶段源/候选变动或环缓溢出应失败并释放 RTMP 接入，不影响本地正常播放。读缓冲复制必须有固定上限与统一锁序，不消费或修改本地帧；候选内绝对帧计数复用既有切换器，禁止新增无界补偿队列。

E 的不可越过边界：单进程无法安全强杀死锁驱动线程。仅给 Task 加超时后遗弃任务、提前 FreeLibrary、并发再开流均不接受。受管预算/可观察性/所有权本轮修复；真正驱动硬卡死的强制回收需要经独立方案和实机门禁验证的进程隔离，不能在本轮冒称完成。若最小原生边界实现无法满足所有权测试，保留失败状态并在交付中明确未闭环项。

## 实施顺序与文件归属

先完成本计划独立评审，关闭阻断意见，再并行 A、C、D/E；主线程实施 B。A 只改解码器和其测试；C 拥有 RTMP/总线/音频控制器相关文件；D/E 拥有麦克风门控/控制器及 PortAudio。MainWindow.Playback.cs 由主线程协调编辑，避免与 C 的 seek/pause 修改冲突。插话 CTS 在其他调用方的同类竞态由文件所有者同步修复。

现有调用边界能够承担职责时不加通用框架。确需复用 Input/Output 的 native 在途操作所有权，只增加一个内部专用 owner，使用 .NET Task/同步原语，无新依赖。窗口生命周期拆到专用 partial，避免继续扩大 MainWindow.xaml.cs。项目文档由主线程统一写入。

## 计划评审清单

- 是否只修表面异常、遗漏普通音频/候选/插话/RTMP 对同一解码器的调用？
- 是否准确判断超时的 API 返回语义，仍能取消并 Join，没有假成功和资源遗弃？
- UI 关闭是否保持 Dispatcher 可运行，既有异步任务是否有明确结束路径？
- RTMP 首帧位置是否来自生产 PCM 的事实，能否处理缓冲领先、候选身份、速率和独立解码？
- 麦克风迟滞是否完整，原生预算是否保留 stream/DLL/delegate 所有权？
- 是否新增不必要的抽象/依赖/队列，或者通过停止正常黄金路径来“修复”？
- 测试是否先验证旧代码失败、再验证修复，是否区分自动化、实机与未验收项？

## 2026-09-08 追加评审：RTMP 正常 unpublish

主线程及 D 条件通过：仅本地 FFmpeg 停止协议调整，不修改 ZLMediaKit。纯视频保持控制 stdin 并发送 q；纯音频最终 PCM EOF；音视频增加 -shortest 随最终 PCM EOF 结束。控制 stdin 不属于 PCM。停止拒绝新写入，写锁后再次核对状态和 stdin identity；取锁超时不关闭在途输入，先 Kill/Join 后取锁。所有阶段共享 2 秒 Stopwatch 截止期，正常退出预算 1.5 秒；stderr 在正常结束期间持续 drain，Join 前不得清除资源所有者。Exited/Start/Stop 共用串行清理，启动失败复用停止路径。

红测：Windows 正常 q/EOF、排队写入、未 Join 的 stderr 所有者保留共 4 项失败；写锁超时强杀保留资源用例通过。命令三轨道用例中纯视频和音视频 2 项失败、纯音频通过。真实 FFmpeg 源循环 EOF 与中间 700ms 空隙由 D 独立验证；真实服务端快速复用仍由主线程验收。实现不新增用户配置、依赖或服务端绕行。

### MF 与 shortest 缓冲追加验证

本地真实源、MF/AAC、固定 1024 帧 PCM 验证发现：裸 `-shortest` 在小分片实时输入时卡住（8192 帧后写入受阻、frame=0）；去掉 shortest 可持续但 EOF 后 10 秒仍不退出。只为音视频增加固定 `-shortest_buf_duration 0.1` 后连续输入 EOF84ms、700ms 中间空隙保持存活且 EOF31ms，均 exit0；无空隙输出进度终点5.376s与已写PCM5.376s一致。该参数是当前 MF 真实故障所需的 FFmpeg 内置缓冲边界，不新增队列或用户配置；仅视频与仅音频不添加。真实服务端反向切轨及音画内容验收由主线程继续执行。

### 退出预算重分配评审（主线程/D 通过）

真实同版本 AV 曾正常657ms完成，也在768ms时因750ms正常退出窗口结束而被强杀，视频/音频均正常。根据这组实际结果，将正常退出窗口改为固定1.5秒，仍使用现有2秒总期限；正常请求、取写锁及等待均计入该窗口，强杀/进程与读取Join共享剩余约0.5秒。剩余期限不足时仍返回失败并保留所有者，不增加总停止上限、不新增用户配置。局部同源 MF/FLV 自然退出分布与后续真实服务器两轮三轨道验证分别记录，不能把本地文件封装结果等同网络发布验收。

### 2026-09-08 追加评审：以原生进程句柄确认退出

两轮全 C# 回归分别出现 decoder 脚本占用、mpv.exe 删除拒绝。只读探针引用当前 Release 产品 DLL，独立保留子进程句柄；4 次中 3 次在 Decode 返回 Cancelled 后观测到 HasExited=true 但 WaitForExit(0)=false，其中一次同时复现脚本共享占用（0x80070020）。随后真实句柄等待成功。红证据为 `artifacts/repair-20260907/exit-handle-probe-red.log`，不是通过增加删除重试隐藏失败。

主线程评审通过：Decoder 最终释放前增加真实进程句柄检查；尚未触发时由 Decode 持续 await 受管 Task.Run 内的 WaitForExit，保留 Process、Job、CTS 和读取任务所有权，外层 Dispose 的原 2 秒超时仍显式失败。mpv 的资源释放判定使用 WaitForExit(0)，有界停止使用内部 2 秒的 WaitForExit 并检查 bool；不得仅以 HasExited/ExitCode 或 WaitForExitAsync 的快速返回确认操作系统已释放句柄。此变更只调整退出确认，不增加通用进程框架、用户配置或测试睡眠。

验收增加独立 observer 句柄断言，修复后运行同探针 20 次及受影响 decoder/mpv 回归。原 25,000 行 stderr 夹具的超时暂不修改，先在正确退出语义下复核是否仍存在负载问题。

局部修复验证：`dotnet test ... --filter WindowsFfmpegPcmDecoder|WindowsMpvProcessHostTests|WindowsMpvShutdownOwnershipTests|WindowsMpvPlaybackRuntimeTests|WindowsMpvPlaybackControllerTests`（各项使用 FullyQualifiedName 包含筛选）共 33/33 通过，包含原 25,000 行 stderr 用例；结果 `exit-handle-target-green.trx/log`。独立同源探针 20/20 均确认真实进程句柄触发、脚本无独占冲突，`EARLY_RETURNS=0`，证据 `exit-handle-probe-green.log`。未增加夹具睡眠、删除重试或期限；完整解决方案复核由主线程继续执行。

### Windows 内核进程句柄退出门禁追加

A 使用独立 Process observer 复现 .NET 10 提前可见 ExitCode/HasExited 而 `WaitForExit(0)` 尚为 false。RTMP 同类资源清理不再把 ExitCode/HasExited 当成内核退出完成：所有释放判断使用 `WaitForExit(0)`；有界等待必须等待真实内核句柄，并继续共享原 Stopwatch 截止期。先加入独立 observer 回归，在 Stop 成功返回时立即检查句柄；不增加产品配置、后台监督框架或服务器修改。

RTMP 修复前观察：cmd 独立句柄32次、显式启用的真实FFmpeg独立句柄12次均未复现提前释放（结果 `rtmp-kernel-exit-red.trx` / `rtmp-kernel-real-red.trx` 实际为通过，不作为失败证据）。此次同步修复依据 A 对相同 .NET API 的4次中3次真实复现及 RTMP 静态同类用法。采用真实 `WaitForExit(0)` 条件轮询，每次最多10ms且受同一Stopwatch剩余期限限制；不会固定睡眠后假定退出，不创建被遗弃的等待任务。
