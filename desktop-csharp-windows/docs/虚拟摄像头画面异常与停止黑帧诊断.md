# 虚拟摄像头画面异常与停止黑帧诊断（2026-09-10）

前半节为离线诊断记录。后续管理员辅助进程与驱动已更新，IPC/黑帧/竖屏 stride 修复已完成真实原生输出验收；最终结果见 [实施记录](./2026-09-09-虚拟摄像头源分辨率与测试组件实施记录.md)。主应用窗口未操作。

## 纹理异常是验收文件格式解释错误

`artifacts/vcam-validation/output-acceptance/native-720-paced.nut` 的采集日志显示
DirectShow 接收格式为 `bgr0 1280×720`，每个真实 packet 为 **3,686,400 字节**。
但 `-c:v copy -f nut` 沿用了 `RGB[15]` codec tag，重新读取时 FFmpeg 将它解释为
`rgb555le`（一帧只解释 1,843,200 字节），导致错误颜色和密集纹理。

把原文件的 packet 用 `-c:v copy -f rawvideo` 导出，再明确以
`-f rawvideo -pixel_format bgr0 -video_size 1280x720` 读取，可恢复正常彩条。
原始 DirectShow RGB 是 bottom-up，离线直接读取这些字节时还需 `vflip`；
正常经过 DirectShow/FFmpeg 解码路径时，不应再无条件翻转画面。

证据文件 `native-720-paced-corrected-upright.png` 已恢复正常色块、文字和几何形状。
因此不为此修改驱动的像素格式、SharedMemory 拷贝或添加 CPU 色彩转换。

不过，正确解释后的 90 帧仅有 24 种 hash，最后 30 帧仅 2 种 hash，
仍然不能证明动态输出合格；这与独立排查的 IPC 阻塞问题一并继续验收。

后续真实接收使用解码后 `-c:v ffv1` 写入 MKV，再检查画面、帧变化及停止黑帧。
不要继续使用这个携带错误 codec tag 的 NUT stream copy 作为验收依据。

## 停止黑帧存在独立的真实代码缺口

上游 `PinPrivate::sendFrame` 在没有有效帧时调用 `randomFrame()`，即使 direct mode
也生成随机噪点。生产者停止时没有预设图片会走这条路径，因此不能满足停止黑帧。

`0006-directshow-yuy2-idle-black.patch` 只对 direct-mode YUY2 返回中性有限范围黑帧
`Y0=16,U=128,Y1=16,V=128`，且生产者变为 inactive 时让它进入黑帧路径；
非 direct 和其他格式沿用上游行为。没有新增队列、缓存、锁或 GPU/CPU 图像变换。

原生 `yuy2_black_frame_test.cpp` 检查 720p、1080p、1080×1920 的两类旧帧全部
覆写为同一合法黑帧，并检查缓冲区前后 guard 字节不变。MSVC x64 编译执行通过，
补丁对含已有 COM/capture-pin 补丁的源树 `git apply --check` 通过。
这些测试不等同于真实设备停止黑帧验收；更新组件后的端到端实测由主线程统一执行。

## 竖屏真实样本中的行填充泄漏

后续 1080×1920 实机灰阶采集发现预期全部为 121 的 2,073,600 个像素中，
15,240 个为 80。上游 `VideoFrame` 的 1080 宽 YUY2 有效行长 2160 字节，
SIMD 对齐后的内部行长为 2176；DirectShow 之前连续复制整个内部缓冲，
把每行多出的 16 字节一同交给下游，导致画面逐行偏移。

`0008-directshow-yuy2-packed-stride.patch` 仅在 YUY2 DirectShow 出口逐行复制有效像素，
将媒体类型、分配大小和 sample 实际长度统一为 `width×height×2`，内部 SIMD 布局、
C API 和其他格式保持原行为。首次真实媒体类型回归失败：原 1080×1920
`lSampleSize/biSizeImage=4177920`，预期 4147200。修复后实际上游媒体类型构造器、
带有 padding 毒值的逐行复制、缓冲边界及 1080×1919 奇数高度测试通过。
该修复仍需要更新后的实际设备均匀帧和彩条回归，不以灰度均值近似代替像素正确性。
