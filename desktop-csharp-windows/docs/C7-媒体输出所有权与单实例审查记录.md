# C7 媒体输出所有权与单实例审查记录

更新时间：2026-09-04

## 审查范围

本轮审查并实施 C# Windows 桌面端与 Rust/Tauri 参考端的启动/退出所有权边界：

- `src/GpAutoLive.Windows/WindowsMediaOutputOwnership.cs`
- `src/GpAutoLive.App/App.xaml.cs`
- `tests/GpAutoLive.Windows.Tests/WindowsMediaOutputOwnershipTests.cs`
- `desktop/src-tauri/src/main.rs`
- `desktop/src-tauri/crates/autolive-media-output-ownership/`
- `desktop/src-tauri/Cargo.toml` 与 `desktop/src-tauri/Cargo.lock`

## 结论与最小修正

- C# 端使用固定 `Local\\GpAutoLive.MediaOutput.Owner.v1` 命名互斥，并用进程内名称集合阻止同一进程重复租约；获取、释放和 abandoned mutex 路径保持立即返回、幂等和 fail-closed。
- C# 启动顺序为：配置 Windows 运行时与 AppUserModelID → 获取媒体/输出租约 → 获取 C# 单实例互斥 → 创建主窗口。任一门禁失败都会释放已经取得的租约；退出时 `MainWindow.OnClosed` 先回收媒体/输出会话，`App.OnExit` 再逆序释放单实例互斥和媒体/输出租约。
- Rust 新增最小 `autolive-media-output-ownership` Windows 封装，使用 `windows 0.61.3` 的 `CreateMutexW`/`WaitForSingleObject`/`ReleaseMutex`，在 Tauri Builder 创建前获取与 C# 相同的 `Local\\GpAutoLive.MediaOutput.Owner.v1`。
- `tauri_plugin_single_instance` 继续负责第二实例的窗口转发；共享媒体 Mutex 负责 C# ↔ Rust 的双边媒体/输出资源所有权，二者职责不再混用。
- C# 的 `autolive-desktop-core` 进程探测保留为更友好的快速提示和 fail-closed 诊断路径，最终是否取得租约仍由共享命名 Mutex 决定。
- Rust helper 只承担句柄生命周期和等待结果映射，Win32 `unsafe` 被限制在该单一平台封装 crate；桌面主 crate 继续 `unsafe_code = forbid`。

该代码已完成双端共享锁实现，但真实 C# 进程与 Rust 进程交叉启动、RTMP/虚拟摄像头/声卡实际资源争用仍属于发布前 `deferred_gate`。
