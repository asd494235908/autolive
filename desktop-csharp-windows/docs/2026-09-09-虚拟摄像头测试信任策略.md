用户明确要求本次用于测试环境，并允许删除本次相关未使用代码；仅做必要代码检查与验证。

## 行为边界

- 默认仍要求 Authenticode 有效。应用目录的 `GpAutoLive.control-plane-profile` 为 `production-v1` 或未知内容时不能使用开发例外；测试 HTTP 控制面本身不授予例外。
- 开发例外必须同时设置 `AUTOLIVE_AKVIRTUALCAMERA_DEVELOPMENT=1` 与 `AUTOLIVE_AKVIRTUALCAMERA_ROOT`（绝对本机包根，含 `akvirtualcamera` 子目录）。所有路径祖先拒绝重解析点。
- `akvirtualcamera/development-manifest.json` 格式为 `{"schemaVersion":1,"files":{"bin/akvirtualcamera-sidecar-x64.exe":"SHA256",...}}`。必须精确列出六项：`bin/akvirtualcamera-sidecar-x64.exe`、`bin/vcam_capi.dll`、`x64/AkVirtualCamera.dll`、`x64/AkVCamAssistant.exe`、`x64/AkVCamManager.exe`、`x86/AkVirtualCamera.dll`。哈希为64位十六进制；文件非空且最多64MiB，清单最多16KiB。
- 逐项校验哈希和签名结果，只接受 `Unsigned` 或 `Valid`；签名无效、探针错误不能被视为未签名。清单证明本地构建文件一致性，不代表发布者身份或正式可发布。
- Locator 返回 `IsDevelopmentTrusted`、`IsTrusted` 和脱敏 `DiagnosticCode`。开发可信启动计划额外携带 `--development-format`；正式计划不能携带此参数。
- Host 在实际启动点重新验证，并在进程生命周期保持清单及六组件只读共享句柄，拒绝启动前文件替换；会话令牌、隐藏启动、Job Object、管道 ACL 和超时继续保留。
- 安装探针保持双注册表所有者、组件完整性与设备存在检查，并补齐显式安装根与注册所有者必须一致。开发包用有效开发清单替代 `release-ready.json`，不生成伪发布就绪状态。
- 原 PnP SetupAPI 枚举不适用于仅注册 DirectShow COM Filter 的设备，已移除并采用微软规定的 System Device Enumerator / `CLSID_VideoInputDeviceCategory` 枚举 FriendlyName。枚举成功只证明设备可列举，不能冒充实际收帧。

参考：[微软 DirectShow 设备枚举](https://learn.microsoft.com/en-us/windows/win32/directshow/using-the-system-device-enumerator)。

## 原生首帧确认补充

管道写入成功不能证明设备输出成功。sidecar 在首次 `vcam_stream_send` 成功之后只发送一次并刷新 `GPAKVC_OUTPUT_READY`。Host 使用每次会话独立的异步完成信号，最多等待5秒；退出、停止和取消均唤醒等待方。Coordinator 必须先启动写入泵，再等待原生确认，成功后才返回 Started；失败按既有 writer→GPU→client→sidecar→Core 顺序有界清理。

仅映射固定退出码：6 提示先关闭下游应用再切换分辨率，7 提示检查设备安装/格式/权限，5 表示原生流创建或发送失败；不透传 stderr。该确认仍不代表下游已显示画面。补充受限状态行、等待/取消、运行态确认和错误映射测试，统一由主线程执行。
