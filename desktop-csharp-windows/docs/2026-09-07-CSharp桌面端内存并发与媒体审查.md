审查日期：2026-09-07。对象：当前工作区 `desktop-csharp-windows`，包含开始审查前已有的未提交改动。审查过程中工作区还存在其他来源的界面改动；测试结论只对应本轮实际构建的代码，不代表后续修改自动获得验收。

## 1. 按优先级排列的发现

### P1：FFmpeg 停止与解码结束并发时使用已释放的取消令牌

位置：`src/GpAutoLive.Windows/WindowsFfmpegPcmDecoder.cs:171`、`:248`、`:268`。

`runCancellation` 是 try 块内的 using 局部变量，离开 try 时先被 Dispose，外层 finally 随后才持有 `_gate` 将 `_activeCancellation` 置空。因此存在 `_activeCancellation` 仍指向已释放对象的窗口；另一线程在 `Stop()` 中调用 `Cancel()` 会抛出 `ObjectDisposedException`。锁住 Cancel 并不能保护锁外的 Dispose。

真实 RTMP 连续轨道探针在停止声音会话时复现，调用链为 `WindowsRtmpAudioSession.StopCoreAsync:707 → WindowsFfmpegPcmDecoder.Stop:268`，探针异常退出。该解码器还被普通声音、候选和插话复用，影响面不限于 RTMP。

同一类的 `DisposeAsync:289` 还忽略 `SemaphoreSlim.WaitAsync(TimeSpan)` 的 bool 返回值：超时返回 false，不会进入 `catch (TimeoutException)`，随后仍 Release/Dispose 信号量。这会破坏仍执行中的解码任务所有权；该第二条为静态发现，未注入原生卡死复现。

修复验收：在同一所有权边界内摘除、取消并释放 CTS；准确处理信号量超时，未 Join 时保留资源及重试入口。增加 EOF/循环边界与 Stop/Dispose 并发的回归测试。

证据：[`probe-final.log`](../artifacts/review-20260907/probe-final.log)。

### P1：最终效果窗口关闭任务在主窗口释放后继续更新界面

位置：`src/GpAutoLive.App/MainWindow.Playback.cs:631–640`；关联 `MainWindow.xaml.cs` 的 `FinalEffectWindow_Closed`、`OnClosed` 和 `MainWindow.MediaThumbnails.cs:8`。

最终效果窗口的 async void 关闭回调启动停止流程，但主窗口退出没有等待该流程。在 `StopMediaForMutationAsync` 返回后仍直接调用 `ApplyMediaSnapshot`，继而读取已被主窗口 Dispose 的 `_windowCancellation.Token`，异常通过 WPF Dispatcher 传播。

真实 WPF 定向组合测试复现：25 项中 24 通过、1 失败，GPU83 测试启动阶段接收到前一个窗口遗留的异常。GPU83 独立进程重跑通过，说明不能将此失败归因于 shader。

修复验收：主窗口持有并回收窗口关闭任务，释放前完成取消/Join；异步恢复点检查关闭状态与当前窗口身份，关闭后不再提交 UI 工作。覆盖“关闭效果窗口后立即关闭主窗口”。

证据：[`app.trx`](../artifacts/review-20260907/app.trx)。

### P1：播放中途开始 RTMP 时画面从零开始，声音来自当前播放位置

位置：`src/GpAutoLive.App/MainWindow.Rtmp.cs:235–241`、`:259–262`。

构造 `RtmpSourceIdentity` 时 `SourcePositionMs` 固定填 0，视频 FFmpeg 因此不生成 `-ss`；音频路径同时传入活动 `FinalPcmBus` 和可切换 RTMP PCM 输出源。用户播放至例如 30 秒后点击推流，画面仍从开头读取，声音则来自当前播放进度。已有参数构造器支持非零起点，但 UI 没传实际位置。

这是调用链可确定的问题，本轮没有录制带时间标记的人声素材量化偏移。合成素材从零开始的独立推流成功不能覆盖此场景。

修复验收：基于同一活动源身份和播放时钟捕获发布起点，定义启动期间的时钟推进处理；验证中途启动、seek、重连、声音周期切换后的远端音画对齐。

### P2：麦克风停止阈值没有参与迟滞判断，会截断较轻的持续语音

位置：`src/GpAutoLive.Media/MicrophoneInterludeGate.cs:138–157`。

`_stopThresholdDb` 仅在构造器赋值，Process 始终只比较启动阈值。默认启动 −42 dB、停止 −48 dB 时，先以 0.02 幅值启动，再持续输入 −45 dB；300 ms 后实际回到 Armed，尽管输入仍高于停止阈值。控制器在非 Speaking/Hangover 状态丢弃输入，可能截断轻声或词尾。

修复验收：Armed 用启动阈值，Speaking/Hangover 用停止阈值及挂起时长维持迟滞；覆盖两阈值之间的持续输入、跌破停止阈值和恢复语音。此字段不应直接按“未使用代码”删除。

证据：探针日志的 `gate_minus45_after_300ms`：`LevelDb=-45, State=Armed, IsSpeaking=false`。

### P2：PortAudio 的“2 秒停止预算”未覆盖原生声卡调用

位置：`src/GpAutoLive.Windows/WindowsPortAudioInputStream.cs:147`、`:379–380`；输出流 `WindowsPortAudioOutputStream.cs` 有同类同步 Stop/Close/Terminate 路径。

输入启动在 Task.Run 中执行原生调用，但没有原生调用级超时；Stop 的两秒仅限制进入信号量，随后 StopStream/CloseStream/Terminate 是同步无超时调用。上层麦克风停止又先无超时等待生命周期信号量。设备/驱动卡住时，取消不会打断 native 调用，主窗口同步等待 Dispose 也会被拖住。

本轮正常虚拟设备启动停止成功，未模拟驱动死锁，因此这项是代码边界缺陷，不是已复现的设备卡死。修复应保留原生资源所有权；不能仅添加超时后丢弃后台任务或卸载仍被使用的 DLL。需补充设备失联/休眠实机门禁，必要时定义独立进程隔离边界。

## 2. 内存与并发检查

- PCM 环缓使用固定数组且容量有限；默认 FinalPcmBus 的四个 48,000 帧、双声道 float 环缓合计约 1.46 MiB，不把完整音轨装入内存。候选切换限制为当前项与一个预载项。
- RTMP PCM 写入使用 ArrayPool 并在 finally 归还；FFmpeg/mpv 有受管进程、Job Object 和读取任务。上述生命周期竞态仍需修复，不能将有 Dispose 接口等同于安全释放。
- 缩略图缓存限制 64 项/16 MiB。审查未进行完整堆快照或所有分支的泄漏证明。
- 本地音频/插话/虚拟输入三轮停止后的探针私有内存为 22,552,576 / 22,601,728 / 23,887,872 bytes；句柄 439 / 444 / 453，线程均 24。采样发生在 Stop 后、该轮 using 对象最终 Dispose 前，包含运行时预热和缓存，不能据此认定泄漏或无泄漏；也不是 WPF 整进程性能基线。
- 结束时未发现 ffmpeg、ffprobe、mpv 或 ReviewProbe 残留。未执行 30 分钟长稳、强制 GC 后比较、堆转储、设备拔插或休眠测试。

## 5. 消融与剩余验收

本轮仅建立最小测试探针，复用现有媒体控制器、FFprobe 导入、编码器选择和测试框架，没有新增产品抽象、依赖、队列或缓存；移除了探针未使用的路径计算。保留固定容量 PCM、原生资源所有者、取消、输入校验及真实状态检查。没有删除现有产品代码；麦克风未使用阈值应通过修复恢复功能，而非删除配置。

代码检查已完成上述重点路径；自动化结果如表；受影响项目本地 Release 编译完成。未执行全量测试、完整发布构建、安装包或签名验证，因为本轮是媒体和生命周期审查，不是发布。容器健康、人工页面点击、外部模型返回均未执行；当前媒体链不调用模型。真实业务结果仅覆盖上述合成素材、虚拟声卡及用户 RTMP 目标短测，不包括服务器配置验收。
