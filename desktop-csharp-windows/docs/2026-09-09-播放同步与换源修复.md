# 播放同步与换源修复

状态：本轮代码与本机定向实测完成，开发入口 Release x64 构建成功。RTMP 真实网络换源/长稳、全显卡矩阵未验收，不能承诺所有设备零停顿。当前产品入口为 C# WPF，历史 Rust/Tauri 链路不作为本次修复对象。

## 范围与调用链

- 本地视频：MainWindow 播放/换源 → WindowsMpvPlaybackController → 单个 mpv gpu-next，GPU83 / CPU4 效果在原会话提交。
- 本地声音：MainWindow → WindowsAudioPlaybackController → FFmpeg PCM → 有界 FinalPcmBus → PortAudio。声音处理与视频处理周期独立。
- 同步：以主音轨实际可听源内 PTS 及实际 PlaybackRate 驱动视频，UI 时间投影不能代替播放器同步。
- 手动与自动换源：保留上一帧、暂停旧画面、同进程加载下一源暂停首帧，音频启动后恢复画面。无音轨视频直接恢复；暂停换源继续暂停。失败保留旧图并报告错误。
- RTMP：直接读源 FFmpeg + 最终 PCM 分流。换源保存用户已启用配置，停止旧发布，新源成功后恢复发布；失败不发布错误源。当前进程依旧固定单源，重建发布会产生间隙，不能宣称跨文件零断流。

## 已确认原因与最小实现

1. 视频监视器仅替换界面显示时间，从未纠正 mpv；新增原串行命令边界内的同步调用，小漂移限幅调速，超过 500ms 才精确 seek。
2. 首次启动及换源先运行视频、后启动音频，造成初始化时间差；音频建立后做一次对齐，换源用既有暂停加载能力避免新视频抢跑。
3. 音频输出补零被当成源媒体帧；主音轨读取计数用于可听位置，插话及欠载不能带动主源时钟。
4. 首轨 `-re` 限速妨碍缓冲与倍速消费；仅在已有总线背压路径复用候选的不限速解码能力。
5. RTMP 换源停止后清空配置；统一保存/恢复发布意图。RTMP 当前 CPU4 静态效果与预览 GPU83 的差异继续如实记录。

不新建播放器池、无界缓冲、重试体系或新的依赖。沿用会话身份、取消、Join、IPC 允许列表和错误传播。不清理无关未使用代码。
